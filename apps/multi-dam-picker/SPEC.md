## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party), but many sites keep their media in a third-party DAM, and only AEM Assets is documented in EW. Today an author who wants a **Cloudinary** image has to leave EW, open the Cloudinary Media Library, find the asset, hand-build or copy a delivery URL, guess whether the multi-megabyte original or a resized version is appropriate, paste it, and retype alt text from the asset's metadata. Nobody checks that the URL works for a visitor, that its size is sensible, or that the alt text exists.

Cloudinary brings two problems that shape the design:

1. **No per-user login for the API.** Cloudinary's Admin and Search APIs authenticate with one API key and secret for the whole product environment (HTTP Basic) [VERIFIED: https://cloudinary.com/documentation/admin_api_overview.md]. There is no end-user OAuth flow to put behind a "Connect" button. The secret is powerful (it can read, change and delete every asset and sign any delivery URL), and the extension code is public static files, so a worker must hold it. Because every EW author then acts through one credential, the worker is also the only place that can limit who may browse and how much.
2. **Renditions are made, not listed.** Cloudinary does not return a list of ready-made renditions. A rendition is a delivery URL with a transformation string inserted ("scale down to at most 1200 px wide, automatic format and quality"). With **strict transformations** enabled, unsigned dynamic transformations are rejected, and the fix, a signed delivery URL, needs the API secret, so it can only be produced on the server [VERIFIED: https://cloudinary.com/documentation/control_access_to_media.md, "Strict transformations": transformations are allowed only via eager transformations, signed delivery URLs, allow-listed named transformations or referral domains].

For the maintainer there is a third problem: four DAMs are planned (Cloudinary, Dropbox, Bynder, Frontify; the Contentful marketplace carries apps for all of them). If each were its own extension, the picker UI, error handling, quota protection and (for three of them) the OAuth/token plumbing would be written four times and drift. The first ticket must therefore deliver one picker shell and a provider interface that already expresses **both** credential kinds, so that Dropbox can add per-user OAuth without redesigning anything and Bynder and Frontify can arrive as modules.

A fourth problem comes from the platform. A web action that holds a vendor key must be reachable only by callers EW vouches for, from origins EW uses; App Builder answers every origin with `Access-Control-Allow-Origin: *` unless the action opts out, and its built-in Adobe auth annotation is organisation-scoped (#2 Decisions 5-6). Those traps are owned by the #2 template; this ticket must use it correctly and prove, on its own routes, that the secure behaviour holds.

## Solution

A **Multi-DAM Picker** library plugin, listed in the EW editor library of the demo site. An author opens it and, because the Cloudinary credential is configured in the worker, sees the Cloudinary asset grid immediately (newest first, within the configured root folder `samples/` on the test environment), with no sign-in step. They search by keyword (typing searches automatically after a short pause), filter by type (images, videos, documents, audio), sort, and open an asset to see a larger preview with name, dimensions and type. They choose a rendition (default **Web**: at most 1200 px wide, automatic format and quality, never upscaled; others Large, Medium, Small, and the original file when browsers can display it), review an alt text prefilled from Cloudinary metadata (editable, or marked decorative), and insert it at the cursor as an `<img>` with the rendition URL and the alt text. Videos, audio, PDFs and other files are inserted as a link with the asset name.

Behind it, the per-extension **worker** (an App Builder app at `apps/multi-dam-picker/worker/`, built from the #2 template: IMS-token-authenticated, CORS-restricted, one raw web action `api` in package `multi-dam-picker`) holds the Cloudinary API key and secret as encrypted action inputs fed from its untracked `.env` at `aio app deploy` time, calls Cloudinary's Search and Admin APIs server-side through the template's `proxy` helper, maps the author's search and filters to a Cloudinary search expression in which user text can only ever be quoted literals, normalises results, builds rendition URLs from structured fields Cloudinary returns, and, when the site enables it, **signs those URLs server-side** so they work under strict transformations. To protect Cloudinary's Admin API quota (500 requests per hour on Free [VERIFIED: admin_api_overview.md]) the browser debounces search, page sizes are modest, and the worker caches results briefly in the App Builder State store (shared by all containers of the workspace) and stops early when Cloudinary reports the quota is nearly spent. The browser only ever holds the author's own IMS token and normalised asset data, never the Cloudinary credential.

The shell is provider-agnostic. A **provider interface** defines identity and capabilities, the **credential kind** (`service` or `user-oauth`, with the members each kind must supply), browse/search, asset detail with renditions and metadata, and failure classes. A shared conformance suite enforces it for every provider and both kinds. This ticket fully builds the `service` kind (Cloudinary) and defines, validates and reserves the `user-oauth` kind; #25 turns that kind on (OAuth routes, token store, browser connect panel) without changing the interface or any browse code, and #22/#24 add one module each.

The plugin is verified inside real EW on the demo site with `ref=local` (page on `localhost:3000`, calling the Stage worker) and with a branch ref (page on the code site's branch host, calling the Stage worker); `main` calls the Production worker (the #2 origin rule).

## Implementation Decisions

(No file paths or code, except tables where a shape carries a decision. Layout is in the Build Analysis. Template contracts are referenced as "#2 Decision N".)

**D1. Surface: library plugin only, one extension, one worker.** Registered by rows in the `library` config tab of the demo site (the #1 convention: the folder is `apps/multi-dam-picker/`, the type comes from the sheet row). No fullscreen app. All providers share the same page, the same browser code and the same worker (one App Builder app, one web action); a provider adds server-side code only.

**D2. Build our own picker UI; do not embed Cloudinary's Media Library widget.** The widget (https://cloudinary.com/documentation/media_library_widget.md) loads third-party JavaScript into the page, requires each user to log in to Cloudinary with a seat licence, and can fail where third-party cookies are blocked [VERIFIED 2026-11-16: that page]; its authentication happens in the browser, which contradicts AC2/AC8 (credentials held only by the worker), and it is Cloudinary-only, so it cannot be the provider-agnostic shell AC4 requires. Its upside is per-user Cloudinary permissions; that is a different design [OPEN: Question 6].

**D3. The provider interface (the AC4 deliverable).** A provider is a self-describing module owned by its own folder and registered by one registry entry. Members (behaviour-level; the exact field names are fixed by the contract tests):

| Half | Member | Required for | Meaning |
|---|---|---|---|
| Identity | `id` (lower-case slug), `label` | both | namespaces routes, config and cache; label is shown to authors |
| Identity | `credentialKind` | both | `service` or `user-oauth` (D4) |
| Capabilities | `assetTypes` | both | subset of image, video, document, audio the provider can filter by |
| Capabilities | `sorts` and `defaultSort` | both | provider-declared sort ids with labels; a sort may be flagged *requires a query* |
| Capabilities | `window` | both | the maximum number of results reachable per query (Cloudinary 500); the shell never asks beyond it |
| Capabilities | `assetIdPattern` | both | the shell validates every asset id against it before any provider call |
| Capabilities | `outboundHosts` | both | the list of hosts the provider may call; the shell hands the provider a `proxy` pinned to it (the proxy helper's `allowedHosts`, #2 Decision 11) |
| Capabilities | `deliveryHosts` (a function of config) | both | the hosts allowed in every URL the provider returns (D13) |
| Capabilities | `cacheSeconds` default | both | default result-cache lifetime; `0` disables (D17) |
| Config | required inputs, optional inputs and secrets, with validators | both | a provider whose required inputs are empty at runtime is omitted, not fatal; an invalid value fails registration naming the setting, never the value (D5) |
| Browse | `search(query, type, sort, page, pageSize)` | both | returns normalised summaries, `hasMore`, optional `total` |
| Browse | `getAsset(id)` | both | returns the normalised detail (renditions, alt candidate, insertable, link URL); may perform an idempotent provider-side effect (a documented, README-stated exception; none in this ticket) |
| Failure | failure classes | both | the provider reports failures as one of: bad request, not found, forbidden, rate limited (with a retry delay), misconfigured, upstream unavailable; `user-oauth` adds *reauth required* and *not connected* (D4) |
| Auth: `service` | credential application | `service` | the provider composes its credential from the secret accessor and applies it to its outbound calls through the proxy helper (Cloudinary: Basic, D6) |
| Auth: `user-oauth` | `scopes`, `buildAuthorizeUrl(state, redirectUri)`, `exchangeCode(code, redirectUri)`, `refresh(refreshToken)`, `accountName(credentials)`, optional `revoke(credentials)`, optional maximum `state` length | `user-oauth` | pure HTTP mappings; the shell owns state sealing, cookies, token encryption and storage, refresh orchestration and credential injection into `search`/`getAsset` (D4) |

The shell owns everything else: author authentication (the #2 pipeline), routing, input validation, error mapping to the #2 error contract, the result cache, the output URL policy (D13), logging and redaction, and all UI. A provider never receives the IMS token or the raw request headers and never reads raw storage; it is handed a per-call context made from the #2 handler context minus identity details it does not need: validated config, secret accessor, a `proxy` pinned to its `outboundHosts`, the store (namespaced by provider id), the injected clock, and for `user-oauth` the author's credentials. Registration is validated when the action's registry is first built (cold start): a provider missing a required member, with a malformed id or id pattern, with a duplicate id, or declaring a credential kind this build cannot host makes the registry build throw; the action then answers every `/dam/*` request (after authentication) with `500 misconfigured` and logs the provider and member name only. The same validation runs in CI against the registry and in the pre-deploy step against the real `.env` (D22), so a deploy never ships a broken registry.

**D4. Two credential kinds are defined now; only `service` is hosted by this ticket.** `service` (Cloudinary) is fully built. `user-oauth` is **defined, validated and reserved**: its required members are part of the interface (D3) and the conformance suite validates a stub `user-oauth` declaration, but the worker core hosts only the kinds in a "hosted kinds" set, which is `{service}` in this ticket. Registering a `user-oauth` provider while the set lacks it fails the registry build ("credential kind not hosted by this build"), so a half-working OAuth provider can never ship. #25 adds `user-oauth` to the set together with: the worker routes (connect, session, disconnect, the two public OAuth browser routes), the encrypted token store, refresh orchestration and credential injection, and the browser connect/disconnect panel. The places it plugs in are fixed here so that it is additive:

- The provider list reports, per provider, `credentialKind` and a `connection` object with a `state` of `connected`, `not_connected` or `reauth_required` (plus an optional account label). `service` providers always report `connected`. The browser shell acts on `connected` only; for any other state it shows the provider as unavailable with a fixed notice (this branch is the single browser extension point that #25 replaces with the connect panel).
- The routes `/dam/{provider}/connect|session|disconnect` and `/oauth/{provider}/begin|callback` are **reserved and not routed** in this ticket (with the auth-first pipeline: no token gives `401`, a token gives `404 not_found`).
- The failure classes *reauth required* and *not connected* are reserved; no shell code path in this ticket emits them, so no new error codes are added to the #2 contract here.
- The result cache applies to `service` providers only (D17); #25 defines the per-user scope for `user-oauth` before enabling it there.
- The unauthenticated OAuth callback and the template gaps it needs (public routes with a custom authenticator, per-request dynamic redaction, HTML responses with custom headers, a vault or encrypt-before-store decision for long-lived tokens, since #2 Decision 10 keeps long-lived credentials and refresh tokens out of State) are **#25's**, not this ticket's; none is a prerequisite of #23.

**D5. Provider hosting rules (settled here so no later ticket must amend the shell).**
- *Config and secrets:* a provider is **registered iff all its required inputs are non-empty at runtime**; otherwise it is omitted from the provider list and its routes answer `404 not_found`; the action still works for the other providers. An invalid *present* value (bad API host, bad root folder, bad renditions JSON, bad signing algorithm) makes the registry build fail with a message naming the setting (D3), never the value. In this ticket only Cloudinary's inputs exist in the app config, so the #2 pre-deploy guard (every referenced `$NAME` present and non-empty in `.env`) is exactly right for them. When #25 adds a second provider's secrets to the same app config, the guard would force every site to set every provider's secrets; making a provider's `$NAME` inputs optional-by-declaration is a template gap that #25 raises (hand-off, not a #23 dependency).
- *Thumbnails:* `thumbnailUrl` is optional on a summary (audio and raw files have none; the browser shows a file-type placeholder). When present it is an `https:` URL on a delivery host, or an inline `data:image/jpeg|png|webp;base64,...` URI of at most 64 KB (needed by Dropbox, which exposes no thumbnail URL; costs nothing before the shell is built). Nothing else is allowed in `thumbnailUrl`, and every other URL the shell returns is `https:` only [OPEN: Question 8: drop the data-URI allowance if the owner prefers #25 to ask for it].
- *Result window instead of cursors:* the shell's list call takes `page` and `pageSize` and returns `hasMore`; a provider declares a `window` (the largest result count it can reach) and emulates pages by fetching `page x pageSize` results and slicing. Cloudinary (500) and Dropbox (cursor-only) fit; Bynder (100,000) fits. A cursor on the wire is not added until a provider needs more than its window [OPEN: Question 9].
- *Sorts and types:* a provider may declare a subset of the four asset types and any list of sort ids; the browser builds its filter and sort controls from the declaration.
- *URL rule:* the **shell** never constructs or parses vendor URLs. A provider may build URLs only from the vendor's documented URL grammar and the structured fields its API returned (Cloudinary does so for renditions, D13), must never derive them from user input, and every URL it returns passes the shell's output policy (D13).

**D6. Auth model for Cloudinary: one service credential, HTTP Basic, held by the worker.** The worker calls `https://{api-host}/v1_1/{cloud_name}/...` with `Authorization: Basic base64(api_key:api_secret)` [VERIFIED: https://cloudinary.com/documentation/admin_api_overview.md, "Basic Authentication over secure HTTP" with the API key and secret from Console Settings > API Keys; re-read 2026-11-18]. Both the key and the secret are worker **secrets**: committed app config references them only as `$CLOUDINARY_API_KEY` and `$CLOUDINARY_API_SECRET`, the untracked `.env` supplies the values at deploy, and the platform stores them encrypted as action inputs (#2 Decision 9). The key is an identifier, but AC2 says "API key/secret are held by the worker", and a secret-named input keeps both out of literals and under #2's secret-hygiene checks (UR3). The credential travels in the header, never in a URL (the documented `curl` form puts it in the URL userinfo; `fetch` does not use that). The inbound IMS token is never forwarded (the proxy helper strips it, #2 Decision 11). The API host defaults to `api.cloudinary.com`; `api-eu.cloudinary.com` and `api-ap.cloudinary.com` exist for EU/AP data centres, an Enterprise-plan premium feature [VERIFIED: admin_api_overview.md]; the host must be one of the three and is the only outbound host. The #2 proxy contract expresses auth as `{ secret, scheme }` with one secret name; Basic needs two: gap TG1 (D22).

**D7. Authorisation reality (shared credential).** Every authenticated EW caller of the worker acts as the one Cloudinary credential, so Cloudinary's own per-user permissions do not apply (no per-user mechanism for the Admin/Search API was found in the docs read [ASSUMPTION it does not exist]). Controls the design provides: (a) an optional **root folder** ANDed into every search and checked on detail (`samples` on the test environment); (b) only the public `upload` delivery type is browsable (D8); (c) the template's IMS client-id allow-list (`ALLOWED_IMS_CLIENT_IDS`) and optional `authorize` hook (#2 Decisions 5 and 20), which decide who may call the worker at all; (d) the README states the model in the first lines of the Cloudinary section. A per-user allow-list by IMS user id is a possible follow-up through the `authorize` hook [OPEN: Question 3].

**D8. Only publicly deliverable assets are browsable.** The search expression always contains `type=upload` (the public CDN delivery type); `private` and `authenticated` delivery types need signed URLs for the original and (authenticated) every derivative, and a signed URL "doesn't prevent link sharing", so they are excluded rather than inserted [VERIFIED: control_access_to_media.md, "Restrictive delivery types" and "Signed URLs" rows, re-read 2026-11-18]. Within `upload` assets, one with a non-empty `access_control` (token or time-limited access) is returned but flagged not insertable with the reason "access-restricted in Cloudinary", and one whose `moderation_status` is `rejected` is likewise not insertable [ASSUMPTION: the field is present only when moderation is in use]. The older `access_mode` field is documented as "no longer supported" in favour of `access_control` [VERIFIED 2026-11-16: search reference, Expression fields table], so it is not relied on. Assets with `status` other than active are not offered. The shell warning enum (limited-use, archived, watermarked) has no Cloudinary equivalent, so `warnings` is empty.

**D9. Search: a JSON body to the Admin API search method; user text confined to quoted literals (the AC1 filter logic and the injection boundary).** Endpoint `resources/search` (Tier 1, on by default for environments under 10 million assets [VERIFIED 2026-11-16: https://cloudinary.com/documentation/search_method.md]). The reference states "When making direct calls to the Cloudinary endpoint, make sure to pass any parameters using JSON (with `Content-Type: application/json`) as in the cURL examples", and those examples send `-d '{...}'` bodies (`curl -d` issues a POST) with `expression`, `sort_by`, `max_results`, `fields` [VERIFIED 2026-11-18: admin_api_resources_search_for_resources.md; its syntax line says `GET /resources/search`, so a GET variant is documented but unspecified: [ASSUMPTION] POST confirmed against `yifoe45l` in M1]. The proxy helper retries `POST` only on `429` by default; the provider marks the read-only search as safe to retry on `5xx` through the explicit opt-in (#2 Decision 11, UP7).
- **Expression:** the AND of (1) always `type=upload`, (2) the root-folder clause when configured, (3) the type clause, (4) the keyword clause. *Keyword:* the user text is trimmed, limited to 200 characters and 8 words; every `"`, `\`, `*` and control character is replaced by a space (removed, not escaped, so nothing depends on escape semantics); each remaining word is wrapped in double quotes and the words joined with `AND` inside parentheses. This leans on the documented rule that inside quotes colons, parentheses and other reserved characters are literal and only `"` and `*` need escaping [VERIFIED 2026-11-16: https://cloudinary.com/documentation/search_expressions.md]. *Type clause:* `image` = `resource_type=image` and not a document format; `video` = `resource_type=video` and not an audio format; `audio` = `resource_type=video` and an audio format; `document` = `format=pdf` or `resource_type=raw`; `all` = no clause. The audio and document format lists are provider constants [ASSUMPTION: audio = mp3, wav, flac, aac, m4a, ogg, oga, opus, aiff; reconciled against test assets in M3]. The split exists because PDFs are stored as `image` and audio as `video` [VERIFIED 2026-11-16: https://cloudinary.com/documentation/cloudinary_glossary.md, "Audio files and PDFs are NOT raw files"]. *Root clause:* `asset_folder` in dynamic folder mode (the exact folder or the prefix form), `folder` in fixed folder mode [VERIFIED 2026-11-16: field split in the Expression fields table; `asset_folder` and `display_name` are "not supported" in legacy fixed folder mode]; the root is administrator configuration (`samples/` normalised to `samples`: trailing slashes stripped), validated against a conservative character set and escaped with the documented backslash rules for unquoted terms.
- **Sort:** `newest` omits `sort_by` (the default is descending creation date [VERIFIED 2026-11-18: search reference]); `oldest` = `created_at` ascending; `name` = `public_id` ascending (the identifier, not the display name); `relevance` = `score` descending, accepted only with a keyword [VERIFIED 2026-11-18 for `score` and the `sort_by` shape; the sortable-field list beyond the doc examples is unverified, M1].

**D10. Request and response size control.** The search request sends a `fields` list limited to what the summary needs: `public_id`, `asset_id`, `asset_folder`, `display_name`, `filename`, `format`, `resource_type`, `type`, `version`, `width`, `height`, `bytes`, `secure_url`, `created_at`, `uploaded_at`, `access_control`, `moderation_status`, `status`. Compared with the 2026-11-16 draft, `tags` and `context` are **dropped from search** (a summary needs neither; alt text and tags come from the detail call), which shrinks a 500-item response and keeps metadata out of the list. `fields` takes top-level attribute names, takes precedence over `with_field`, and `public_id`, `asset_id`, `asset_folder`, `created_at`, `status`, `type`, `resource_type` are always returned [VERIFIED 2026-11-18: search reference]; that each listed name is honoured is confirmed in M1. The single-resource detail call has no `fields` parameter and returns "details on all derived assets" [VERIFIED 2026-11-16: the by-asset-ID page], so its payload grows as renditions are generated; the mapper drops everything it does not allow-list. Raw Cloudinary payloads never cross to the browser: Cloudinary "may add more fields ... at any time" [VERIFIED 2026-11-18: admin_api_overview.md], so mapping is allow-list based and forward compatible. Platform bound: the worst search call (page 21 of 24 = 500 results) is an estimated 300-400 KB upstream [ASSUMPTION: about 700 bytes per trimmed item; measured in M1], under the Runtime 1 MB parameter, payload and result limits [VERIFIED: https://developer.adobe.com/app-builder/docs/guides/runtime_guides/system-settings, as cited in #2]; the proxy's upstream-size cap must allow it (TG4, D22).

**D11. Asset identity and detail.** The shell id is Cloudinary's immutable `asset_id` (stable across rename and move, supported in both folder modes [VERIFIED 2026-11-16: https://cloudinary.com/documentation/folder_modes.md]); the provider's `assetIdPattern` is 32 lowercase hex [ASSUMPTION universal; every documented sample id has that form]. Detail uses `GET resources/{asset_id}` [VERIFIED 2026-11-16: endpoint on the by-asset-ID page] because it is authoritative and immediate whereas search is eventually consistent ("within a few seconds" [VERIFIED 2026-11-18]) and because the single-resource response carries structured `metadata` and `context` (the documented by-public-ID sample shows `context.custom.alt` and `caption` [VERIFIED 2026-11-16]; the by-asset-ID response is assumed identical, ASSUMPTION; M1 records a real one). Detail enforces the same scope as search: an asset whose delivery type is not `upload` or that sits outside the configured root returns `404 not_found`, never its data.

**D12. Result window and pagination.** The shell passes `page` and `pageSize` (default 24, cap 50). The provider requests `max_results = min(500, page x pageSize)` and returns the slice for that page; `total` = `total_count`; `hasMore` is true only while the end of the slice is below both `total_count` and the 500 window; a page whose first item would fall beyond the window is `400 bad_request`. [VERIFIED 2026-11-18: `max_results` maximum 500, `next_cursor`, `total_count` (`max_results=0` returns only the count).] Cost: one Admin API request per call, equal to cursor paging; the payload grows with the page number (trimmed by `fields`), and results can shift between calls because of eventual consistency, so the browser de-duplicates on append. The README says "browse shows the first 500 matches per query; refine with a keyword, type or folder".

**D13. Normalised asset contract, rendition construction and the shell's output URL policy.**
- *Summary:* `id`, `provider`, `name`, `type` (image, video, document, audio, other), optional `thumbnailUrl`, optional `width`, `height`, `extension`, `fileSize`, `dateModified`, `warnings[]`. *Detail* adds `description`, `tags[]`, `copyright`, `alt { value, source: property | description | name | none }`, `renditions[] { id, label, url, kind: derivative | original, width?, height? }`, `defaultRenditionId`, `insertable { ok, reason? }`, `linkUrl?` (non-image asset URL).
- *Cloudinary mapping:* `id` = `asset_id`; `name` = `display_name` in dynamic mode, else the last path segment of `public_id`; `type`: PDF (`resource_type=image`, format `pdf`) is `document`, `image` is `image`, `video` with an audio format is `audio`, other `video` is `video`, `raw` is `document` (or `other` for fonts and similar by a small format list); `extension` = `format`; `fileSize` = `bytes`; `dateModified` from `uploaded_at` when present (search returns `created_at` and `uploaded_at`). `copyright` is omitted (no native field).
- *Rendition grammar* [VERIFIED 2026-11-16: https://cloudinary.com/documentation/image_transformations.md, "Transformation URL structure"]: `https://res.cloudinary.com/<cloud_name>/<asset_type>/<delivery_type>/<transformations>/<version>/<public_id>.<extension>`; transformations, version and extension are optional; chained steps are separated by `/`. Observed 2026-11-18 on the test environment: `https://res.cloudinary.com/yifoe45l/image/upload/c_limit,w_300/samples/landscapes/beach-boat.jpg` answers `200` and is about 9 KB against 1.2 MB for the original, which is the saving the default rendition exists for.
- *Method:* take the `secure_url` exactly as the API returned it, locate the first `/<resource_type>/<type>/` segment, require the remainder to begin with `v<version>/` and the public ID, and insert the transformation (and, when signing, the signature) between the delivery type and the version. If the URL does not match, the asset is not insertable with the reason "unrecognised Cloudinary URL". No public ID, cloud name or host is re-derived from user input or from other fields; only API-returned values are used.
- *Default set (images; administrator-overridable by a JSON list):* `web` (default) = scale down to at most 1200 px wide with automatic format and quality; `large` = 2000 px; `medium` = 800 px; `small` = 400 px; `original` = the returned `secure_url` unchanged, offered only for browser-displayable formats (jpg, jpeg, png, gif, webp, avif, svg). "Scale down only" is the `limit` crop mode ("Same as fit, but only scales down the image" [VERIFIED 2026-11-16: https://cloudinary.com/documentation/resizing_and_cropping.md]); `f_auto` and `q_auto` are the documented optimisation transformations [VERIFIED 2026-11-16: image_transformations.md]. Each rendition's reported dimensions are `min(asset width, rendition width)` with proportional height.
- *Non-image assets:* no transformation; `linkUrl` is the returned `secure_url` for videos, audio, PDFs and raw files; `renditions` is empty.
- *Thumbnails:* images get a fixed small `limit` rendition (320 px wide with `f_auto,q_auto` [ASSUMPTION: size]); videos use the same with a still-image extension; PDFs use the first page as an image; audio and raw files have none [ASSUMPTION: the video-poster and PDF-page URL forms are not stated in the pages read; confirmed in M3]. Thumbnails are signed like any transformed URL.
- *Output URL policy (shell-enforced, provider-agnostic):* after a provider returns, the shell drops every field outside the contract, requires every URL (renditions, `linkUrl`, `thumbnailUrl`) to be `https:` (thumbnails may also be the inline form of D5) and its host to be in the provider's `deliveryHosts(config)`; a violating rendition or link makes the asset not insertable with a fixed reason, a violating thumbnail is dropped. For Cloudinary the hosts are `res.cloudinary.com` plus the administrator's list (private CDNs and CNAMEs are a paid-plan feature [VERIFIED 2026-11-16: pricing page lists "Custom domain (CNAME) support" on Advanced and above; image_transformations.md, "cloud_name" row]). This is what turns "a provider may construct URLs" (D5) into a safe rule.

**D14. Signed delivery URLs, generated server-side (AC2).** When `CLOUDINARY_SIGN_URLS` is on, every transformed URL (renditions and thumbnails) carries a signature component `s--<8 chars>--` immediately after the delivery type. The signature is the first 8 characters of the URL-safe base64 of the SHA-1 (or, when configured, SHA-256) digest of the string made of the transformation(s), public ID and extension joined with `/`, followed immediately by the API secret [VERIFIED 2026-11-18: https://cloudinary.com/documentation/delivery_url_signatures.md; the documented example `c_fill,w_300,h_250/e_grayscale/sample-authenticated.png` with secret `abcd` gives `iDy_JeBq` with SHA-1, and Node `crypto` recomputed on 2026-11-18 gives `iDy_JeBq` for SHA-1 and `rSONCRLG` for SHA-256: known-answer test vectors]. Both SHA-1 and SHA-256 are accepted by default and an account can restrict itself to SHA-256 [VERIFIED 2026-11-18], hence the algorithm switch. Why it is needed: with strict transformations enabled dynamic transformations are rejected unless eager, allow-listed, referral-domain based or signed [VERIFIED 2026-11-18: control_access_to_media.md]. Why server-side: the secret "should never be generated on the client side" [VERIFIED 2026-11-18: delivery_url_signatures.md]. The signing code runs in the action with Node's `crypto` and the secret accessor; the signed `original` URL is not altered (it carries no transformation).
- **Version handling (documented ambiguity).** The doc says the signed string contains "any transformation parameters, the version number, the public_id, and file extension that will be used in the delivery URL" [VERIFIED 2026-11-18], yet its worked example has no version, and the SDK convention is to leave the version out [ASSUMPTION about the SDK]. To make both readings agree, **signed URLs omit the `v<version>/` segment** (so the signed string is exactly the documented example form); unsigned URLs keep the API's version. The rule is one provider constant covered by a test and confirmed against a strict-enabled environment in M6; fallback if M6 shows version-less URLs fail: include the version in the URL and in the signed string [OPEN: Question 5].
- **Percent-encoded public IDs.** How a public ID containing `%` (or other characters that need URL encoding) must be signed is not stated; when signing is on, such an asset is not insertable with a reason, until M6 settles it [ASSUMPTION].
- **Default off, guidance on.** `CLOUDINARY_SIGN_URLS` is `false` until M6 proves the signing rule against a real strict-enabled environment (which `yifoe45l` currently is not, see decision 3); the README recommends `true` whenever strict transformations are on [OPEN: Question 5: flip the default after M6]. The signature is derived data that ends up in public page content by design; the secret and the digest input are never returned or logged.
- **Rotation consequence.** The signature is derived from the API secret, so rotating the secret changes every signature; URLs already inserted into published pages carry old signatures [INFERENCE from the signature definition; whether Cloudinary keeps accepting old signatures is not documented: observed in M7]. The README states it, and it is a reason to leave signing off where strict transformations are off.

**D15. Alt text policy (AC1 "alt text from asset metadata").** A ranked fallback returned with its source, mapped to the shell enum: (1) `property`: the contextual-metadata field named by `CLOUDINARY_ALT_CONTEXT_FIELD` (default `alt`, Cloudinary's documented text-alternative field [VERIFIED 2026-11-16: https://cloudinary.com/documentation/accessible_media_images.md]) or, when configured, the structured-metadata field `CLOUDINARY_ALT_METADATA_FIELD` (detail only: search returns `metadata` only on Tier 2 [VERIFIED 2026-11-18: search reference, `with_field`]); (2) `description`: the contextual field `CLOUDINARY_CAPTION_CONTEXT_FIELD` (default `caption`; documented as a conventional example key, [ASSUMPTION it is conventional rather than built-in]); (3) `name`: the display name or filename without extension, separators turned into spaces; (4) `none`: empty, flagged "needs alt text". The setting names say `FIELD`, not `KEY`, so the #2 UR3 rule (inputs named `*KEY*` must be `$NAME` secrets) does not misclassify them. The context object appears as `context.custom.<field>` in the documented single-resource sample; the mapper accepts both `context.custom.<field>` and `context.<field>` because the search response shape was not shown [ASSUMPTION, fixture-settled in M1]. All candidates are stripped to plain text (markup, entities and control characters removed, whitespace collapsed). The author always sees and may edit the value or mark the image decorative. Cloudinary's AI captioning add-on is out of scope.

**D16. Errors and limits (all mapped to the #2 error contract; fixed messages; no upstream text).** Cloudinary statuses: 200, 400, 401, 403, 404, 409, 420 [VERIFIED 2026-11-18: admin_api_overview.md "Error handling"]. Mapping onto #2 Decision 12 codes: `400` -> `400 bad_request`; `401` and `403` -> `500 misconfigured` with a log line naming the cause class only (the credential is shared, so the author cannot fix it and must not be invited to "reconnect"; Cloudinary notes HTML bodies on authentication problems [VERIFIED 2026-11-18], so a non-JSON body on any status is never parsed and is treated as upstream failure); `404` on detail -> `404 not_found`; `409` -> `502 upstream_unavailable`; `420` and `429` -> `429 rate_limited` with `Retry-After` computed from `X-FeatureRateLimit-Reset` (an HTTP date [VERIFIED 2026-11-18: headers `-Limit`, `-Remaining`, `-Reset`]) minus now, at least 1 s, capped at 3600 s, 60 s when the header is absent; `5xx` and network errors -> the proxy's retries, then `502 upstream_unavailable`. `420` is declared to the proxy as a rate-limit status (#2 Decision 11, UP13) and is deliberately **not** retried (the window is up to an hour, longer than the proxy's 15 s deadline). A failing store never fails a request (D17).

**D17. Quota protection (AC3).** The Admin API allows **500 requests per hour on the Free plan and from 2,000 per hour on paid plans**, counted per request and shared by every author; search and detail each cost one request (a detail call with `versions=true` costs more and is never used) [VERIFIED 2026-11-18: admin_api_overview.md, "Usage limits" and "How requests are counted"]. Five controls:
- (a) the browser **debounces** search (about 350 ms after the last keystroke, Enter searches immediately [ASSUMPTION: value]) and cancels a superseded request;
- (b) **modest page sizes**: default 24, hard cap 50, enforced by the shell for every provider;
- (c) a **short result cache in the shell**, default 30 s per provider (`CLOUDINARY_CACHE_SECONDS`, `0` disables), kept in the template's **store** (App Builder State in the deployed action, so every container of the workspace shares it; the in-memory twin in tests). The key is provider id plus a SHA-256 hex digest of the provider's configuration fingerprint (cloud name, root, folder mode, signing switch and algorithm, renditions, delivery hosts) and the full validated request (query, type, sort, page, page size), which satisfies the State key rules (alphanumeric plus `-_.`, at most 1024 bytes [VERIFIED 2026-11-18: application-state page "Constraints"]); the value is the compact JSON of the normalised response, stored only when at most 64 KB, with TTL set in seconds (default 1 day, so an explicit short TTL is always passed; whether State enforces a minimum TTL is not documented [ASSUMPTION: none, UT1/M10]). It applies to `service` providers only, where it is safe to share across authors precisely because every author sees the same data under the shared credential and scope; detail responses and errors are never cached. State limits that bound it [VERIFIED 2026-11-18: https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/storage/]: 2 MB/min bandwidth per non-production workspace (10 MB/min Production), counting bytes uploaded plus downloaded; at roughly 20 KB per entry that is about 100 entry transfers per minute on Stage, well above what the 500-per-hour Admin quota can generate on misses, so State bandwidth is not the binding constraint at this scale [INFERENCE; measured in M10]. A store failure (`store_unavailable`, a State `429` or `403`) is swallowed by the shell: the request is served from upstream without caching;
- (d) an **early stop**: the provider records `X-FeatureRateLimit-Remaining` and `-Reset` from each response in the store (a tiny value whose TTL is the time until reset, capped at one hour) and, when `Remaining` falls to the reserve (20 requests [ASSUMPTION: starting point]), answers the next calls with `429 rate_limited` until the reset time instead of spending the last requests; when the store is unavailable the early stop is skipped (best effort);
- (e) the shared Runtime limits are respected by construction: 6,000 actions per minute and 100 concurrent activations per namespace, shared with every other worker in the workspace (#2 Decision 9); the debounce and page cap keep this extension far below them.
Thumbnails and renditions are delivered by the CDN and do not count against the Admin API limit [VERIFIED 2026-11-18: the limit "refers only to Admin API requests"; delivery is not an Admin API request].

**D18. Insertion and experience.** Images: the browser builds one `<img>` with only `src` (the chosen rendition URL) and `alt`, serialises it with DOM APIs (never string concatenation), and sends it with `actions.sendHTML`, then `actions.closeLibrary`; non-images: a single `<a>` whose text is the asset name; only `https:` URLs are ever inserted. The SDK actions are fire-and-forget with no acknowledgement (verified in the SDK source in #1/#2), so "inserted" is shown optimistically and verified only in EW manually. [VERIFIED: https://www.aem.live/docs/ew/developing/apps-plugins lists `sendText`, `sendHTML`, `closeLibrary` for plugins, re-read 2026-11-18; the host parses the HTML and inserts at the selection, per https://github.com/adobe/da-live/blob/main/blocks/canvas/ew-panel-extensions/iframe-protocol.js as read in #1/#2.] The detail preview shows the selected rendition URL, so the author sees exactly what will be inserted and the CDN is warmed. Default registration recommendation is `experience = fullsize-dialog` (a large grid and detail pane need room); the narrow inline layout (single-column responsive grid) must also work and is the documented fallback. [VERIFIED in source 2026-11-18: `extensionToPanelView` in https://github.com/adobe/da-live/blob/main/blocks/canvas/ew-panel-extensions/helpers.js gives `fullsize-dialog` views a `loadModal` that renders the plugin in an iframe with `allow = 'clipboard-write *'`; the public library docs list an `experience` column but no values [VERIFIED 2026-11-18: https://www.aem.live/docs/ew/administering/set-up-library], so the value is source-only knowledge, Question 4.]

**D19. Browser to worker authentication, origin and failure handling.** Every worker call carries `Authorization: Bearer <IMS token from the SDK>` (the #2 contract). The worker origin is a **constant keyed by the page's own hostname**, never taken from the URL (#2 Decision 15; a test proves a `?worker=` parameter is ignored): `main--ew-extensions--jazhou-adobe.{aem.live,aem.page,preview.da.live}` -> the Production worker; any other `*--ew-extensions--jazhou-adobe.*` host and `localhost` -> the Stage worker; any other host (including the sibling demo site `*--ew-extensions-demo--jazhou-adobe.*`) -> no worker calls, the UI says "not available here". The base URLs have the form `https://<namespace>.adobeioruntime.net/api/v1/web/multi-dam-picker/api` (#2 Decision 15); the namespaces are known only after the first deploy [OPEN, owned by #2]. Because the platform's own failures (rate limit, oversize, crash, timeout) carry no CORS headers, the page sees a rejected `fetch`; the browser treats a rejected fetch as "service unavailable, try again" and every call has a bounded wait (about 20 s [ASSUMPTION: value], under the action's 25 s limit) with a visible "working" state, because a cold start adds latency (#2 R12).

**D20. Worker API surface in this ticket (small, provider-namespaced).** `GET /dam/providers` (configured providers with credential kind, connection state, account label, capabilities), `GET /dam/{provider}/assets?q&type&sort&page&pageSize` (search), `GET /dam/{provider}/assets/{id}` (detail). Errors reuse the #2 contract with no extension-defined codes (an unknown or unconfigured provider is `404 not_found`). **D22. ## Testing Decisions

**What makes a good test here.** Assert external behaviour only: given a web-action invocation (raw `params` with headers, path, query; inputs from the kit's `makeInputs`; fake IMS and a fake Cloudinary) assert the returned `{ statusCode, headers, body }`, the requests the fake Cloudinary received (method, path, JSON body, headers), the store writes and what was logged; given normalised data and an SDK result, assert what the DOM shows and which SDK actions fire. Never assert on internal helper names or call counts of internal functions. Properties asserted as negatives across every path: **no Cloudinary key, secret, Basic value or signature material ever reaches a response, log line or the browser**, **nothing runs before authentication succeeds**, and **no user-supplied byte can alter the structure of the Cloudinary search expression or the upstream path**.

## Further Notes

- **Docs say nothing about third-party pickers or backends in EW.** The cited EW developer doc (https://www.aem.live/docs/ew/developing/apps-plugins) documents the SDK, `sendText`, `sendHTML`, `closeLibrary` and the config rows; nothing on backends, OAuth or DAMs [VERIFIED 2026-11-18 by re-reading the page]. All EW-side design derives from the SDK and library source.
- **Library rows resolve against the editor's site, not the code site (important for the demo-site setup).** [VERIFIED in source 2026-11-18: `calculateSources` in da-live `helpers.js`] a `path` starting with `/` becomes `http://localhost:3000{path}` on `ref=local`, else `https://{branch}--{site}--{org}.aem.live{path}`, where `site` and `org` are the *editor's* site, i.e. `ew-extensions-demo`; so a relative `path` would load the demo site, not the code site. Rows therefore use absolute code-site URLs (absolute values are used as given). Consequences, all from `fetchExtensions`/`getIsPluginAllowed` in the same file: a row's `ref` filters (blank or `main` always shows; another value shows when it equals the editor's `?ref=` or the editor is on `ref=local`); rows with the same title are de-duplicated and **the first allowed row in sheet order wins**, so the `ref=local` row and any branch row go *above* the `main` row and share its title; `ref=local` is not rewritten for absolute URLs, hence the explicit `http://localhost:3000/...` row. The editor reads `ref` from the page's query string (`window.location.search`), so `?ref=local` goes before the `#`. Both the rows and the order are verified end to end in M2/M4.
- **The iframe origin is probably a preview proxy host.** [VERIFIED in source 2026-11-18: `extensionToPanelView` passes `{ getUrl: getPreviewOrigin, currentOrg: ext.org }`; in `preview-proxy.js` an `*.aem.live`/`*.aem.page` URL of the same org as the editor is rewritten to the preview-proxy URL, and URLs of another org are left unchanged.] The code site and the demo site share the org `jazhou-adobe`, so the extension page's real `Origin` is expected to be `https://{ref}--ew-extensions--jazhou-adobe.preview.da.live` (or the `.aem.page`/`.aem.live` fallback; the docs say apps load from `aem.page` [VERIFIED 2026-11-18]); the #2 allowlist covers all three. `localhost:3000` rows are not rewritten. Observed for real in M4 (#2 R2).
- **Why Cloudinary goes first.** Its Free plan is self-serve ("Free forever", "No credit card required", 3 users, 25 monthly credits [VERIFIED 2026-11-16: https://cloudinary.com/pricing]) and includes "Upload widget, API, and search". The OAuth DAMs need either an enabled portal (Bynder: Customer Support must enable OAuth Apps) or a developer app review path. Cloudinary also needs no token store, so the shell can be built and proven before the harder plumbing.
- **What differs between credential kinds, in one table.**

  | Concern | `service` (Cloudinary, this ticket) | `user-oauth` (Dropbox #25, then Bynder #22, Frontify #24) |
  |---|---|---|
  | Who authenticates | the worker, with one key/secret for everyone | each author, via an OAuth pop-up |
  | Who sees what | everyone sees the same assets, scoped by root folder and `upload` type | each author's own DAM permissions |
  | Sign-in UI | none; grid loads at once | connect/disconnect panel (#25) |
  | Stored by the worker | nothing (encrypted action inputs only; cache entries in State) | encrypted per-user tokens (#25; #2 keeps long-lived credentials out of State until a vault decision) |
  | Result cache | shared across authors | per-user scope, defined by #25 |
  | Failure classes | misconfigured on `401`/`403` | reauth required, not connected (reserved) |

- **Free-plan transformation credits.** A new derived asset (a new transformation URL) counts one transformation the first time it is generated; repeated requests to the identical URL are not counted again [VERIFIED 2026-11-16: https://cloudinary.com/documentation/transformation_counts.md]. One credit equals 1,000 transformations [VERIFIED 2026-11-16: pricing page], so the Free plan's 25 monthly credits cover about 25,000 new derived assets. Every previewed thumbnail and every inserted rendition is one such asset on first view; the design keeps one thumbnail size and a short fixed rendition list so browsing does not explode the count, and the README says so.
- **Search latency and consistency.** Search is eventually consistent (seconds): a just-uploaded asset may be missing briefly; detail by `asset_id` is immediate. The type clauses use negation for the image and video filters, and Cloudinary warns that `NOT`/`-` "can lead to significant latency on large repositories" [VERIFIED 2026-11-16: search_expressions.md]; large environments are timed against the test environment (R8).
- **Embedded-URL longevity.** Inserted URLs reference Cloudinary: deleting an asset breaks the page; renaming or moving does not change the public ID or delivery URL in dynamic folder mode but does in fixed mode [VERIFIED 2026-11-16: folder_modes.md]. - **EDS and external images.** Whether Edge Delivery Services keeps an external `<img src>` from a DA document untouched on publish is [ASSUMPTION it is kept]; checked in manual step M5 on the demo site.
- **State is an optimisation here, not a dependency.** If State is unreachable (or `aio app dev` is used, where State does not work [VERIFIED in #2]) the worker still serves every request; only caching and the early stop degrade.
- **Template and scaffold state (observed 2026-11-18).** `shared/worker-template/` holds only its spec (TG1, TG3, TG4 above are additions to a template not yet built) and `apps/hello-world/` has its implemented #1 scaffold without a worker. ## 3. External APIs and auth flows

All Cloudinary calls go to `https://{api-host}/v1_1/{cloud_name}/...`, `api-host` default `api.cloudinary.com`, with HTTP Basic (API key as user, API secret as password) [VERIFIED 2026-11-18: https://cloudinary.com/documentation/admin_api_overview.md].

| API | Use | Auth | Source / status |
|---|---|---|---|
| `resources/search` (JSON body: `expression`, `sort_by`, `max_results` <= 500, `fields`; `next_cursor` unused) | browse and search | Basic | [VERIFIED 2026-11-18 params and JSON-body examples] https://cloudinary.com/documentation/admin_api_resources_search_for_resources.md; POST vs GET [ASSUMPTION, M1] |
| `GET resources/{asset_id}` | asset detail: `context`, structured `metadata`, URLs | Basic | [VERIFIED 2026-11-16 endpoint] https://cloudinary.com/documentation/admin_api_resources_get_details_of_a_single_resource_by_asset_id.md; response shape from the by-public-ID sample [ASSUMPTION identical] |
| `GET config?settings=true` | folder mode (dynamic/fixed) | Basic | [VERIFIED 2026-11-16] https://cloudinary.com/documentation/admin_api_config.md; used by hand during setup (README, M1), not at runtime |
| `GET ping` | reachability (used by #2's live check CL1) | Basic | `{"status":"ok"}` [VERIFIED in #2, 2026-11-18: https://cloudinary.com/documentation/admin_api_ping.md]; whether it counts toward the quota is [OPEN, observed in M1] |
| CDN delivery (`res.cloudinary.com` or a private CDN) | rendition and thumbnail display by browsers | none, or a signature in the URL | [VERIFIED 2026-11-16 structure; anonymous fetch of `yifoe45l` samples observed 2026-11-18] https://cloudinary.com/documentation/image_transformations.md; signature https://cloudinary.com/documentation/delivery_url_signatures.md |

Limits [VERIFIED 2026-11-18: admin_api_overview.md]: Free plan 500 Admin API requests per hour, paid plans from 2,000; each request counts one; the Upload API is not rate-limited (not used); headers `X-FeatureRateLimit-Limit`, `-Remaining`, `-Reset` on every Admin API response; status `420` = rate limited. Search is Tier 1 by default; `metadata` in search results is Tier 2 only. State and Runtime limits as in D17 and #2.

**Auth flow (author to worker):** SDK token -> `Authorization: Bearer` -> the #2 pipeline (origin gate, token verification) -> `identity.userId` (used for logging and the optional `authorize` hook only; not for the Cloudinary call).
**Auth flow (worker to Cloudinary, per call):** secret accessor -> Basic credential applied by the proxy helper (TG1; composed value registered for redaction) -> proxy to the pinned API host -> parse only if JSON -> normalise -> output URL policy -> respond. No token exchange, refresh, cookie or per-user storage; State holds only cache entries and the rate-limit record.
**Signing flow (rendition URLs):** API-returned `secure_url` -> locate the delivery-type segment -> choose the transformation -> if signing is on: digest(`<transformation>/<public_id>[.<ext>]` + secret) -> first 8 URL-safe base64 characters -> insert `s--sig--` and the transformation, drop the version -> https and delivery-host check -> include in the normalised asset.

## 4. Data contracts

Behaviour contracts, not code.

**Worker API (all `Authorization: Bearer <IMS>`; JSON; CORS and errors per #2; base `https://<namespace>.adobeioruntime.net/api/v1/web/multi-dam-picker/api`):**

| Method + path | Purpose | Success | Notable errors |
|---|---|---|---|
| `GET /dam/providers` | configured providers with credential kind, connection state, capabilities | `200 { providers: [{ id, label, credentialKind, connection: { state, account? }, capabilities }] }` (Cloudinary: `connected`, account label = cloud name) | |
| `GET /dam/{provider}/assets?q&type&sort&page&pageSize` | search | `200 { items, page, pageSize, total?, hasMore }` | `400 bad_request`, `404 not_found` (unknown or unconfigured provider), `429 rate_limited` (+ `Retry-After`), `500 misconfigured`, `502 upstream_unavailable` |
| `GET /dam/{provider}/assets/{id}` | detail with renditions and alt candidate | `200 { asset }` | as above plus `404 not_found` |
| (reserved, not routed) `POST /dam/{provider}/connect`, `GET .../session`, `POST .../disconnect`, `GET /oauth/{provider}/begin`, `GET /oauth/{provider}/callback` | #25 | none in this ticket | `401` without a token, `404` with one |

All other paths: no token `401`; token and unknown path `404 not_found`; wrong method `405 method_not_allowed` (#2 UA12). Responses carry `Cache-Control: no-store`, `x-request-id`, and for allowed origins the CORS headers including `Retry-After` and `x-request-id` in `Access-Control-Expose-Headers` (#2 UC9). The browser reads `Retry-After` from `429` responses only because of that header.

**Provider capabilities (Cloudinary):** `assetTypes = [image, video, document, audio]`; `sorts = newest (default), oldest, name, relevance (requires a query)`; `window = 500`; `assetIdPattern = 32 lowercase hex`; `outboundHosts = [api host]`; `deliveryHosts = res.cloudinary.com + configured hosts`; `cacheSeconds = 30`.

**Query rules (shell, all providers):** `q` <= 200 characters; `type` in the provider's `assetTypes` or `all`; `sort` in the provider's `sorts` (a sort that requires a query without one is `400`); `page` >= 1; `pageSize` 1-50 (default 24); `page x pageSize` beyond the provider's window is `400`; any rejection makes zero upstream calls.

**Upstream request (Cloudinary search):** `{ expression, sort_by?, max_results, fields }`, `Content-Type: application/json`, Basic credential; no other header forwarded (the proxy strips inbound `Authorization`, `Cookie`, `Host`, forwarding headers, #2 Decision 11). **Expression grammar produced** (illustrative strings): `type=upload`; with a root: `AND (asset_folder=samples OR asset_folder:samples/*)`; type image: `AND resource_type=image AND NOT format=pdf`; keyword: `AND ("word1" AND "word2")`. **Proxy options per call:** `allowedHosts = [api host]`, `auth = Basic (key, secret)`, `retry.idempotent = true` for search and detail (read-only), `rateLimitStatuses = [420]` (no retry), default backoff and deadline of #2.

**Rendition table (defaults, overridable by `CLOUDINARY_RENDITIONS`):**

| id | label | transformation | applies to |
|---|---|---|---|
| `web` (default) | Web, up to 1200 px | `c_limit,w_1200/f_auto/q_auto` | images |
| `large` | Large, up to 2000 px | `c_limit,w_2000/f_auto/q_auto` | images |
| `medium` | Medium, up to 800 px | `c_limit,w_800/f_auto/q_auto` | images |
| `small` | Small, up to 400 px | `c_limit,w_400/f_auto/q_auto` | images |
| `original` | Original file | none (the returned `secure_url`) | browser-displayable image formats only |

The strings use the documented `limit` crop, width and automatic format/quality parameters; whether a single component (`c_limit,w_1200,f_auto,q_auto`) or chained components is preferable matters only for allow-listing on strict accounts that do not sign, and is settled in M6 [OPEN: Question 7].

**Store contract use (#2 Decision 10; keys are prefixed per worker by the store):** `cache.<providerId>.<sha256 hex>` (compact normalised response, at most 64 KB, TTL = `CLOUDINARY_CACHE_SECONDS`), `ratelimit.<providerId>` (`{remaining, resetAt}`, TTL until reset, at most one hour). Keys use only alphanumeric, `-`, `_`, `.`; values are JSON strings; failures never fail a request.

**Normalised asset, capabilities, errors:** as D13, D3 and D16. The error shape is the #2 contract `{ error: { code, message, requestId } }`; messages are fixed strings.
