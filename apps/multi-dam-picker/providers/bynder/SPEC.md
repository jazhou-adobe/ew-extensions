## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party) and, after #23 and #25, from Cloudinary and Dropbox. Many brands keep their governed brand assets in **Bynder**. Today an author who wants a Bynder image leaves EW, finds the asset in the portal, works out which public URL is safe to use (a private or expiring link, an oversized original, a limited-use asset), copies it, pastes it and retypes alt text from the asset's description. Nobody checks that the URL works for a visitor or that the alt text exists.

Bynder is a **per-user OAuth DAM**: what an author may see depends on their own Bynder permissions (brand, category and metaproperty access), and Bynder says a token never exceeds what its user could already do [VERIFIED: https://developers.bynder.com/integrate, "We only grant scopes that match the user's underlying permissions"]. A shared service account would flatten every EW author into one identity, so the picker needs each author to connect their own Bynder account. That machinery (connect and disconnect from the library iframe, a public callback made safe without an `Authorization` header, an encrypted server-side token store, silent refresh) is exactly what #25 builds once, provider-agnostically, on App Builder. This ticket must **use** it, not rebuild it.

Bynder differs from Dropbox in ways that decide the provider half:

1. **Per-portal hosts.** Every Bynder call, including the OAuth authorize and token endpoints, goes to the customer's own portal host, so the hosts the shell pins (authorize, outbound, delivery) are a function of configuration, not constants [VERIFIED: the token reference says the endpoint is `https://example.com/v6/authentication/oauth2/token` with the placeholder replaced; Getting started shows `https://{portal-domain}.bynder.com/v6/...`].
2. **Rendition URLs exist, and they are opaque.** Unlike Dropbox, Bynder's API returns ready-made public URLs (`thumbnails.mini|thul|webimage`, an `original` for public assets, public custom derivatives in `mediaItems`), and Bynder is migrating its public link format (`/m/...` to `/asset/...`) and says integrations that consume URLs as returned need no change [VERIFIED*: public assets article]. The module must never build or parse them.
3. **Real DAM metadata.** Bynder has `name`, `description`, `copyright`, `tags` and site-defined metaproperties (`property_<name>`), so alt text can come from real metadata, but there is no dedicated alt-text field, so the metaproperty must be configurable [VERIFIED: the list schema has no alt field].
4. **Refresh tokens that probably rotate and cannot be revoked per token.** The refresh response schema returns a `refresh_token` whose example differs from the one sent [VERIFIED: refresh reference, request example `c11e...b5bc`, response example `c12e...b5dc`; weak evidence], the authorize redirect uses a `login_challenge` (the Ory Hydra login-provider vocabulary, [ASSUMPTION] Bynder uses it) and Hydra's refresh tokens are single-use [VERIFIED*: snippet of https://www.ory.com/docs/hydra/debug]. Access tokens last about an hour (schema example `expires_in: 3600`), so a rotating refresh happens **every hour of use**, far more often than Dropbox's four-hour non-rotating one. Bynder publishes no per-token revoke endpoint; a portal admin can revoke all refresh tokens of an OAuth app [VERIFIED*: support article]. These facts stress the parts of #25's plumbing that Dropbox does not (the State lock, rotation races, retry safety, "Disconnect").
5. **A portal that has to be enabled by a vendor.** OAuth Apps must be enabled by Bynder Customer Support, the registering admin needs "Manage portal settings" and "Manage OAuth apps", the client secret is shown once, and an OAuth app's scopes cannot be edited later (a new app is needed) [VERIFIED*: support article]. No self-serve sandbox was found. This is why Bynder comes after Dropbox, and why real verification is an owner prerequisite.

## Solution

**Bynder** appears in the existing Multi-DAM Picker as a source next to Cloudinary and Dropbox when its worker configuration is present. An author chooses *Bynder*, sees the shell's **Connect to Bynder** panel (built in #25), signs in to the portal in a pop-up with their own Bynder account (including company SSO) and consents to read access. The panel then shows "Connected as <name>" with **Disconnect** and the author's own view of the asset bank: the most recently modified assets first, a thumbnail grid with names, keyword search (debounced), a type filter (images, videos, documents, audio), sorting (recently modified, recently created, name) and "Load more". Opening an asset shows a larger preview, name, dimensions, type, size and any limited-use, archived or watermarked warning. The author picks a **rendition** (default Bynder's `webimage`; the other standard derivatives, the portal's public custom derivatives and, when Bynder returns it, the public original), reviews alt text prefilled from a configurable Bynder metaproperty (else the asset description, else a cleaned-up name; editable, or marked decorative) and inserts it at the cursor as an `<img>` with the exact URL Bynder returned. Videos, documents and audio with a public URL are inserted as a link.

Behind it nothing new is built on the security side. The Bynder **provider module** supplies pure HTTP mappings to #25's `user-oauth` interface: the authorize URL on the portal host, the code exchange and refresh calls (form-encoded, client credentials in the body), the current-user lookup for the account label, the failure classification, and the browse mappings (`/api/v4/media/` with `keyword`, `type`, `orderBy`, `page`, `limit`). The plumbing owns state sealing, the binding cookie, token encryption and storage in State, refresh orchestration (including single-use rotation and the lock), credential injection and per-user caching. The Bynder client secret exists only as an encrypted action input fed from the untracked `.env`; every Bynder token exists only in the worker and in encrypted State records; the browser holds only its own IMS token and normalised asset data.

The ticket's acceptance criterion "no changes needed in the shell beyond registering the provider" is made **machine-checkable**: the diff that adds Bynder touches only the provider's own folder, one registry line, the worker's app-config inputs, `.env.example`, the README section and the conformance registration, and repo checks prove nothing else mentions the vendor and that the provider folder contains no token-storage, State, encryption or cookie code.

## Implementation Decisions

(No file paths or code, except endpoint names, parameter names and wire contracts, which are API contracts. Layout is in the Build Analysis. Template contracts are "#2 Decision N", shell decisions "#23 DN", plumbing decisions "#25 DN".)

**D1. Scope: one provider module on #25's plumbing; no shell change.** The ticket delivers the Bynder module (its mappings, fixtures, tests and README section) and exactly four touch points outside its folder: the registry entry, the worker's app-config inputs, `.env.example` and the extension README (plus the one conformance-suite registration line). The shell, the OAuth plumbing, the `oauth` action, the browser code and the template are not changed. If #25's plumbing needs a change for Bynder, it is made **in #25** (amendments A1 to A7, section 9); this ticket carries no shell work. The module is a `user-oauth` provider in the sense of #23 D3 and #25 D5.

**D2. Surface and registration unchanged.** Library plugin only; the one `library` row from #23 is unchanged; **no new config-sheet row and no new entry page; site config read: none** (the README states it). Bynder appears in the panel when its inputs are present and the OAuth plumbing is enabled (#25 D4: `TOKEN_ENC_KEY`, `OAUTH_STATE_KEY` and `OAUTH_PUBLIC_BASE_URL` non-empty); a Bynder-configured deployment without the plumbing fails the registry build naming the missing items and the pre-deploy guard refuses the deploy (#25 D4, CN6).

**D3. Build our own UI on the HTTP API; do not embed Bynder's Universal Compact View (UCV).** UCV is Bynder's ready-made picker but it authenticates in the browser ("Pass an existing access token to skip the login screen entirely"; it works with every portal login method [VERIFIED*: https://developers.bynder.com/universal-compact-view]); that contradicts the criterion that tokens are stored and refreshed server-side and never reach the browser, and it is single-vendor, which cannot be the capability-driven shell. Contentful's Bynder app uses UCV (https://github.com/contentful/marketplace-partner-apps/tree/main/apps/bynder [VERIFIED*]) and is prior art for insertion semantics (default `webimage`) only. The decision mirrors #23 D2 and #25 D3.

**D4. Provider identity, kind and config-derived hosts.** `id` = `bynder`, `label` = `Bynder`, `credentialKind` = `user-oauth`. The provider is *configured* when `BYNDER_PORTAL_DOMAIN`, `BYNDER_CLIENT_ID` and `BYNDER_CLIENT_SECRET` are all non-empty (#23 D5, #25 D16; an empty input means "absent", #25 D4). **The portal host drives three of the interface's host lists**, all derived from the one validated setting: `authorizeHosts` = the portal host, `outboundHosts` = the portal host (the authorize redirect, the token endpoint and the API are all on it [VERIFIED: the authorize reference redirects to `https://your-bynder-domain/v6/login-provider/login...`; the token reference; the media and current-user references list `https://{your-bynder-domain}/`]), `deliveryHosts` = the portal host plus the administrator's optional list (D9). `BYNDER_PORTAL_DOMAIN` is a bare DNS host name: no scheme, path, port, userinfo or IP literal, lower-cased, validated at registration naming the setting and never echoing its value. [Needs amendment A1 to be confirmed in #25: `authorizeHosts` and `scopes` may be functions of validated configuration, as `deliveryHosts` and Cloudinary's `outboundHosts` already are; #25's stub with a per-tenant host (PO4) already exercises it.] There is no test-only origin input: tests make the portal host resolve to a fake through the test kit's injected `fetch` and Playwright routing, so no production code path honours a test origin (#25 D16).

**D5. Per-user OAuth: authorization code with the `offline` scope, confidential client, executed by the plumbing; Bynder supplies the mappings.** Client credentials (a service account) are rejected for the reason in the Problem Statement [VERIFIED*: the OAuth app article says client-credentials tokens "will still be linked to the configured assigned user"]. Both token calls go through the **pinned proxy helper** with the provider's own retry options (D7; #25 D22 makes the same per-call declaration for Dropbox [ASSUMPTION: confirmed as clarification A2]). **D6. Failure classification of the OAuth calls (the vocabulary #25 D5 defines).** Classification is by documented HTTP status and by the JSON `error` string only; a non-JSON body (Bynder is not documented to return HTML, but proxies do) is never parsed and is *misconfigured*. Bynder's token-error body shape is **not documented** [OPEN: recorded in MB3 and MB4 with a real revoked grant]; the provisional table assumes RFC 6749 error codes, which an Ory Hydra-style flow would use [ASSUMPTION]. Dropbox returns `error` as one "code: description" string (#25 O2), so the classifier matches on the **prefix** before any colon and tolerates both an object and a string form:

| Token endpoint outcome | Class |
|---|---|
| `invalid_grant` (revoked, expired or already-used code or refresh token) | **reauth** |
| `invalid_client`, `unauthorized_client`, `invalid_scope`, `invalid_request`, `redirect_uri` mismatch, any `401` | **misconfigured** |
| `5xx`, timeout, network failure | **transient** |
| anything unclassifiable (unknown JSON, empty body, other `4xx`) | **misconfigured**, never reauth (#25 D5: a vocabulary surprise must never delete a working connection) |

The honest cost of that safety rule is that a real revoked-grant response in an unexpected shape would show "ask your administrator" instead of "Reconnect" until the table is corrected from MB4 (risk R10); amendment A4 keeps "Disconnect" reachable in that state so an author is never stuck.

**D7. Refresh of a single-use rotating token: no retry, never unlocked, and the plumbing handles the rest.** Bynder's refresh probably rotates the refresh token (D5 evidence). A refresh that times out after Bynder has already rotated would be burned by a blind retry, so the module **declares neither of its token calls safe to retry**: `exchangeCode` and `refresh` are POSTs, which the template retries only on `429` unless the caller opts in (#2 Decision 11), and the module opts in to nothing and sets the retry count to zero. A transient refresh failure therefore answers `502 upstream_unavailable` with the record kept; if the lost response had in fact rotated the token, the next attempt gets `invalid_grant` and the author reconnects (documented residual risk R2, the same one #25 D9 steps 6 and 7 and RF9, RF10 and RF12 prove ends cleanly). Everything else is #25's and is **not Bynder code**: the proactive refresh 60 s before expiry; in-container single flight; the cross-container lock (`lock.v1.<hash>`, `putIfAbsent`, TTL about 20 s) with a re-read after acquiring it; the wait-and-poll of up to about 5 s when the lock is held; the refusal to refresh unlocked for a provider that rotates; the conditional write (`putIfPresent`) that never resurrects a disconnected record; the re-read before a definitive failure destroys tokens; the one write retry and in-container keep after a rotating refresh. **Why this matters more here than for Dropbox:** at hourly expiry every active author triggers a rotating refresh each hour, so races between two Runtime containers, two browser tabs and a killed action are routine rather than rare; State's cross-container read-your-writes, minimum TTL and conditional-write behaviour are not fully documented (#25 R27, spike S-OA), so MB4 includes a **parallel-refresh drill** on the real platform. The first real-vendor evidence that the lock works with a rotating provider will come from this ticket or #24, whichever runs first (the rotating-provider gate, #25 Question 3).

**D8. No token-storage code in this ticket (AC3).** The module never reads or writes State or any other storage, never uses the store interface, never encrypts or seals, never sets or reads cookies, never refreshes on its own (it reports *reauth required* from a browse call and the shell forces one refresh and one retry, #25 D5, D9) and never sees the IMS token, the inbound `Authorization` or cookies (#25 PO7). It applies the author's access token as `Authorization: Bearer` to its own outbound calls through the pinned proxy helper, and the client secret only through the secret accessor in the token calls. Repo check BYN-RC3 makes this a CI failure rather than a review comment.

**D9. Configuration (provider config on top of #25's shared items).** Shared items from #25 are reused unchanged and add nothing here: inputs `OAUTH_PUBLIC_BASE_URL`, `CONNECTION_TTL_DAYS`, `STATE_REGION`, secrets `TOKEN_ENC_KEY`, `TOKEN_ENC_KEY_PREVIOUS`, `OAUTH_STATE_KEY`, and the template's `ORG`, `SITE`, `IMS_ORIGIN`, `ALLOWED_LOCAL_ORIGINS`, `AUTH_MODE`, `ALLOWED_IMS_CLIENT_IDS`. Bynder's own items, in the committed app config as `$NAME` references fed from the untracked `.env` where they differ per environment, and as literals where a reviewable default is better (the split mirrors #23 D21):

- **Environment-specific, from `.env`, optional marker so a deployment without Bynder still deploys** (the #2 guard otherwise fails on an empty `$NAME`; #23 TG2): `BYNDER_PORTAL_DOMAIN` (required for the provider), `BYNDER_CLIENT_ID` (required for the provider; public by nature, it is in the authorize URL) and the **secret** `BYNDER_CLIENT_SECRET` (required for the provider).
- **Literal inputs with reviewable defaults:** `BYNDER_SCOPES` (default D5; must contain `offline`, `asset:read` and `current.user:read` or registration fails naming the setting), `BYNDER_ALT_PROPERTY` (empty; the metaproperty system name, validated as letters, digits and underscore), `BYNDER_DEFAULT_DERIVATIVE` (`webimage`), `BYNDER_DELIVERY_HOSTS` (empty; comma list of bare host names), `BYNDER_PUBLIC_ONLY` (`false`; boolean-looking inputs may arrive as strings or booleans [ASSUMPTION: parse both; tested]), `BYNDER_CACHE_SECONDS` (`30`, `0` disables).

Invalid *present* values fail registration naming the setting and never its value (#23 D3, D5). **OAuth scopes are frozen at app creation in Bynder** [VERIFIED*: "All OAuth App specifications can be changed except the OAuth scopes"], so changing `BYNDER_SCOPES` requires a new OAuth app and new connections; the README says so (D19).

**D10. Browse mapping: `GET /api/v4/media/` (the AC1 filter logic).** Parameters sent, all from the documented list [VERIFIED: https://api.bynder.com/reference/get_api-v4-media]: `keyword` (only when the author typed one; the reference says it searches file names, tags, extensions, collection names and more), `type` (one of `image`, `video`, `audio`, `document`; omitted for "all", so `3d` assets appear only there), `orderBy` (from the closed enum, D11), `limit` (the shell page size, 24 default, 50 cap; Bynder allows up to 1000, default 50) and `page` (1-based), `total=1`, and `isPublic=true` only when `BYNDER_PUBLIC_ONLY` is on. User text travels only as the `keyword` value through URL-parameter encoding; Bynder documents no query language for `keyword`, so the injection boundary is parameter encoding alone [ASSUMPTION no special syntax; probed in MB3]. `includeMediaItems` is **not** sent on search (summaries need only `thumbnails`). The author's token is the only credential. The list reference has no `fields` parameter, so each result carries every asset field; the page-size cap bounds the payload against the template's upstream-body cap and the 1 MB Runtime result limit (D20, risk R15).

**D11. Sorts, types, window and paging.** Declared capabilities: `assetTypes` image, video, document, audio; `sorts` **`modified`** (default; `dateModified desc`), **`created`** (`dateCreated desc`) and **`name`** (`name asc`), all from the documented `orderBy` enum [VERIFIED]; **no `relevance` sort** (the enum has no score; the order of keyword results is unspecified [OPEN: MB3]); `window` **100,000** (`page` times `limit` must not exceed it, otherwise Bynder answers `400 RESULT_WINDOW_TOO_LARGE` [VERIFIED]; the shell never asks beyond it, so Bynder's cursor paging is not used); `assetIdPattern` the **8-4-4-16** hexadecimal form of `/api/v4` identifiers, case-insensitive (the 8-4-4-4-12 form belongs to other endpoints and is rejected before any call) [VERIFIED: https://developers.bynder.com/integrate]; `outboundHosts`, `authorizeHosts`, `deliveryHosts` per D4; `cacheSeconds` default 30. `hasMore` comes from the response total when present; the documented success schema of the list is a bare array and the shape produced by `total=1` is **not documented** [OPEN: MB3], so the mapper accepts both a bare array and an object carrying the assets and a total, and falls back to "the page was full" when no total is present (the cost is at most one empty last page, which the shell already tolerates).

**D12. Asset identity, detail and the fixed call budget.** The shell id is Bynder's `id` exactly as returned. Detail is `GET /api/v4/media/` with `id=<id>` and `includeMediaItems=1`: both parameters are on the list reference [VERIFIED], and `mediaItems` (public custom derivatives with `publicUrl`) exists only on the list schema, not on the single-asset schema [VERIFIED 2026-11-18: https://api.bynder.com/reference/get_api-v4-media-id contains no `mediaItems`]. An empty result is `404 not_found`. That the combination returns populated `mediaItems` is [ASSUMPTION; MB3]; the fallback is `GET /api/v4/media/{id}/` with `versions=1`. The module **never** calls the download endpoint (its URL is temporary and needs a high-resolution role [VERIFIED*: https://api.bynder.com/reference/get_api-v4-media-id-download]), the derivatives endpoint, or any write endpoint (BYN-RD1). Detail has no side effect (unlike Dropbox's link creation, #25 D21). Per `api` request the worker makes at most one Bynder call plus, rarely, one refresh, and the plumbing's State operations (one record read, at most one write, the lock pair only when refreshing).

**D13. Normalised asset mapping (the AC1 insertion contract).** Summary: `id`; `provider` `bynder`; `name`; `type` from Bynder's `type` (`image`, `video`, `audio`, `document`; `3d` becomes `other`); `extension` the first entry of the `extension` array; `fileSize`; `width`, `height`; `dateModified`; `warnings[]` from `limited`, `archive`, `watermarked` (`limited-use`, `archived`, `watermarked`); `thumbnailUrl` the first of `thumbnails.thul`, `thumbnails.webimage`, `thumbnails.mini` that passes the shell's output URL policy (https and a delivery host), else absent (the browser shows a file-type placeholder). Thumbnails are public URLs, so **no inline `data:` thumbnail is needed** (unlike Dropbox) [VERIFIED*: "Thumbnails are public by default"; ASSUMPTION they load without a session for non-public assets, MB5]. Detail adds `description`, `tags[]`, `copyright`, `alt` (D15), `renditions[]`, `defaultRenditionId`, `insertable`, `linkUrl`. Only allow-listed fields are mapped; Bynder fields such as `userCreated`, `property_*` values (other than the alt property), `propertyOptions`, `videoPreviewURLs`, `idHash`, `transformBaseUrl` never cross the boundary.

**D14. Renditions: opaque, API-returned, public-only.** Candidates, in order: (1) the standard derivatives from `thumbnails`, ids `webimage`, `thul`, `mini`, labelled by name; (2) for images, each `mediaItems` entry that has a `publicUrl`, id `custom:<name>`, labelled by name, `kind: derivative`; (3) `original` only when Bynder returns it (carried from the public-assets article: `original` is returned only for assets marked public and only when the portal has the SEO base URL set [ASSUMPTION; not found on today's reference pages, MB3]) and its extension is browser-displayable (jpg, jpeg, png, gif, webp, avif, svg), `kind: original`. The default is `BYNDER_DEFAULT_DERIVATIVE` when that rendition exists, else `webimage`, else the first available. Every URL is passed through byte-for-byte; the module **never constructs, rewrites or parses** a Bynder URL (the `/m/` to `/asset/` migration is Bynder's, and "if your integrations consume URLs as-is, no action is required" [VERIFIED*: public assets article]); it never appends `?format=` even though API thumbnails carry no file extension [VERIFIED*: same article, FAQ], because that would be URL construction (MB5 records the delivered content type). Each URL must pass the shell's output policy (https, host in `deliveryHosts`); a failing rendition is dropped; an image with none left is `insertable.ok=false` with the fixed reason "No public rendition is available for this asset". Dimensions: only the asset's own width and height, attached to `original`; derivative dimensions are not reported by the documented API [ASSUMPTION; MB3] and are omitted. Non-image assets: `linkUrl` is the returned `original` when present, `renditions` is empty; with no public original the asset is not insertable ("This asset has no public link"). Dynamic asset transformations (`transformBaseUrl`) are out of scope.

**D15. Alt text policy (AC1 "alt text from DAM metadata").** A ranked fallback returned with its source, mapped to the shell enum: (1) `property`: the value of `property_<BYNDER_ALT_PROPERTY>` when configured (a string, or an array of strings, whichever Bynder returns; the first non-empty entry is used; the schema shows `property_*` as an array of option names for option-type metaproperties [VERIFIED: get_api-v4-media-id, `property_assettype`] and as a plain string for `property_limitedrights` [VERIFIED 2026-11-18: list schema]; the free-text shape is [ASSUMPTION; MB3]); (2) `description`: the asset `description`; (3) `name`: the asset name without extension, separators turned into spaces; (4) `none`. Every candidate is reduced to plain text (no markup, entities, control characters; whitespace collapsed). The author always sees and may edit it or mark the image decorative. Whether the `asset:read` scope suffices to read `property_*` values, or whether `meta.assetbank:read` is also required, is [OPEN: MB3]; because scopes cannot be edited later (D9) this must be settled before the real OAuth app is created.

**D16. Errors and limits (all mapped to the #2 error contract; fixed messages; no upstream text).** Browse and detail calls: `401` is reported as **reauth required** (the shell then forces one refresh and retries once, #25 D5, D9); `403` forbidden (the author's Bynder role lacks access); `404` on detail not found; `400` bad request (the provider validates the window and the id before calling, so this is rare, including `RESULT_WINDOW_TOO_LARGE`); `429` rate limited with a retry delay (Bynder allows 4,500 requests per five minutes per source IP and pauses that IP for five minutes [VERIFIED: https://developers.bynder.com/integrate]; the module uses `Retry-After` when present, else 300 s, clamped by the shell; whether Bynder sends the header is [OPEN: MB3]); `5xx` and network failures upstream unavailable. **Runtime's outbound calls leave from published IP ranges that every action in Runtime shares** (the documentation tells you to allow-list *ranges*, retrievable with `aio runtime ip-list get` [VERIFIED: https://developer.adobe.com/app-builder/docs/guides/runtime_guides/reference_docs/configuringproxy]), so Bynder's per-IP limit and its five-minute pause are probably shared with other Runtime tenants and one noisy neighbour can pause every author [INFERENCE; R12; Question 9]. The template's short retry window (cap 2 s, #2 Decision 11) cannot outwait a five-minute pause, by design; the browser honours the delay. Whether the template's default retry of `429` during Bynder's pause extends it is [OPEN: MB3]; if it does, the module asks for a per-call "do not retry 429" option (the analogue of Cloudinary's `420` handling, #23 D16).

**D17. Quota protection.** The shell's controls apply unchanged (debounce, page size 24 default and 50 cap, the per-author result cache `BYNDER_CACHE_SECONDS` default 30 s in container memory only, keyed by the connection key and a configuration fingerprint of portal, client id and public-only flag; detail and errors never cached; #25 D14). Search and detail each cost one Bynder request. The module keeps **no State entry of its own** (Cloudinary's rate-limit early stop has no Bynder counterpart: Bynder documents no remaining-quota header, so there is nothing to record).

**D18. Disconnect semantics (the honest version).** Without a `revoke` member, the plumbing's Disconnect makes no upstream call and only deletes the stored record and the author's cache entries (#25 D11). The Bynder grant therefore remains valid at Bynder until a portal admin uses "Revoke all refresh tokens" or deletes the OAuth app [VERIFIED*: support article]; a Bynder refresh token "will not expire", so a leaked stored token is a standing credential [VERIFIED*: same article]. That is why encryption at rest, the retention TTL (`CONNECTION_TTL_DAYS`, default 180) and the purge procedure in #25 D27 matter more here than for Dropbox. The README states the semantics and the offboarding procedure (portal admin revokes the app's refresh tokens; maintainer purges the State key for the author with the #25 purge script); the panel should say it too (amendment A4, a capability flag derived from the absence of `revoke`).

**D19. Replacing the OAuth app invalidates stored connections (scope immutability).** Because Bynder scopes cannot be edited, changing scopes (or losing the client secret, which is shown once) means creating a new app with a new client id. Stored refresh tokens belong to the old app and will fail at the token endpoint (probably `invalid_client` or `invalid_grant`), and under D6 an `invalid_client` is *misconfigured*: the author would see "ask your administrator" and no Reconnect until their record expires. Amendment A3 asks #25 to bind a **configuration fingerprint** (client id and tenant host, never a secret) into the stored record and to read a mismatch as `reauth_required`, so a deliberate app replacement turns into a clean Reconnect for everyone. Fallback if A3 is declined: the README documents the purge procedure (the State key purge script, #25 TS10) and the retention TTL as the recovery path.

**D20. Runtime budgets for Bynder's payloads.** Per `api` request: at most one Bynder call (search or detail) plus at most one refresh; per callback: the code exchange plus one `currentUser` call. All run inside the action's 25 s timeout and the proxy's 15 s overall deadline (#2 Decision 11). Because the list has no `fields` parameter, a 50-item page carries every asset field including every `property_*`, `tags` and URLs; the template's upstream-body cap ("below the 1 MB result limit", `502 upstream_too_large` above it) and the 1 MB result limit apply. Estimated 2 to 10 KB per asset, so 24 items is roughly 50 to 240 KB and 50 items up to about 500 KB [INFERENCE; unmeasured, R15]. The module maps the response to the allow-listed summary before returning, so the **outbound** payload is small even when the upstream one is large; the constraint is the upstream cap. Stored record: about 2 to 5 KB (access tokens are JWTs, access and refresh token plus metadata, base64 inflation inside the envelope) against State's 1 MB value limit; bandwidth, not size, is the State constraint to watch (one record read per `api` request and per connect poll; #25 R19). MB3 and the emulator tier record the real sizes (BYN-ED3); A7 asks the template for a per-call cap override if 50 full records do not fit.

**D21. Insertion and experience.** Unchanged: the shell serialises one `<img src alt>` with DOM APIs and sends it with `sendHTML` then `closeLibrary`; non-images are one `<a>`; only `https:` URLs are inserted (#23 D18). Bynder public URLs end up in the document; deleting an asset breaks them after CDN cache expiry (default 24 h on Bynder's CDN), and archiving or limiting an asset does not invalidate cached URLs and, by default, does not break them at all unless Customer Support enables that [VERIFIED*: public assets article]. One README sentence: pickers insert references, not copies.

**D22. Bynder app registration, environments and deploy.** Recommended: **one Bynder OAuth app per workspace** (one for Stage, one for Production), registered by a portal admin after Customer Support has enabled OAuth Apps, with the three default scopes (unless MB3 shows more are needed), and **one redirect URI: the workspace's `oauth` callback `{OAUTH_PUBLIC_BASE_URL}/bynder/callback`** (known only after the first deploy; the `ref=local` page also calls the Stage worker, so no localhost URI exists) [OPEN: Question 4: whether Bynder accepts an `https://<namespace>.adobeioruntime.net/...` redirect URI and more than one URI per app; Bynder's own example is `https://localhost/callback`]. Each workspace has its own untracked `.env` (client id and secret of its own app, optionally a different portal for Stage, plus #25's keys). Deploy is manual and Stage-first (`env -u CI aio app deploy` from the worker folder with the owner's Developer Console login, #2 Decision 18, #25 D28); adding Bynder is "set three `.env` values, deploy"; the first Stage deploy of the Bynder inputs is the owner's or an explicitly authorised step. Rotating the client secret is "edit `.env`, `aio app deploy --action api` and `--action oauth`" [VERIFIED in #2: the `--action` flag]; whether a Bynder OAuth app can issue a new secret without being replaced is [OPEN: Question 4]. No Developer Console credential is in CI.

**D24. Docs ship with the code (AC5).** The extension README gains a **Bynder section**: what the provider does and its limits (read-only, no folders, no collections, public URLs only, no relevance sort); Bynder-side setup (Customer Support enablement, required admin permissions, registering the OAuth app per workspace, scopes and that they are immutable, the redirect URI of each workspace, that the secret is shown once, enabling public derivatives and the SEO base URL so `original` is returned, an alt-text metaproperty, custom CDN hosts); the exact inputs and secret table with the `.env` entries and the `aio app deploy` commands (`env -u CI`); the exact `library` row (unchanged); "site config keys read: none; no new config-sheet row"; Disconnect and offboarding semantics (D18); the replacement-of-app procedure (D19); rate limits and the shared egress caveat (D16); the per-user permission model; the public-link longevity sentence (D21); and a troubleshooting list (consent completes but nothing appears: narrowed scopes; every rendition "not insertable": delivery hosts; image broken for visitors: public flag or `/asset/` routing on a custom domain; "ask your administrator": OAuth app, secret or redirect URI).

## Testing Decisions

**What makes a good test here.** Assert external behaviour only: given a web-action invocation (raw `params`: headers, path, query; inputs from the kit's `makeInputs`; fake IMS, fake Bynder, in-memory store) assert the returned `{ statusCode, headers, body }`, redirects and cookies, the stored (encrypted) bytes and the requests the fake Bynder received (method, host class, path, query, headers, form body); given an SDK result and a worker stub, assert the DOM and the SDK actions. Never assert on internal helper names or internal call counts. Properties asserted as negatives across every path: **no Bynder client secret, access token, refresh token, sealed ticket or state, binding nonce or encryption key ever reaches a response, header, redirect, log line or the browser**; **nothing runs before authentication succeeds on `api`, and the `oauth` action does nothing without a valid sealed value**; **no URL Bynder returned is ever altered, and no URL is built from an id or a name**; **the Bynder folder contains no token-storage, State, encryption or cookie code**; **a rotating refresh is never retried and never runs unlocked**.

**Proposed seams** (recorded here instead of asked, per #60). The seams are #2's, #23's and #25's; **this ticket adds no seam**. The one seam #23 introduced for this purpose, the provider interface with its shared conformance suite (P1), is what proves "Bynder only adds a module".

**Auth flow (author to worker):** SDK token -> `Authorization: Bearer` -> #2 verification inside `api` -> `identity.userId` -> record key `conn.v1.` + hash(userId, "bynder") (#25 D6).

**Auth flow (Bynder connection)** is #25 D7's six steps with Bynder values: (1) `POST connect` returns `{ beginUrl }`; (2) the click handler opens the pop-up synchronously and navigates it to `beginUrl`; (3) `begin` verifies the ticket, sets the binding cookie and `302`s to `https://{portal}/v6/authentication/oauth2/auth` with the sealed `state`; (4) the author signs in to the portal (possibly SSO) and approves the listed scopes; (5) Bynder `302`s to `{OAUTH_PUBLIC_BASE_URL}/bynder/callback` with `code` and `state`; the `oauth` action verifies state and cookie, exchanges the code (form body, same `redirect_uri`), requires a refresh token and the full requested scope, calls `currentUser`, stores the encrypted record and returns the static page; (6) the extension's `session` poll flips to connected. The stored access expiry is `now + expires_in` (about 3,600 s).

**Auth flow (per call):** read and decrypt the record -> refresh if under 60 s remain (in-container single flight, then the State lock; **rotation-aware, never unlocked, no retry**, D7) -> call Bynder with `Authorization: Bearer <author's token>`, never the IMS token -> on `401` the shell forces one refresh and retries once; a second rejection destroys the tokens, writes the reauth marker and answers `409 provider_reauth_required` -> normalise -> output URL policy -> respond.

**Disconnect flow:** `POST disconnect` -> (no `revoke` member, so no upstream call) -> delete the record -> purge the author's cache entries -> `204`.

### Amendments requested to ticket #25 (OAuth plumbing gaps this vendor exposes; each has a fallback so #22 is never blocked on a redesign)

- **A1. Config-derived hosts and scopes (confirm).** Bynder's authorize, token, API and delivery hosts are one per-portal host and its scopes are configurable. Please confirm that `authorizeHosts` and `scopes` (like `deliveryHosts` and Cloudinary's `outboundHosts`) may be functions of validated configuration and that registration validates them after config validation (#25 PO2). This is probably already covered by #25's per-tenant-host stub (PO4); the ask is an explicit conformance assertion. *Fallback:* none at module level (a static host list cannot express a tenant host); treat as a blocker if declined.
- **A2. Token-call retry options are the provider's (clarify; was a change in the earlier draft).** #25 D22 declares the Dropbox refresh grant safe to retry through the proxy's explicit POST opt-in, which implies the provider owns the retry options of its token calls; D9 step 6 says the retry schedule applies "only where the call is declared safe to retry". Please confirm that a provider can leave both token calls undeclared (and set zero retries), and parametrise RF7 so the "refresh retried" expectation applies only to providers that declare it. *Fallback:* none needed if confirmed; if the shell issues token calls itself with a fixed retry policy, make "refresh is retry-safe" a provider-declared flag (default true as today), set false by Bynder and Frontify.
- **A3.
