## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party) and, after #23, from Cloudinary, but many teams, especially small marketing teams, agencies and regional offices, keep working brand assets in **Dropbox**. Today an author who wants a Dropbox image leaves EW, finds the file, creates a shared link, edits the link by hand so that it renders instead of showing Dropbox's preview page (`dl=0` -> `raw=1`), pastes it and retypes alt text from the file name. Nothing checks that the link is public: a team-only or password-protected link looks fine in the editor and is a broken image for every visitor.

Dropbox is also the **first vendor that authenticates the individual author**, and that is the larger problem. The picker so far (#23) uses one service credential held by the worker; every author sees the same assets. Dropbox, like Bynder and Frontify, decides what each person may see through OAuth on behalf of that person. That needs four things the picker does not have: a way for an author to **connect and disconnect from inside the library iframe**, a **callback that cannot carry an IMS token** (a browser redirect from dropbox.com has no `Authorization` header) and must therefore be made safe in another way, a **server-side store for long-lived refresh tokens** that are encrypted at rest and never reach the browser, and **refresh logic** that keeps short-lived access tokens fresh without prompting the author. The extension code is public, so none of this can live in the browser.

If each of the three OAuth DAMs (Dropbox, Bynder, Frontify) wrote this itself, the security-critical parts (state handling, login-CSRF defence, encryption, refresh races, revocation) would be written three times and drift. This ticket must therefore build the plumbing **once, provider-agnostically**, proven by more than one OAuth shape (Dropbox's non-rotating form-encoded tokens and a stub that behaves like Frontify's single-use rotating JSON tokens), so that #22 and #24 are a module and a registry line.

Finally Dropbox is the least DAM-like vendor of the four. It has no rendition URLs, no description or alt-text field, no tags, no type facet, thumbnails that are binary API responses rather than URLs, folder-first navigation instead of a flat asset bank, and cursor-only search paging. Those differences, not the OAuth mechanics, are the real work of the provider half and are decided below.

## Solution

The existing **Multi-DAM Picker** library plugin gains a second provider, **Dropbox**, and the ability to host providers whose credential kind is `user-oauth`. When more than one provider is configured the author sees the shell's source switcher. Choosing *Dropbox* for the first time shows **Connect to Dropbox**: a pop-up to dropbox.com where the author signs in with their own Dropbox account (personal or work, including company SSO) and approves read access and link creation. The panel then shows "Connected as <name>" with a **Disconnect** action and the author's files: a thumbnail grid with file names, searchable by file name and content, filterable by type (images, videos, documents, audio), sortable (newest, relevance when searching), with "Load more". Selecting a file opens a detail pane with name, dimensions (photos), type, size, an alt text prefilled from a configured Dropbox file property if the team uses one else from the file name (editable, or "decorative"), and one rendition: the file itself through a public Dropbox link. **Insert** places an `<img>` with that URL and the alt text at the cursor and closes the library; non-image files insert as a link with the file name as text. Files that cannot be used (the sharing policy forbids a public link, the existing link is password-protected or expiring, the format cannot be shown by browsers) are shown as not insertable with a one-line reason. If Dropbox access is later revoked, the panel shows **Reconnect** instead of a cryptic error.

Behind it, the existing worker, extended, does everything sensitive. It starts the Dropbox authorization-code flow with `token_access_type=offline`, protects the public callback with a **sealed, expiring state plus a browser-binding cookie** (so only the browser that started a flow can finish it), exchanges the code with the app secret, stores each author's tokens **encrypted at rest, keyed by the author's verified IMS identity**, refreshes the four-hour access token silently, injects the author's own access token into every Dropbox call, and on Disconnect **revokes the grant at Dropbox** before deleting the stored copy. The browser only ever holds its own IMS token and normalised asset data. The plumbing knows nothing about Dropbox: the provider supplies HTTP mappings (authorize URL, code exchange, refresh, account name, revoke) and the browse methods; a later provider adds the same and nothing else.

## Implementation Decisions

(No file paths or code, except endpoint names and wire contracts, which are API contracts. Layout is in the Build Analysis.)

**D1. Scope and delivery split: shell plumbing first, provider second, in one ticket.** The ticket delivers (A) the OAuth plumbing in the shell (worker core and browser panel) and (B) the Dropbox provider module. This is the owner-approved reading of #25's criteria: "no changes needed in the extension shell beyond registering the provider" holds for the **provider** (B) and for every later provider; the plumbing (A) is itself #25's first deliverable and is by necessity shell work [OPEN: Question 1, carried from #23 Question 1]. The ticket is built and reviewed in two phases so that the criterion is checkable: **Phase A** (plumbing) lands and is verified with a vendor-neutral stub `user-oauth` provider before any Dropbox app exists; **Phase B** (Dropbox) is a diff that touches only the provider folder, one registry line, the worker's wrangler vars and `.dev.vars.example`, the README section and the conformance-suite registration (D1 is enforced by repo check RO2).

**D2. Surface and registration unchanged.** Library plugin only; the one `library` row from #23 is unchanged; **no new config-sheet row and no new entry page**; **site config read: none**, and the README says so. Dropbox appears in the existing panel when its worker configuration is present (#23 D5, D20).

**D3. Build against the Dropbox HTTP API, not Dropbox's Chooser drop-in.** The Chooser (https://docs.dropboxapi.com/dropbox-api/docs/pre-built-components/chooser.md) is cheaper (no worker, no OAuth, no production approval) and is what Contentful ships (O5). It is rejected: (a) #25's criteria require per-user OAuth through the worker with tokens stored and refreshed server-side, and the Chooser authorises in the browser on dropbox.com's own session; (b) it brings its own picker UI, which the capability-driven shell cannot drive, so it would need browser code and break "provider module only"; (c) it needs the hosting domains registered in the Dropbox app, and EW iframes pages from three host families plus `localhost` (#2 Decision 5). Dropbox's own guide steers pickers to the Chooser ("Requesting Full Dropbox access to pick a file when you could use the Chooser isn't a good use of the permission", https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md [VERIFIED*]); the cost of this choice is the production-approval path (D23). **A second alternative is recorded: online-only tokens.** Dropbox's OAuth guide recommends, for "a server-side web application that only calls the Dropbox API as users interact with it", the code flow with short-lived tokens only and no refresh tokens (https://docs.dropboxapi.com/dropbox-api/docs/oauth.md, summary table [VERIFIED]); an expired token then re-runs the redirect, which needs no user input while their Dropbox session and approval are valid. That would remove stored refresh tokens but contradicts #25's "tokens are stored and refreshed server-side", would make every four-hour expiry a pop-up, and would not generalise to Bynder and Frontify, so it is not chosen [OPEN: Question 6].

**D4. Turn on the `user-oauth` credential kind; enablement rule.** #23 D4 defines `user-oauth`, validates a stub declaration and refuses to start when a provider declares a kind not in the "hosted kinds" set (`{service}`). This ticket adds `user-oauth` to the set **together with everything #23 D4 lists**: the connect/session/disconnect routes and the two public OAuth routes, the encrypted token store, refresh orchestration and credential injection, and the browser connect panel. Conformance test PC5 ("defined but not hosted") is **retired and replaced** by the tests of this ticket. **Enablement rule:** the OAuth plumbing is *enabled* when the token-store binding and both shell secrets (token-encryption key, state key) and the public worker origin are present. A `user-oauth` provider is *configured* when its own required vars and secrets are present (#23 D5: otherwise omitted, routes `404 not_found`, worker still starts). If a `user-oauth` provider is fully configured but the plumbing is not enabled, **the worker fails to start** with a message naming the missing plumbing items (never their values): the admin clearly intended to use the provider, and a silently missing Dropbox is a debugging trap. The shell-owned secrets are **not** in the wrangler `secrets.required` guard, because a Cloudinary-only deployment (#23) must keep deploying unchanged [Needs #23 TG2 optional secrets; OPEN: Question 2].

**D5. Interface additions (additive, optional, defaulted).** #23 D3 fixes the `user-oauth` members: `scopes`, `buildAuthorizeUrl(state, redirectUri)`, `exchangeCode(code, redirectUri)`, `refresh(refreshToken)`, `accountName(credentials)`, optional `revoke(credentials)`, optional maximum `state` length, with the shell owning state sealing, cookies, token encryption and storage, refresh orchestration and credential injection. The plumbing pins the behaviour of those members and adds the following **optional members and normalised shapes**; none changes an existing member, and a provider that omits them gets the default:

| Item | Behaviour |
|---|---|
| Token result of `exchangeCode` and `refresh` | the provider returns a normalised result: `accessToken`, `expiresInSeconds`, optional `refreshToken`, optional `scope` (string), optional `accountId`. The shell stores what it is given: a refresh result **without** `refreshToken` keeps the stored one (Dropbox); one **with** it replaces the stored one (Frontify-style rotation). An absent `expiresInSeconds` is treated as the shell default of 3600 s [ASSUMPTION: Bynder, Frontify always send it; confirmed in their tickets] |
| Failure classes of the OAuth calls | each of `exchangeCode`, `refresh`, `accountName`, `revoke` fails with exactly one of: **reauth** (definitive: the grant is invalid or revoked), **transient** (retry later, keep the record), **misconfigured** (client id/secret/redirect problem: keep the record, generic failure). An unclassifiable failure is **misconfigured**, never reauth, so a vocabulary surprise can never delete a working connection |
| `authorizeHosts` (required for `user-oauth`) | the hosts `buildAuthorizeUrl` may point at (a top-level navigation target, not an outbound call). The shell refuses to redirect anywhere else: an https URL, host in the list (loopback only when the local flag is set), the supplied `state` and `redirect_uri` present byte-for-byte, no client secret anywhere in it. This closes an open-redirect and secret-in-URL class for every provider |
| `callbackCodeParam` (optional, default `code`) | the query parameter carrying the authorization code on the callback (Frontify's page shows `authorization_code`, https://developer.frontify.com/document/68#/get-started/authentication-1 [VERIFIED*]) |
| `maxStateBytes` (optional, default 2000) | the provider's limit on `state`; Dropbox documents 2,000 bytes. The shell checks the sealed state against it at `connect` time and refuses (generic failure) rather than truncating |
| `requiresRefreshToken` (optional, default true) | the shell refuses to store a connection whose first token result lacks a refresh token (a connection that cannot refresh is never kept) |
| Required scope check | when the first token result carries `scope`, the shell requires it to contain every scope in `scopes`; otherwise the connection is refused. When it is absent the check is skipped |
| Per-call context for `user-oauth` | the credentials (`accessToken`, `scope`, account), the outbound helper pinned to `outboundHosts`, config, secret accessor, injected clock. **Never the IMS token, the inbound `Authorization` or cookies** (PC7). The provider applies the access token to its own outbound calls |
| "Token rejected" signal | a provider reports an upstream authentication failure from `search`/`getAsset` as the existing failure class **reauth required**. The shell treats the first such failure of a call as "access token rejected": it forces one refresh and retries once; a second one makes the connection `reauth_required` (D9). The provider never refreshes or stores tokens itself |

**D6. Connection identity and record key.** A connection belongs to the **verified IMS `userId`** produced by the #2 template, never to anything the client sends; different EW users never share a connection, the same user shares one connection across browsers and sessions. The record key is `conn:v1:` + the URL-safe base64 of SHA-256 over `userId`, a separator and the provider id; it is also bound into the ciphertext as authenticated data (D8). The hash keeps the IMS user id out of the KV key listing; it is deliberately **unkeyed**, so a party with KV read access could test a guessed user id for membership. Accepted: the same party already sees ciphertext, and a keyed hash would either tie record lookup to a rotating secret or add a third permanent secret [ASSUMPTION: acceptable; Open Question 3]. [ASSUMPTION: the IMS `user_id` claim is the same for the shell token and the library token of one person; carried from #2 R4 and #22 R14; confirmed in manual step MD7.]

**D7. The connect flow: ticket, begin, sealed state, binding cookie, callback.** The browser redirect from dropbox.com cannot carry an `Authorization` header, so two routes are public (D12) and made safe as follows:

1. `POST /dam/{provider}/connect` (IMS-authenticated) returns `{ beginUrl }`, whose origin is the configured `PUBLIC_WORKER_ORIGIN` (never derived from `Host` or forwarded headers) and which carries a **ticket**: a sealed (AEAD) payload `{ purpose: ticket, userId, provider, exp ~60 s }`.
2. The click handler opens a pop-up synchronously and navigates it to `beginUrl` (D13).
3. `GET /oauth/{provider}/begin?ticket=` (public) verifies the ticket, generates a random **nonce**, sets the **binding cookie** carrying the nonce (HttpOnly, SameSite=Lax, path-scoped to `/oauth/`, `Secure` except in the local environment, `Max-Age` at most 600 s), and `302`s to the provider's authorize URL (validated per D5) with `state` = a sealed payload `{ purpose: state, provider, userId, SHA-256(nonce), exp ~10 min }`.
4. The author signs in at the provider and consents.
5. The provider `302`s to `GET /oauth/{provider}/callback?code&state` (public). The worker (a) answers `405` to anything but `GET`; (b) on a provider `error` parameter shows the generic failure page, reflects nothing and makes no token call; (c) unseals `state` (expiry, purpose, provider equal to the path), (d) requires the cookie nonce to hash to the value in `state`, (e) exchanges the code once with the provider's mapping (client secret from the secret store), (f) validates the token result (refresh token present, scope check, D5), (g) fetches the account name, (h) writes the encrypted record, (i) clears the cookie and returns the static result page. Any failure before (h) stores nothing, leaves an existing record for the user untouched and returns the **same** generic failure page for every cause (no oracle).
6. The extension polls `GET /dam/{provider}/session` (IMS-authenticated) until `connected` (D13).

**Why the cookie.** Without it an attacker could start a flow with their own IMS token and trick a victim into completing the consent in the victim's browser, silently linking the victim's Dropbox to the attacker's EW identity (login-CSRF / account linking). With it only the browser that began the flow can finish it. The cookie is a first-party cookie of the worker origin: the pop-up is a top-level browsing context, and `SameSite=Lax` cookies are sent on the cross-site top-level `GET` navigation from dropbox.com back to the worker [VERIFIED: MDN `Set-Cookie`: `Lax` cookies are sent on cross-site requests that are a top-level navigation and use a safe method]. A `Secure` cookie is sent only over `https:` (MDN notes an exception for `localhost`), so the local environment, which runs over plain `http`, sets the cookie without `Secure`; production always sets it [VERIFIED: MDN `Set-Cookie`, `Secure`]. The state and ticket are **stateless** (sealed, no KV record): a pending-flow record would cost a KV write per click against the Free-plan write budget (D8) for no gain; replaying a callback URL is harmless because the provider's code is single-use [ASSUMPTION: Dropbox codes are single-use; the second exchange fails upstream, OA9, and the record from the first stays intact]. Sealing is AES-256-GCM under keys derived (HKDF) from the state secret with distinct labels for ticket and state, so a ticket can never be accepted as a state or the reverse.

**D8. Token store: encrypted at rest in Workers KV behind a small storage interface.** The record is `{ v, accessToken, accessExpiresAt, refreshToken, scope, account: { displayName, id? }, connectedAt }` for a connected state, or a **reauth marker** `{ v, reauth: true, account: { displayName }, at }` after a definitive failure (D9): tokens are destroyed but the account label is kept so the panel can say "Reconnect (was connected as ...)" and the provider list can report `reauth_required` (the third `connection.state` of #23 D4). Records are sealed with **AES-256-GCM** under a worker secret, fresh random IV per write, key id in the envelope, **authenticated data = the KV key**, so a record copied to another key fails to decrypt (treated as not connected, logged by outcome only). A **previous-key secret** may be set so rotation does not force every author to reconnect: reads try the current then the previous key and writes re-encrypt under the current one. The store interface is `get(key)`, `put(key, envelope)`, `delete(key)`, hiding KV so a Durable Object implementation can replace it without touching providers or the orchestration. **Retention:** every write sets a KV expiry of `CONNECTION_TTL_DAYS` (default 180) so an idle author's stale refresh token disappears (an active author rewrites the record at least every access-token lifetime; Dropbox: every four hours); an expired record reads as not connected and the Dropbox grant stays listed in the author's own connected apps (README says so) [OPEN: Question 4]. **Why KV:** simplest platform store, fits a low-write workload, no template dependency beyond a binding. Limits [VERIFIED: https://developers.cloudflare.com/kv/platform/limits/]: Free plan 1,000 writes per day to different keys and 100,000 reads per day, 1 write per second to one key, 25 MiB values, 512-byte keys. Dropbox writes once per connect and once per four-hour refresh per active author (at most about 6 per day), so the Free plan serves roughly 150 active authors per day before the write limit; the README states this and that the Paid plan lifts it. **Consistency:** KV is eventually consistent; changes may take 60 seconds or more to be visible in other locations and negative lookups are cached too [VERIFIED: https://developers.cloudflare.com/kv/concepts/how-kv-works/]; the same page recommends Durable Objects where stronger guarantees are needed. Effects are handled in D9 (refresh) and D13 (the poll tolerates a delayed `connected`). A Durable Object store is the documented upgrade, a shell-internal change, **not** needed for Dropbox, whose refresh tokens never rotate [OPEN: Question 3, decision gate before #24 enables a rotating provider].

**D9. Refresh orchestration (provider-agnostic).** Per call to `search`/`getAsset`: read and decrypt the record; if `reauth` marker or absent -> `409 provider_not_connected` / `409 provider_reauth_required` before any provider call. (1) **Proactive:** if fewer than 60 s remain on the access token, refresh first. (2) **Single-flight:** concurrent refreshes of the same record in one isolate share one provider call. (3) **Reactive:** if the provider reports *reauth required* from a browse call, force exactly one refresh and retry the browse call once; a second *reauth required* is definitive. (4) **Store the result:** `accessToken` and expiry always; the refresh token is replaced only when the result carries one (D5). (5) **Failure classes:** *reauth* from `refresh` -> **before destroying anything, re-read the record**; if storage now holds a newer record (another isolate won), use it; otherwise destroy the tokens, write the reauth marker and answer `409 provider_reauth_required`; *transient* -> the template's retry schedule applies only where the call is declared safe to retry (the refresh grant is; D22), then `502 upstream_unavailable`, **record kept**; *misconfigured* -> `500 misconfigured`, record kept, no reconnect prompt, a log line naming the provider and class only. (6) **Write failure after a successful rotating refresh** (the provider already invalidated the old refresh token): retry the write once, keep the new record in isolate memory for the isolate's lifetime and log the event; if every attempt fails the next isolate finds the old, now-invalid token and the author reconnects (documented residual risk R5; absent for Dropbox, whose refresh token never changes). The orchestration is identical for every provider; Dropbox exercises the non-rotating path and the stub exercises rotation (D17, tests RF1-RF10).

**D10. Credential injection and redaction.** The shell hands the provider the author's credentials through the per-call context; the provider sets the `Authorization: Bearer <author's access token>` header on its outbound calls through the pinned outbound helper. The IMS token is never forwarded, never stored, never in the context. Because the user's access and refresh tokens, the sealed values and the binding nonce are not in `env`, the #2 redaction pass cannot know them: the plumbing registers each request's live token values for **per-request redaction** of every response body, header and log line [Needs template gap OG3, D15], so a provider that echoes a token in an error body cannot leak it.

**D11. Disconnect revokes upstream, then deletes.** `POST /dam/{provider}/disconnect` (IMS-authenticated, idempotent, `204`): if the record holds tokens and the provider implements `revoke`, the shell calls it **best-effort** with a fresh access token (refreshing first if stale), then **deletes the record regardless of the result** (a stale grant at Dropbox is visible to the author in their connected apps; a stuck record in our store is not recoverable by them); it also purges the author's entries in the per-user result cache (D14). A reauth marker is simply deleted. Dropbox revoke (D17) invalidates the refresh token and every access token derived from it. Shared links already created are **not** removed (README says so). Connecting again replaces the previous record without revoking the old grant: revoking the old tokens could, for a provider that shares token families, kill the new connection [ASSUMPTION; harmless orphan grants remain visible to the author].

**D12. Worker API surface (#23 reserved routes, now routed).** All paths below `/dam/` require the IMS token (auth-first, #2 Decision 4): no token `401` (including unknown paths), token and unknown `404 not_found`.

| Method + path | Auth | Purpose | Result |
|---|---|---|---|
| `GET /dam/providers` (existing) | IMS | gains, for `user-oauth` providers, `connection: { state: connected \| not_connected \| reauth_required, account?: { displayName } }` | `200` |
| `POST /dam/{provider}/connect` | IMS | issue the begin URL | `200 { beginUrl }`; `404 not_found` unknown/unconfigured; `400 bad_request` if `state` would exceed the provider's limit |
| `GET /dam/{provider}/session` | IMS | connection state for one provider | `200 { connection }` |
| `POST /dam/{provider}/disconnect` | IMS | revoke (best-effort) and delete | `204` |
| `GET /dam/{provider}/assets...` (existing) | IMS | browse and detail now run with the author's credentials | adds `409 provider_not_connected`, `409 provider_reauth_required` |
| `GET /oauth/{provider}/begin?ticket` | **public, sealed ticket** | set the binding cookie, `302` to the provider | `302`; `400` generic page for any ticket problem |
| `GET /oauth/{provider}/callback?...` | **public, sealed state + cookie** | finish the flow | `200` static page on success, `400` identical static page on every failure; `405` for other methods |

The two public routes are top-level navigations, not CORS endpoints (no `Access-Control-Allow-Origin`), and answer **only** `GET`. They are the **only** unauthenticated routes in the worker besides `OPTIONS` preflight. The callback page is static and script-free ("You are connected. You can close this window." or one generic failure sentence), with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and a restrictive CSP (`default-src 'none'; frame-ancestors 'none'`), reflecting no request input. **Error contract additions:** the #2 shape `{ error: { code, message, requestId } }` with two extension codes, `provider_not_connected` and `provider_reauth_required` (both `409`, fixed messages) [Needs template gap OG4]; everything else reuses #2 codes (an unknown or unconfigured provider is `404 not_found`, as #23).

**D13. Browser connect panel: the single extension point #23 left.** #23 UI15 shows a provider whose `connection.state` is not `connected` as unavailable with a fixed notice; this ticket replaces that branch with the panel, with **no vendor knowledge** (label and state only):

- `not_connected` -> "Connect to <label>" button. The click handler calls `window.open` **synchronously before any `await`**, then requests `beginUrl` and sets the pop-up's location; if `window.open` returns `null` (blocked) a visible instruction and a real link fallback are shown. Completion is detected by **polling `session`** (about every 1.5 s, backing off to 3 s, giving up after about 5 minutes [ASSUMPTION: values]) and by noting the pop-up closing without a connection (message with retry); there is **no `postMessage`** channel, because the pop-up can lose its opener under cross-origin opener policies. On `connected` the panel best-effort closes the pop-up (`close()` works on windows script-opened by the page, [VERIFIED: MDN `Window.close()`; a no-op otherwise, the page then says it can be closed]) and loads the grid without a reload. Polling cost is one KV read per poll (about 200 per connect, well inside the Free plan's 100,000 reads per day).
- `connected` -> a header "Connected as <displayName>" with **Disconnect**; Disconnect calls `POST disconnect` then shows the Connect state.
- `reauth_required` -> "Reconnect" (and the old account label); an in-band `409 provider_reauth_required` or `409 provider_not_connected` from any browse call flips the panel to the matching state **without a reload**.
- `misconfigured` (`500`) never shows Reconnect: "ask your administrator" only (#23 UI7).
- Because KV is eventually consistent (D8), a poll in another location may see `not_connected` for up to a minute or more after a successful callback; the poll tolerates that by continuing to its deadline. Same user, same browser normally reaches the same location [ASSUMPTION; observed in MD7].

**D14. Result cache scope for `user-oauth` (the rule #23 D17 left to this ticket).** The shell's short result cache is enabled for `user-oauth` providers **per author only**: the key includes the connection key (D6, so the hashed IMS user and provider), the provider's configuration fingerprint (client id, root path) and the full validated request. Two authors never share an entry; entries for an author are dropped on Disconnect and on any *reauth required*; detail responses and errors are never cached (unchanged). Entries live in isolate memory only (never in KV, they would hold file names of private files) and the hit rate is best effort. Dropbox default `DROPBOX_CACHE_SECONDS=30` (`0` disables).

**D17. Dropbox OAuth: authorization-code grant with `token_access_type=offline`, executed by the worker.** Authorize at `https://www.dropbox.com/oauth2/authorize` with `client_id`, `response_type=code`, `redirect_uri` (exact, registered), the sealed `state`, `token_access_type=offline` and an explicit `scope`; token endpoint `https://api.dropboxapi.com/oauth2/token`, authenticated with the app key and secret as `application/x-www-form-urlencoded` POST parameters or HTTP Basic [VERIFIED: https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization.md]. It can be stored and re-used multiple times"; a refresh "won't return a new refresh token since refresh tokens don't expire automatically and can be reused repeatedly" (so Dropbox never rotates: the refresh race that matters for rotating vendors cannot invalidate a Dropbox connection); a refresh response carries `access_token`, `expires_in`, `token_type` and (only if requested) `scope`; `state` is "up to 2000 bytes"; "All redirect URIs must be HTTPS except for localhost URIs", registered exactly, so `http://localhost:8787/oauth/dropbox/callback` is registrable; on error or denial the redirect carries `error`, `error_description` and `state` [VERIFIED, same page]. The authorize page "should not be displayed in a web-view", so the pop-up is the supported shape [VERIFIED, same page]. The client secret is the confidential-client credential, so **PKCE is not used and the console's "Allow public clients" toggle is switched off**, which Dropbox advises when neither PKCE nor implicit is used ("If your app uses neither, it is safer to turn the toggle off", OAuth guide [VERIFIED]); the plumbing has no PKCE support in this ticket and gains it additively if Bynder requires it [OPEN: Question 12]. Client credentials (app auth) are not used (they cannot call user endpoints). **Error classification** (the provider's mapping into D5 classes): token endpoint `400` whose `error` string starts with `invalid_grant` -> *reauth*; `400` starting with `invalid_client` (O2) -> *misconfigured*; any other `400` -> *misconfigured* (never delete on a vocabulary surprise); `5xx`/network -> *transient*; browse calls: `401` with `invalid_access_token`, `expired_access_token`, `missing_scope` or `user_suspended` -> *reauth required* (D5 token-rejected signal; `invalid_access_token` and `expired_access_token` both mean "refresh then retry", https://docs.dropboxapi.com/dropbox-api/docs/error-handling.md [VERIFIED*], O3). [ASSUMPTION: `invalid_grant` is the form for a revoked refresh token; O2 shows only the `invalid_client` form because no valid client exists to probe with; confirmed in MD4.] **Account name:** `POST /2/users/get_current_account` (scope `account_info.read`), `name.display_name` [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account.md; whether a no-argument RPC takes no body is [ASSUMPTION], MD3]. **Revoke:** `POST /2/auth/token/revoke` "disables the access token used to authenticate the call. If there is a corresponding refresh token for the access token, this disables that refresh token, as well as any other access tokens for that refresh token" [VERIFIED: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/auth/token-revoke.md]; a `401` on revoke means the token is already invalid and counts as success.

**D20. Type, format and thumbnails.** Dropbox metadata has no mime type and results carry no category, so a **provider-owned extension table** maps extensions to the shell's types (image, video, document, audio, other) and to *insertable as an image* (browser-renderable: jpg, jpeg, png, gif, webp, avif, svg [ASSUMPTION: Dropbox serves SVG through `raw=1` with an image content type, MD5]); HEIC, TIFF, BMP and camera RAW are `image` for filtering but **not insertable as `<img>`** with a fixed reason. **Thumbnails:** Dropbox exposes no thumbnail URL (`get_temporary_link` URLs last four hours and "should not be used to display content directly in the browser", https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-temporary-link.md [VERIFIED*]); the thumbnail endpoint returns base64 bytes, up to 25 per `get_thumbnail_batch` call, for jpg, jpeg, png, tiff, tif, gif, webp, ppm, bmp, files over 20 MB are not converted [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-thumbnail-batch.md]; an `<img>` cannot send a bearer header, so a worker thumbnail route would need sealed URLs and new shell routes. #23 D5 already allows the one needed flex: `thumbnailUrl` (only that field) may be an inline `data:image/jpeg|png|webp;base64,...` of at most 64 KB, everything else stays `https:` only. The provider therefore returns inline thumbnails for convertible files up to 20 MB, in batches of at most 25 (two calls for a 50-item page), and **a thumbnail failure never fails the search** (the item is returned without `thumbnailUrl`; the shell shows a file-type placeholder). **Fallback if the owner drops the inline allowance (#23 Question 8): zero further shell change, the provider omits `thumbnailUrl`** and the thumbnail step and tests DBX-TH1-TH3 are replaced by DBX-TH-F.

**D21. Detail: link resolution, rendition and alt text (the `getAsset` effect).** Dropbox has no CDN-style rendition URLs; the only stable URL that works for visitors is a shared link. For the selected file `getAsset` (a) reads metadata with media info (dimensions; `media_info` may be `pending`, then dimensions are omitted: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata.md [VERIFIED*]); (b) lists the file's existing links with `sharing/list_shared_links` (`direct_only`) and takes the first that is public (`effective_audience` public, not password-protected, no `expires`, downloads allowed); (c) only if none, creates one with `sharing/create_shared_link_with_settings` requesting `audience: public`, `access: viewer`, `allow_download: true`, and **checks what Dropbox resolved**, because "the resolved visibility, though, may depend on other aspects such as team and shared folder settings" (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/create-shared-link-with-settings.md [VERIFIED*]). A resolved non-public audience, a `settings_error` (`not_authorized`, `invalid_settings`), `access_denied`, `email_not_verified`, or an existing link that is not public makes the asset `insertable: { ok: false, reason }` with a fixed reason, **never an HTTP error**. A repeated call is a no-op by construction (step b finds the link), so the `GET`-triggered effect is idempotent; this is the "documented, README-stated exception" #23 D3 allows for `getAsset`, and **Dropbox is its first user**. Existing links are **never modified or revoked** (modifying an existing link's access level is not supported and widening someone's sharing silently would be worse). Cost, stated plainly in the README and in the rendition label: **opening a file's detail pane creates a public link to it** (the URL carries an unguessable `rlkey`, but anyone holding it can read the file). Creating on insert instead needs a new "prepare for insert" step in the shell [OPEN: Question 5]. **Rendition policy:** one rendition, `original` ("Original (size)"), `defaultRenditionId` pointing at it; no resized variants exist as stable URLs. The inserted image URL is the API-returned link with the display parameter set as Dropbox documents ("use raw=1 as a query parameter ... Changing 'dl=1' or 'dl=0' to 'raw=1' in a URL will cause an HTTP redirect", and developers should "properly parse the URL and add or modify parameters as needed", https://help.dropbox.com/en-us/share/force-download [VERIFIED*]). This stays within #23 D5's URL rule (a provider may build URLs from the vendor's documented URL grammar and the structured fields its API returned): the provider parses the returned link with a URL parser (never string concatenation), deletes `dl`, sets `raw=1`, keeps every other parameter (`rlkey`, `st`) untouched, and requires `https` and host `www.dropbox.com` (the output URL policy of #23 D13 then enforces `deliveryHosts`); it never builds a link from a file id or path; the non-image `linkUrl` is the link exactly as returned. **Alt text:** Dropbox has no description or alt field; the only genuine metadata channel is **file properties**: when `DROPBOX_ALT_TEMPLATE_ID` and `DROPBOX_ALT_FIELD` are set, `get_metadata` asks for that template only (`include_property_groups` with `filter_some`) and the field value, stripped to plain text, is the candidate with `source: property`; else the file name without extension, separators to spaces, `source: name`; else empty with `source: none`; `source: description` is never produced; markup, entities and control characters are stripped as in #23 D15; the author always sees and can edit it or mark the image decorative [OPEN: Question 9].

**D22. Error mapping and retry flags (Dropbox).** Dropbox answers: `401` (`invalid_access_token`, `expired_access_token`, `missing_scope`, `user_suspended`) -> *reauth required* (D5, D9); `403` (`no_permission`, team access) -> the shell's forbidden mapping; `409` endpoint errors: `path/not_found` -> not found, search `invalid_argument` -> bad request, link-creation errors -> a `200` detail with `insertable.ok=false` (D21); `429` (always with `Retry-After`; `reason` `too_many_requests` or `too_many_write_operations`, https://docs.dropboxapi.com/dropbox-api/docs/performance.md [VERIFIED*]) -> *rate limited* with the delay; `5xx` and network -> *upstream unavailable*; fixed messages, never upstream text. **Retry flags** (the #2 explicit opt-in for POST): the read-only RPC calls Dropbox exposes as POST (search, list, metadata, thumbnails, shared-link listing, account) are safe to retry on `5xx`; the **refresh grant is safe to retry**; the **authorization-code exchange and revoke are not**; link creation is safe to retry because repeating it returns `shared_link_already_exists`, never a duplicate (D21).

**D23. Dropbox app registration and Dropbox's rules the README must carry.** One Dropbox app per worker deployment, created by the maintainer in the App Console: scoped access, **Full Dropbox**, the five scopes, redirect URIs for the deployed callback and the local one, "Allow public clients" off. The app name "may not include the word 'Dropbox' or begin with 'drop'" (https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/branding-guide.md [VERIFIED*]); proposed name **EW Multi-DAM Picker**; the button text "Connect to Dropbox" identifies the integration and is allowed. A new app has **development status**: it links your own account plus enabled development users up to "500 total Dropbox users", but "once your app links 50 Dropbox users, you will have two weeks to apply for and receive production status approval before your app's ability to link additional Dropbox users will be frozen", and production review "will not be reviewed until your app has linked with at least 50 Dropbox users"; it expects a privacy policy and branding compliance, and the name cannot be changed after approval [VERIFIED: https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md, "Production approval"]. The same guide lists "Don't build file sharing apps" ("Dropbox doesn't support building publicly searchable file sharing networks on top of Dropbox", [VERIFIED]); embedding images from the team's own Dropbox is not a public file-sharing network, but Dropbox's terms (https://www.dropbox.com/developers/reference/tos) were not read [OPEN: Question 7].

**D24. Team spaces are out of scope for v1.** All calls run against the author's home root. Business teams with a Team Space keep shared team folders in a separate root that needs the `Dropbox-API-Path-Root` header and the `root_namespace_id` from `get_current_account` (https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/path-root-header-modes.md, https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account.md [VERIFIED*]). Brand folders are often team folders, so this is the likeliest first follow-up and a real limitation on Business accounts [OPEN: Question 8]; the mechanism is documented so the follow-up is a provider-only change.

**D25. Rate and size budget.** Dropbox publishes no numeric limits: they are "per-authorization", `Retry-After` is always present, and rate-limited requests count (https://docs.dropboxapi.com/dropbox-api/docs/performance.md [VERIFIED*]). Per request the worker issues: a browse (up to 3 search calls plus up to 2 thumbnail-batch calls at the 50-item cap), a detail (3 calls: metadata, list links, create link), at most 1 refresh, plus the KV operations (a few reads, at most one write); all inside the Free plan's 50 subrequests per invocation (#2 Further Notes). Inline thumbnails make a 24-item response roughly half a megabyte [ASSUMPTION: about 15 KB per 256-px JPEG]; the shell's page-size default stays 24. Shared links are subject to Dropbox bandwidth limits that affect **published pages**: "Dropbox Basic 20 GB and 100,000 downloads per day, paid plans 1 TB to 4 TB", and a link "shared or downloaded too many times over a 24 hour period" is temporarily disabled (https://help.dropbox.com/share/banned-links [VERIFIED*]). The README states Dropbox links are for staging and low-traffic use, not a production CDN (Out of Scope names the alternative).

**D26. Tooling and conventions** follow #1, #2 and #23 unchanged and are pinned to upstream: ESLint 8 + helix config, Stylelint 16, `@web/test-runner` for browser unit tests, Node `node:test` for worker tests, Playwright (Chromium) for e2e, Node 22 (>= 22.12 for wrangler 4), husky. Tests live inside the extension folder; the Dropbox tests live under the provider folder, the plumbing tests under the worker folder. No new runner.

**D27. Docs ship with the code.** The extension README gains (1) an **OAuth plumbing section**: how connections work, the shell vars/secrets/KV binding with exact names, how to create the KV namespace and generate the two keys, rotating `TOKEN_ENC_KEY` with `TOKEN_ENC_KEY_PREVIOUS`, retention and the purge procedure (D8, a maintainer script computing the record key from an IMS user id, documented and tested), the privacy note, KV Free-plan limits, and the **"add an OAuth provider" checklist** (implement the `user-oauth` members, classify failures, set `authorizeHosts`, add fixtures, one registry line, pass the suite, add a README section); and (2) a **Dropbox section**: what the provider does and its limits (no folders, original-only rendition, public-link side effect, bandwidth), Dropbox-side setup (D23, scopes, redirect URIs, naming, development vs production), worker vars and secrets by exact name, the optional alt-text property setup, `DROPBOX_ROOT_PATH`, local development (local redirect URI, `DROPBOX_TEST_ORIGIN`), what Disconnect does and does not remove, and "site config keys read: none; no new config-sheet row".

## Testing Decisions

**What makes a good test here.** Assert external behaviour only: given an HTTP request to the worker (fake IMS, fake Dropbox, in-memory KV), assert the response, redirects, cookies, the stored (encrypted) bytes and the requests the fake Dropbox received (method, host class, path, headers, form or JSON body); given an SDK result and a worker stub, assert the DOM and the SDK actions. Never assert on internal helper names or internal call counts. Properties asserted as negatives across every path: **no Dropbox app secret, access token, refresh token, sealed ticket or state, binding nonce or encryption key ever reaches a response, header, redirect, log line or the browser**; **nothing runs before authentication succeeds, except the two sealed public OAuth routes**; **only the browser that began a flow can finish it**; **one author's connection is unusable by any other author**; and, for Dropbox, **the page never contacts a Dropbox API host, no link is created by anything but the detail call, and an existing non-public link is never modified**.

**Proposed seams** (recorded here instead of asked, per #63). The seams are #23's; **this ticket adds no seam**. The one new seam #23 introduced (P1, the provider interface) is what proves "Bynder and Frontify only add provider config".

## Further Notes

- **Dropbox's API answers browser CORS preflights for `https://da.live` (O1).** That makes it technically easy to put an access token into the page and call Dropbox from the browser; the requirement that the browser never receives a credential forbids it, and the e2e host-allowlist check (EO5) and the unit tests for the connect panel make the forbidden shortcut fail loudly.
- **Dropbox refresh tokens do not rotate and do not expire** (D17), so the Dropbox connection is the robust case, but a leaked stored refresh token is a standing credential until revoked. That is why encryption at rest, key separation, the retention TTL, the purge procedure and the real upstream revoke on Disconnect matter, and why they sit in the plumbing, not in the provider.
- **Why Dropbox first proves only half of the plumbing.** Dropbox's non-rotating refresh and form-encoded exchange do not stress the rotation logic (D9 step 5-6) or the stale-read race (D8). The stub OAuth provider does, in CI. What neither can prove is a real rotating vendor's behaviour; that is verified in #24 (Frontify) and #22 (Bynder), which is why the Durable Object decision gate sits before #24 enables a rotating provider.
- **Why not create the link at browse time or insert time.** Browse-time creation would publish every file the author scrolled past; insert-time creation is the right moment but needs a shell step that does not exist. Detail-time creation (D21) is the least intrusive point within the current contract (Open Question 5).
- **EDS and external images.** Whether Edge Delivery Services keeps an external `<img src>` in a DA document, and whether it follows the `raw=1` redirect to `dl.dropboxusercontent.com`, is unverified (carries #23 R13) [ASSUMPTION: kept and rendered as an ordinary external image]; manual step MD6 observes it.
- **The Dropbox docs moved** to https://docs.dropboxapi.com (the old `www.dropbox.com/developers/documentation/http/documentation` page is client-rendered); every API claim cites the stable `.md` page of the new site.
- **#23 and #2 are not built yet** (specs only). Everything here that says "the shell provides" presumes #23 has landed with its contract, and that the template gaps of D15 are approved or wrapped.

**Auth flow (author to worker):** SDK token -> `Authorization: Bearer` -> #2 verification -> `identity.userId` -> record key `hash(userId, "dropbox")`.

**Auth flow (Dropbox connection)** is D7's six steps with Dropbox values: (1) `POST connect` returns `{ beginUrl }`; (2) the click handler opens the pop-up synchronously and navigates it to `beginUrl`; (3) `begin` verifies the ticket, sets the binding cookie, `302` to the Dropbox authorize URL of D17 with the sealed `state` (kept under 2,000 bytes); (4) the author signs in to Dropbox and approves the listed access; (5) Dropbox `302`s to the worker callback with `code` and `state`; the worker verifies state and cookie, exchanges the code with the app secret, requires a refresh token and the full required scope, calls `get_current_account` for the display name, stores the encrypted record and returns the static page; (6) the extension's `session` poll flips to connected. The stored access expiry is `now + expires_in` (about 14,400 s).

**Auth flow (per call):** read and decrypt the record -> refresh if under 60 s remain (single-flight; no rotation to guard for Dropbox) -> call Dropbox with `Authorization: Bearer <author's Dropbox access token>`, never the IMS token -> on `401` force one refresh and retry once -> normalise -> output URL policy -> respond. A second rejection destroys the tokens, writes the reauth marker and answers `409 provider_reauth_required`.

**Disconnect flow:** `POST disconnect` -> refresh if stale -> `token/revoke` (best-effort) -> delete the record -> purge the author's cache entries -> `204`.

## 4. Data contracts

Behaviour contracts, not code.

**Worker API:** D12 (table). **Provider-list item for a `user-oauth` provider:** `{ id, label, credentialKind: "user-oauth", connection: { state, account? }, capabilities }`; `state` is `connected` (a record with tokens exists), `not_connected` (no record, expired record or undecryptable record) or `reauth_required` (reauth marker); `account` carries `displayName` only.

**Connect response:** `{ beginUrl }` (origin = `PUBLIC_WORKER_ORIGIN`; query = the sealed ticket). **Session response:** `{ connection: { state, account? } }`.

**Dropbox capabilities:** `assetTypes: [image, video, document, audio]`; `sorts: modified (default), relevance (requires a query)`; `window: 300`; `assetIdPattern: ^id:[A-Za-z0-9_-]{1,128}$` [ASSUMPTION: charset, MD3]; `outboundHosts: [api.dropboxapi.com, content.dropboxapi.com]`; `authorizeHosts: [www.dropbox.com]`; `deliveryHosts: [www.dropbox.com]`; `cacheSeconds: 30`; `scopes`: D18; `maxStateBytes: 2000`; `requiresRefreshToken: true`.

**Summary (search items):** `id` = the Dropbox file id (`id:...`); `provider: dropbox`; `name`; `type` by the extension table; `thumbnailUrl` = `data:image/<jpeg|png|webp>;base64,...` of at most 64 KB (or absent: fallback, unsupported format, over 20 MB, conversion failure); `extension`; `fileSize` (`size`); `dateModified` (`server_modified`); `width`/`height` **omitted** (Dropbox returns no `media_info` in search or list results); `warnings: []`.

**Detail:** the summary plus `width`/`height` (when `media_info` is ready), `tags: []`, no `description`/`copyright`, `alt { value, source: property | name | none }`, `renditions: [ { id: "original", label: "Original (<size>)", url, kind: original, width?, height? } ]` (empty when there is no usable public link), `defaultRenditionId: "original"`, `insertable { ok, reason? }`, `linkUrl?` (non-image files: the link as Dropbox returned it).

**`insertable.reason` (fixed strings, never upstream text):** "Dropbox does not allow a public link for this file"; "The existing link for this file is not public"; "The existing link for this file needs a password or has an expiry date"; "This file cannot be shown as an image in a browser"; "This file cannot be downloaded"; "Sign-in with a verified Dropbox email is required to share this file".

**Dropbox-to-shell error map** (D17, D22):

| Dropbox | Shell outcome |
|---|---|
| browse `401` `invalid_access_token` / `expired_access_token` | *reauth required*: shell refreshes once and retries; a second rejection -> tokens destroyed, marker written, `409 provider_reauth_required` |
| browse `401` `missing_scope` / `user_suspended` | same path (reconnect re-requests scopes; suspension is temporary) |
| `403` `no_permission` and team access errors | forbidden mapping |
| `409` `path/not_found` | `404 not_found` |
| `409` link-creation errors | `200` detail with `insertable.ok=false` and a fixed reason |
| `429` (`too_many_requests`, `too_many_write_operations`) | `429 rate_limited` + `Retry-After` |
| `5xx`, network | `502 upstream_unavailable` |
| token endpoint `400 invalid_grant...` | *reauth*: tokens destroyed (after the re-read, D9), marker written, `409 provider_reauth_required` |
| token endpoint `400 invalid_client...` or any other `400` | *misconfigured*: `500 misconfigured`, record kept |
| token endpoint `5xx`, network | *transient*: retried (refresh only), `502`, record kept |

**Stored connection record** (D8; encrypted envelope): `{ v, accessToken, accessExpiresAt, refreshToken, scope, account: { displayName, id? }, connectedAt }`, or `{ v, reauth: true, account, at }`. KV key `conn:v1:` + hash(userId, provider); AES-256-GCM, random IV per write, key id in the envelope, authenticated data = the KV key; KV expiry `CONNECTION_TTL_DAYS`. The Dropbox refresh token is stored once and **not rewritten on refresh** (only `accessToken` and `accessExpiresAt` change).

**Sealed values:** *ticket* `{ purpose, userId, provider, exp }` (about 60 s); *state* `{ purpose, provider, userId, nonceHash, exp }` (about 10 min); both AES-256-GCM under HKDF subkeys of `OAUTH_STATE_KEY`, label-separated, base64url.

### 1.2 Token store and isolation (AC2, AC3, AC7)

| ID | Behaviour asserted |
|---|---|
| TS1 | The raw KV dump (keys and values) contains none of: access token, refresh token, IMS user id, account name; values are envelopes (version, key id, IV, ciphertext); keys are `conn:v1:` + a hash |
| TS2 | A record copied to another user's key (or another provider's) fails authenticated decryption -> not connected; logged by outcome only; no exception reaches the caller |
| TS3 | A record written under the previous key is readable when `TOKEN_ENC_KEY_PREVIOUS` is set and is re-encrypted under the current key on its next write; with neither key it reads as not connected |
| TS4 | User A connected; user B's `session` is `not_connected`; B's browse -> `409 provider_not_connected`; B's request never causes a provider call with A's token; the same user's records for two providers are mutually invisible |
| TS5 | `disconnect` deletes the record; repeating it is `204`; the next browse -> `409 provider_not_connected` |
| TS6 | Retention: every write carries a KV expiry of `CONNECTION_TTL_DAYS` (default 180; a custom value honoured; an invalid value fails registration naming the setting); an expired record reads as not connected; reads do not extend the expiry (write log) |
| TS7 | **Reauth marker:** after a definitive failure the access and refresh tokens are absent from the KV dump (only the marker remains), the provider list reports `reauth_required` with the account label, a successful connect overwrites the marker and Disconnect deletes it |
| TS8 | The orchestration uses only `get`/`put`/`delete`: a second storage implementation (an in-memory map) and the stale-read double pass the same suite, proving the store is swappable (the Durable Object path) |
| TS9 | Start-time validation: `TOKEN_ENC_KEY`, `TOKEN_ENC_KEY_PREVIOUS` or `OAUTH_STATE_KEY` that is not a base64 32-byte value fails the start naming the setting and never its value; identical values in `TOKEN_ENC_KEY` and `OAUTH_STATE_KEY` fail (key separation) |
| TS10 | Purge: the maintainer script, given an IMS user id and a provider id, prints the record key; deleting that key makes the user `not_connected`; the script never prints tokens or reads secrets |

| RF3 | A refresh result **without** a refresh token keeps the stored one byte-identical (Dropbox, `stub-oauth-b`); a result **with** one replaces it (`stub-oauth-a`) |

| RF6 | Refresh answers *reauth*-class: storage is **re-read first**; with nothing newer the tokens are destroyed, the marker written and `409 provider_reauth_required` returned, and the next call answers `409` with **no upstream call**; refresh answers *misconfigured*-class -> `500 misconfigured`, record kept, no marker, no reconnect prompt |

| RF9 | **Rotation under stale reads:** isolate A refreshes `stub-oauth-a` and writes; isolate B reads the stale record (old refresh token); the stub rejects the reused token -> B re-reads (still stale) -> graceful outcome: at most one refresh attempt from B, the marker is written, no loop, and **reconnecting works** (the documented residual risk R5); after the stale window B reads the new record and succeeds |

1. **Plumbing is shell work inside #25 (D1, R21; carried from #23 Question 1).** Confirm the reading: #25 adds the provider-agnostic OAuth host to the shell (routes, token store, refresh, connect panel, additive interface members) as Phase A, and the Dropbox module as Phase B, whose diff touches only the provider folder, the registry, wrangler vars, `.dev.vars.example` and the README. Also confirm the additive members of D5 (`authorizeHosts`, `callbackCodeParam`, `maxStateBytes`, `requiresRefreshToken`, the normalised token result and the three OAuth failure classes) as acceptable extensions of #23's interface.
2. **Template gaps OG1-OG4 and #23's TG2/TG3 (D15, R2).** Approve as #2 additions (OG1 explicit public routes with a custom authenticator, which amends #2 Decision 4's "no unauthenticated routes except preflight"; OG2 an optional KV binding; OG3 per-request dynamic redaction; OG4 HTML responses with custom headers and extension-defined error codes), or accept a thin wrapper in this worker that reuses the template's exported helpers? Is a configured provider with missing OAuth plumbing correctly a **failed start**, while a Cloudinary-only deployment stays untouched (D4)?
3. **Token store (D8, R5, R19).** Accept Workers KV (encrypted records, retention TTL, simplest) now, with the store behind an interface? KV is eventually consistent and cannot serialise refreshes across isolates, which is harmless for Dropbox (non-rotating) but a residual risk for Frontify's single-use rotating tokens (verified in the Frontify docs). Do you want to decide **now** that the store is a Durable Object (stronger, but adds a class, a migration and a template change), or keep KV and decide before #24 enables a rotating provider? Is the Paid plan acceptable (the Free plan allows 1,000 KV writes per day, about 150 active authors for Dropbox)? Is the unkeyed record-key hash (D6) acceptable?
4. **Policy and privacy (R4).** Storing third-party OAuth refresh tokens linked to Adobe user ids in a Cloudflare account that, per #1 R1 and #2 R1, may be personal raises the outside-activity/IP question and a data-protection question. Which account, who signs off, and is the **180-day idle retention** and the purge procedure acceptable (D8)? Should the README ship the retention statement before any real user data is stored?
5. **When a public link is created (D21, R7).** This spec creates (or reuses) the public link when the author opens a file's detail pane, because the shell has no "prepare for insert" step. Authors who only look at a file still publish a link to it. Accept, or amend #23's interface with an insert-time hook (a new provider method and one extra worker call at Insert)? Is creating public Dropbox links from an Adobe-authored tool acceptable under your policy, and should link creation be switchable off per deployment (read existing public links only)?
6. **API vs Chooser, and online-only tokens (D3).** Confirm building the full OAuth provider rather than the much cheaper Chooser (no worker, no OAuth, no production approval, what Contentful ships). Also confirm that Dropbox's own recommendation of online-only tokens for server apps that act only during user interaction is rejected, because the criterion requires stored and refreshed tokens. The Chooser needs no review at any audience size; the API route commits you to Dropbox's production-approval path above 50 linked users.
7. **Dropbox app ownership, naming and policy (D23, R12).** Who owns the Dropbox app (a personal or a company developer account)? Proposed name "EW Multi-DAM Picker" (it may not contain "Dropbox"; fixed once in production). Is the audience likely to exceed 50 Dropbox users (then production review, a privacy policy and branding assets are needed), and have you read Dropbox's developer terms (https://www.dropbox.com/developers/reference/tos; not read here) regarding serving published pages through shared links?
8. **Business teams and Team Space (D24, R11).** Brand folders are often team folders, invisible without the path-root header. Is v1 (home namespace only) acceptable, or should `root_namespace_id` support ship in this ticket? Also confirm the browse model: a configured root folder, a non-recursive empty-search view (newest first within a scan window), no folder navigation.
9. **Alt text and metadata (D21, R10).** Dropbox has no description or alt field. Accept "file property (if your team defines a template), else the cleaned file name, always editable"? Which template and field name would you use, or do you want a different convention (sidecar naming, embedded EXIF/IPTC) as a follow-up?
10. **Hotlinking limits and the ingest alternative (R8).** Dropbox links are bandwidth-capped (20 GB and 100,000 downloads per day on Basic) and depend on the link staying alive. Accept "staging and low-traffic use, documented", or do you want a follow-up ticket that copies the picked file into DA/EDS media at insert time (robust, needs DA write APIs, changes what "insert" means)?

Who creates and owns them? Without them MD1-MD10 and the real fixtures are blocked and the docs-derived fixtures stay unverified.
