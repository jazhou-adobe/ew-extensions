## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party) and, after #23, from Cloudinary, but many teams, especially small marketing teams, agencies and regional offices, keep working brand assets in **Dropbox**. Today an author who wants a Dropbox image leaves EW, finds the file, creates a shared link, edits the link by hand so that it renders instead of showing Dropbox's preview page (`dl=0` -> `raw=1`), pastes it and retypes alt text from the file name. Nothing checks that the link is public: a team-only or password-protected link looks fine in the editor and is a broken image for every visitor.

Dropbox is also the **first vendor that authenticates the individual author**, and that is the larger problem. The picker so far (#23) uses one service credential held by the worker; every author sees the same assets. Dropbox, like Bynder and Frontify, decides what each person may see through OAuth on behalf of that person. That needs four things the picker does not have: a way for an author to **connect and disconnect from inside the library iframe**, a **callback that cannot carry an IMS token** (a browser redirect from dropbox.com has no `Authorization` header) and must therefore be made safe in another way, a **server-side store for long-lived refresh tokens** that are encrypted at rest and never reach the browser, and **refresh logic** that keeps short-lived access tokens fresh without prompting the author. The extension code is public, so none of this can live in the browser.

The platform adds its own constraints. App Builder State is shared by every worker in a workspace and Adobe "strongly discourage[s]" keeping secrets in it (https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/security/, "Known issue 1"), while #2 Decision 10 deliberately kept long-lived credentials and refresh tokens out of State until an encrypt-before-store scheme or a vault is decided; the callback is served from a shared `adobeioruntime.net` host; and the platform's built-in Adobe auth annotation, which #2 may adopt, would reject an unauthenticated browser redirect. This ticket must make the decisions the template deferred, and make them once.

If each of the three OAuth DAMs (Dropbox, Bynder, Frontify) wrote this itself, the security-critical parts (state handling, login-CSRF defence, encryption, refresh races, revocation) would be written three times and drift. This ticket must therefore build the plumbing **once, provider-agnostically**, proven by more than one OAuth shape (Dropbox's non-rotating form-encoded tokens and a stub that behaves like Frontify's single-use rotating JSON tokens), so that #22 and #24 are a module and a registry line.

Finally Dropbox is the least DAM-like vendor of the four. It has no rendition URLs, no description or alt-text field, no tags, no type facet, thumbnails that are binary API responses rather than URLs, folder-first navigation instead of a flat asset bank, and cursor-only search paging. Those differences, not the OAuth mechanics, are the real work of the provider half and are decided below.

## Solution

The existing **Multi-DAM Picker** library plugin gains a second provider, **Dropbox**, and the ability to host providers whose credential kind is `user-oauth`. When more than one provider is configured the author sees the shell's source switcher. Choosing *Dropbox* for the first time shows **Connect to Dropbox**: a pop-up to dropbox.com where the author signs in with their own Dropbox account (personal or work, including company SSO) and approves read access and link creation. The panel then shows "Connected as <name>" with a **Disconnect** action and the author's files: a thumbnail grid with file names, searchable by file name and content, filterable by type (images, videos, documents, audio), sortable (newest, relevance when searching), with "Load more". Selecting a file opens a detail pane with name, dimensions (photos), type, size, an alt text prefilled from a configured Dropbox file property if the team uses one else from the file name (editable, or "decorative"), and one rendition: the file itself through a public Dropbox link. **Insert** places an `<img>` with that URL and the alt text at the cursor and closes the library; non-image files insert as a link with the file name as text. Files that cannot be used (the sharing policy forbids a public link, the existing link is password-protected or expiring, the format cannot be shown by browsers) are shown as not insertable with a one-line reason. If Dropbox access is later revoked, the panel shows **Reconnect** instead of a cryptic error.

Behind it, the existing worker (the App Builder app `apps/multi-dam-picker/worker/`, package `multi-dam-picker`), extended, does everything sensitive. Its `api` web action keeps the template contract (every call needs a verified IMS token) and gains the connect, session and disconnect routes. A second web action, `oauth`, serves only the two browser-navigation routes `begin` and `callback`: it starts the Dropbox authorization-code flow with `token_access_type=offline`, protects the callback with a **sealed, expiring state plus a browser-binding cookie** (so only the browser that started a flow can finish it), exchanges the code with the app secret, stores each author's tokens **encrypted at rest in State, keyed by a hash of the author's verified IMS identity**, and shows a static result page. The `api` action refreshes the four-hour access token silently (serialised across containers by a State lock), injects the author's own access token into every Dropbox call, and on Disconnect **revokes the grant at Dropbox** before deleting the stored copy. The browser only ever holds its own IMS token and normalised asset data. The plumbing knows nothing about Dropbox: the provider supplies HTTP mappings (authorize URL, code exchange, refresh, account name, revoke) and the browse methods; a later provider adds the same and nothing else.

## Implementation Decisions

(No file paths or code, except endpoint names and wire contracts, which are API contracts. Layout is in the Build Analysis. Template contracts are referenced as "#2 Decision N"; shell decisions as "#23 DN".)

**D1. Scope and delivery split: shell plumbing first, provider second, in one ticket.** The ticket delivers (A) the OAuth plumbing in the shell (worker core and browser panel) and (B) the Dropbox provider module. This is the reading of #25's criteria carried from #23: "no changes needed in the extension shell beyond registering the provider" holds for the **provider** (B) and for every later provider; the plumbing (A) is itself #25's first deliverable and is by necessity shell work [OPEN: Question 1]. The ticket is built and reviewed in two phases so that the criterion is checkable: **Phase A** (plumbing) lands and is verified with vendor-neutral stub `user-oauth` providers before any Dropbox app exists; **Phase B** (Dropbox) is a diff that touches only the provider folder, one registry line, the worker's app-config inputs and `.env.example`, the README section and the conformance-suite registration (enforced by repo check RO2).

**D2. Surface and registration unchanged.** Library plugin only; the one `library` row from #23 is unchanged; **no new config-sheet row and no new entry page**; **site config read: none**, and the README says so. Dropbox appears in the existing panel when its worker configuration is present (#23 D5, D20).

**D3. Build against the Dropbox HTTP API, not Dropbox's Chooser drop-in.** The Chooser (https://docs.dropboxapi.com/dropbox-api/docs/pre-built-components/chooser.md) is cheaper (no worker, no OAuth, no production approval) and is what Contentful ships (O5). It is rejected: (a) #25's criteria require per-user OAuth through the worker with tokens stored and refreshed server-side, and the Chooser authorises in the browser on dropbox.com's own session; (b) it brings its own picker UI, which the capability-driven shell cannot drive, so it would need browser code and break "provider module only"; (c) it needs the hosting domains registered in the Dropbox app, and EW iframes pages from three host families plus `localhost` (#2 Decision 8). Dropbox's own guide steers pickers to the Chooser ("Requesting Full Dropbox access to pick a file when you could use the Chooser isn't a good use of the permission", https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md [VERIFIED*]); the cost of this choice is the production-approval path (D23). **A second alternative is recorded: online-only tokens.** Dropbox's OAuth guide recommends, for "a server-side web application that only calls the Dropbox API as users interact with it", the code flow with short-lived tokens only and no refresh tokens (https://docs.dropboxapi.com/dropbox-api/docs/oauth.md, summary table [VERIFIED*]); an expired token then re-runs the redirect, which needs no user input while their Dropbox session and approval are valid. That would remove stored refresh tokens but contradicts #25's "tokens are stored and refreshed server-side", would make every four-hour expiry a pop-up, and would not generalise to Bynder and Frontify, so it is not chosen [OPEN: Question 6].

**D4. Turn on the `user-oauth` credential kind; enablement rule.** #23 D4 defines `user-oauth`, validates a stub declaration and fails the registry build when a provider declares a kind not in the "hosted kinds" set (`{service}`). This ticket adds `user-oauth` to the set **together with everything #23 D4 lists**: the connect/session/disconnect routes, the two public OAuth routes (now served by the `oauth` action, D7), the encrypted token store, refresh orchestration and credential injection, and the browser connect panel. Conformance test PC5 ("defined but not hosted") is **retired and replaced** by the tests of this ticket. **Enablement rule:** the OAuth plumbing is *enabled* when the shell inputs `TOKEN_ENC_KEY`, `OAUTH_STATE_KEY` and `OAUTH_PUBLIC_BASE_URL` are present and non-empty (State needs no binding: it uses the action's implicit Runtime credentials and the template's `STATE_REGION`). A `user-oauth` provider is *configured* when its own required inputs and secrets are non-empty (#23 D5: otherwise it is omitted, its routes answer `404 not_found`, and the action still works for the other providers). If a `user-oauth` provider is fully configured but the plumbing is not enabled, **the registry build fails** with a message naming the missing items (never their values): the `api` action then answers every `/dam/*` request after authentication with `500 misconfigured` (#23 D3 behaviour), and the same validators run in the pre-deploy guard (#2 Decision 16, #23 D22) so that a deploy is refused before it ships. The admin clearly intended to use the provider; a silently missing Dropbox is a debugging trap. The shell-owned secrets must be **optional** at deploy time, because a Cloudinary-only deployment (#23) must keep deploying unchanged: the #2 guard fails a deploy when any referenced `$NAME` is empty, so an "optional `$NAME`" marker is needed (#23 TG2; Open Question 2). An empty input means "absent", never "empty value".

**D5. Interface additions (additive, optional, defaulted).** #23 D3 fixes the `user-oauth` members: `scopes`, `buildAuthorizeUrl(state, redirectUri)`, `exchangeCode(code, redirectUri)`, `refresh(refreshToken)`, `accountName(credentials)`, optional `revoke(credentials)`, optional maximum `state` length, with the shell owning state sealing, cookies, token encryption and storage, refresh orchestration and credential injection. The plumbing pins the behaviour of those members and adds the following **optional members and normalised shapes**; none changes an existing member, and a provider that omits them gets the default:

| Item | Behaviour |
|---|---|
| Token result of `exchangeCode` and `refresh` | the provider returns a normalised result: `accessToken`, `expiresInSeconds`, optional `refreshToken`, optional `scope` (string), optional `accountId`. The shell stores what it is given: a refresh result **without** `refreshToken` keeps the stored one (Dropbox); one **with** it replaces the stored one (Frontify-style rotation). An absent `expiresInSeconds` is treated as the shell default of 3600 s [ASSUMPTION: Bynder, Frontify always send it; confirmed in their tickets] |
| Failure classes of the OAuth calls | each of `exchangeCode`, `refresh`, `accountName`, `revoke` fails with exactly one of: **reauth** (definitive: the grant is invalid or revoked), **transient** (retry later, keep the record), **misconfigured** (client id/secret/redirect problem: keep the record, generic failure). An unclassifiable failure is **misconfigured**, never reauth, so a vocabulary surprise can never delete a working connection |
| `authorizeHosts` (required for `user-oauth`) | the hosts `buildAuthorizeUrl` may point at (a top-level navigation target, not an outbound call). The shell refuses to redirect anywhere else: an https URL, host in the list (loopback only when the template's local-origin list is non-empty), the supplied `state` and `redirect_uri` present byte-for-byte, no client secret anywhere in it. This closes an open-redirect and secret-in-URL class for every provider |
| `callbackCodeParam` (optional, default `code`) | the query parameter carrying the authorization code on the callback (Frontify's page shows `authorization_code`, https://developer.frontify.com/document/68#/get-started/authentication-1 [VERIFIED*]) |
| `maxStateBytes` (optional, default 2000) | the provider's limit on `state`; Dropbox documents 2,000 bytes. The shell checks the sealed state against it at `connect` time and refuses (generic failure) rather than truncating |
| `requiresRefreshToken` (optional, default true) | the shell refuses to store a connection whose first token result lacks a refresh token (a connection that cannot refresh is never kept) |
| `rotatesRefreshToken` (optional, default true) | whether a refresh result may replace the refresh token (Frontify-style single-use rotation). It decides one thing only: whether the shell may proceed with an **unlocked** refresh when the refresh lock cannot be acquired in time (D9 step 3). Dropbox declares `false` |
| Required scope check | when the first token result carries `scope`, the shell requires it to contain every scope in `scopes`; otherwise the connection is refused. When it is absent the check is skipped |
| Per-call context for `user-oauth` | the credentials (`accessToken`, `scope`, account), the proxy helper pinned to `outboundHosts`, config, secret accessor, injected clock. **Never the IMS token, the inbound `Authorization` or cookies** (PC7). The provider applies the access token to its own outbound calls |
| "Token rejected" signal | a provider reports an upstream authentication failure from `search`/`getAsset` as the existing failure class **reauth required**. The shell treats the first such failure of a call as "access token rejected": it forces one refresh and retries once; a second one makes the connection `reauth_required` (D9). The provider never refreshes or stores tokens itself |

**D6. Connection identity and record key.** A connection belongs to the **verified IMS `userId`** (`identity.userId`, #2 Decision 5), never to anything the client sends; different EW users never share a connection, the same user shares one connection across browsers and sessions. The record key is `conn.v1.` + the URL-safe base64 of SHA-256 over `userId`, a separator and the provider id (only characters that State accepts: alphanumeric, `-`, `_`, `.` [VERIFIED: application-state page, "Constraints"]); the template's store prefixes it per worker. The key is also bound into the ciphertext as authenticated data (D8). **The raw IMS user id is never stored or sealed anywhere**: the ticket and the state carry this hash (D7), so a sealed value, a State listing or a log line cannot reveal it. The hash is deliberately **unkeyed**, so a party with State read access could test a guessed user id for membership. Accepted: State access already shows ciphertext, and a keyed hash would either tie record lookup to a rotating secret or add a third permanent secret [ASSUMPTION: acceptable; Open Question 3]. [ASSUMPTION: the IMS `user_id` claim is the same for the shell token and the library token of one person; carried from #2 R7 and #23 R15; confirmed in manual step MD7.]

**D7. The connect flow: ticket, begin, sealed state, binding cookie, callback; two web actions.**

*Why a second web action.* The browser redirect from dropbox.com cannot carry an `Authorization` header, so two routes must answer without an IMS token. #2 Decision 7 says the `api` action has no unauthenticated routes other than `OPTIONS` preflight (so that a bare request gets `401`, the liveness signal, and so that an unauthenticated probe learns nothing), and the platform annotation `require-adobe-auth`, which #2's spike S0 may adopt, rewrites an action into a sequence whose validator rejects every request without a valid bearer token [VERIFIED: https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/security/, "Authentication and authorization handling"]. Both rule out putting the redirect routes inside `api`. **Decision: the worker's app config declares two raw web actions in the one package `multi-dam-picker`: `api` (unchanged contract) and `oauth` (this ticket), whose only routes are `GET /{provider}/begin` and `GET /{provider}/callback`.** The `oauth` action is built by a template factory variant that runs the #2 pipeline without IMS authentication and with a per-route sealed-value authenticator (gap OG1). It sets the same raw web mode, `web-custom-options` annotation (so the platform adds no `Access-Control-Allow-Origin: *`) and explicit timeout as `api`, and **never** the `require-adobe-auth` annotation. This amends #2 Decision 4 ("one action per extension") deliberately and narrowly; the fallback if the owner rejects a second action is to register the same two handlers as public routes of `api` through an explicit route option (OG1), which forbids `AUTH_MODE=platform` for the worker and weakens #2's "bare request gets `401`" signal [OPEN: Question 2]. #23 reserved `/oauth/{provider}/begin|callback` under the `api` base; with this decision `api` simply does not route them, so #23's SH2 (no token `401`, token `404`) still holds unchanged.

*URLs.* `OAUTH_PUBLIC_BASE_URL` (an input, one value per workspace, known only after the first deploy) is the `https://<namespace>.adobeioruntime.net/api/v1/web/multi-dam-picker/oauth` base [ASSUMPTION: URL form, as #2 Decision 15; confirmed by `aio app get-url` in spike S-OA]; the routes are `{base}/{provider}/begin` and `{base}/{provider}/callback`; the redirect URI registered with Dropbox is exactly `{base}/dropbox/callback`. The base is configuration, **never derived from `Host` or forwarded headers**; it is validated at registry build (https, host ending `.adobeioruntime.net`, expected path suffix; an `http` loopback base is accepted only when the template's local-origin list is non-empty, which the guard forbids on Production).

*The six steps.*
1. `POST /dam/{provider}/connect` (`api`, IMS-authenticated) returns `{ beginUrl }`, whose origin is the configured `OAUTH_PUBLIC_BASE_URL` and which carries a **ticket**: a sealed (AEAD) payload `{ purpose: ticket, connKey, provider, exp ~60 s }` where `connKey` is the D6 hash.
2. The click handler opens a pop-up synchronously and navigates it to `beginUrl` (D13). The browser checks that `beginUrl`'s origin equals the worker's origin before navigating (UO2).
3. `GET {base}/{provider}/begin?ticket=` (`oauth`, public) verifies the ticket, generates a random **nonce**, sets the **binding cookie** carrying the nonce, and `302`s to the provider's authorize URL (validated per D5) with `state` = a sealed payload `{ purpose: state, provider, connKey, SHA-256(nonce), exp ~10 min }`. The response is `statusCode 302` with the target in `headers.location` and the cookie in `headers['Set-Cookie']`, the two result shapes the platform documents [VERIFIED: https://github.com/apache/openwhisk/blob/master/docs/webactions.md, redirect and cookie examples]; that the Adobe gateway passes both through unchanged is [ASSUMPTION: confirmed in spike S-OA].
4. The author signs in at the provider and consents.
5. The provider `302`s to `GET {base}/{provider}/callback?code&state` (`oauth`, public). The action (a) answers `405` to anything but `GET`; (b) on a provider `error` parameter shows the generic failure page, reflects nothing and makes no token call; (c) unseals `state` (expiry, purpose, provider equal to the path); (d) requires the cookie nonce to hash to the value in `state`; (e) exchanges the code once with the provider's mapping (client secret from the secret accessor); (f) validates the token result (refresh token present, scope check, D5); (g) fetches the account name; (h) writes the encrypted record; (i) clears the cookie and returns the static result page. Any failure before (h) stores nothing, leaves an existing record for the user untouched and returns the **same** generic failure page for every cause (no oracle).
6. The extension polls `GET /dam/{provider}/session` (`api`, IMS-authenticated) until `connected` (D13).

*Why the cookie.* Without it an attacker could start a flow with their own IMS token and trick a victim into completing the consent in the victim's browser, silently linking the victim's Dropbox to the attacker's EW identity (login-CSRF / account linking). With it only the browser that began the flow can finish it. The cookie is a first-party cookie of the `<namespace>.adobeioruntime.net` host: the pop-up is a top-level browsing context, and `SameSite=Lax` cookies are sent on the cross-site top-level `GET` navigation from dropbox.com back to the worker [VERIFIED*: MDN `Set-Cookie`: `Lax` cookies are sent on cross-site requests that are a top-level navigation and use a safe method]. Attributes: `HttpOnly`, `SameSite=Lax`, `Max-Age` at most 600 s, `Path` equal to the `oauth` base path (so it is sent only to `begin` and `callback`), no `Domain` (host-only), `Secure` except for the loopback test base (a `Secure` cookie is sent only over `https:` [VERIFIED*: MDN `Set-Cookie`, `Secure`]). **Shared-host caveat [INFERENCE]:** every worker of the workspace is served from the same namespace host, so another worker's pages share this cookie jar; `Path` is not a security boundary. The cookie holds only a one-time binding nonce, never a credential, and an attacker who can already run code on that host is outside this threat model (R25). The state and ticket are **stateless** (sealed, no State record): a pending-flow record would cost State operations per click for no gain; replaying a callback URL is harmless because the provider's code is single-use [ASSUMPTION: Dropbox codes are single-use; the second exchange fails upstream, OA9, and the record from the first stays intact]. Sealing is AES-256-GCM (Node `crypto`, no new dependency) under keys derived (HKDF) from `OAUTH_STATE_KEY` with distinct labels for ticket and state, so a ticket can never be accepted as a state or the reverse. The sealed state appears in the `Location` header of the `begin` activation result, which Runtime keeps for seven days [VERIFIED: #2 system-settings facts; ASSUMPTION that web-action results are stored in the activation record]; it expires after ten minutes and is bound to the cookie nonce, so a stored copy is useless. Tokens never appear in any action result.

**D8. Token store: encrypted at rest in App Builder State behind the template's store interface (the decision #2 deferred).** #2 Decision 10 keeps refresh tokens and other long-lived credentials out of State "until the owner decides on a vault or an encrypt-before-store scheme". **This spec proposes encrypt-before-store and asks for approval** (Open Question 3), because a vault is not part of the documented App Builder surface this repo can reach (the security page says "use a Secret Vault" without naming a product [VERIFIED: security page]) and the alternatives are worse: `aio-lib-files` has no TTL, so no retention (#2 Decision 10), and the App Builder database library is out of #2's scope.

The record is `{ v, accessToken, accessExpiresAt, refreshToken, scope, account: { displayName, id? }, connectedAt }` for a connected state, or a **reauth marker** `{ v, reauth: true, account: { displayName }, at }` after a definitive failure (D9): tokens are destroyed but the account label is kept so the panel can say "Reconnect (was connected as ...)" and the provider list can report `reauth_required` (the third `connection.state` of #23 D4). Records are sealed with **AES-256-GCM** under the action input `TOKEN_ENC_KEY`, fresh random IV per write, key id in the envelope, **authenticated data = the full State key**, so a record copied to another key fails to decrypt (treated as not connected, logged by outcome only). Because State is **one container per workspace shared by every action in the namespace** ("Parameters set in State are shared among actions running within the same namespace" [VERIFIED: security page, Known issue 1]; "isolated in a 'State container' which maps to your I/O Runtime namespace and application Workspace" [VERIFIED: application-state page]), another worker of the same workspace can read this ciphertext but not decrypt it: the key exists only as an encrypted input of this worker's actions. An optional `TOKEN_ENC_KEY_PREVIOUS` lets rotation avoid forcing every author to reconnect: reads try the current then the previous key and writes re-encrypt under the current one. The envelope is JSON-serialised into the string that State requires (values are strings only, at most 1 MB [VERIFIED]); the store interface is the template's (`get`, `put` with TTL, `delete`) **plus two conditional writes (gap OG2): `putIfAbsent` and `putIfPresent`**, which map to the library's `ifNotExists` and `ifExists` put options [VERIFIED: https://github.com/adobe/aio-lib-state/blob/main/doc/api.md, `AdobeStatePutOptions`, and the 5.4.0 package source; a conditional put resolves to `null` when its condition is not met]. **Retention and TTL:** State's TTL defaults to **one day** when none is given and is at most 365 days (`MAX_TTL`) [VERIFIED: application-state page and api.md], so a connection write that forgets the TTL would silently expire in 24 hours; **every connection-record write therefore passes an explicit TTL of `CONNECTION_TTL_DAYS`** (default 180, validated to at most 365), so an idle author's stale refresh token disappears (an active author rewrites the record at least every access-token lifetime; Dropbox: every four hours). An expired record reads as not connected; the Dropbox grant stays listed in the author's own connected apps (README says so) [OPEN: Question 4]. **Limits** [VERIFIED: https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/storage/, read 2026-11-18]: per workspace 200 MB (1 GB Production), bandwidth 2 MB/min (10 MB/min Production), storage counted as twice the key size plus the value size; `get`/`put` may answer `429` (rate limit) or `403` (storage limit), which the template maps to `503 store_unavailable` (#2 Decision 10). A record is about 1-2 KB, so capacity is not a constraint; bandwidth is the one to watch (every browse reads one record, each connect poll reads one, D13) and R19 does the arithmetic. **Consistency:** the State page names only `list` as "not strongly consistent" (a replica read with about 5 ms lag) [VERIFIED]; it does not state read-your-writes for `get` across containers [INFERENCE: point reads and writes are strongly consistent; OPEN: confirmed in spike S-OA, and the tests keep a stale-read double so the design does not depend on it]. **Region:** the template's `STATE_REGION`; `apac` stores data in Japan, `amer` in the US [VERIFIED: application-state page], which matters for a store of third-party refresh tokens (Open Question 4). The store is behind an interface so a different backing service can replace State without touching providers or the orchestration. The **purge** is `aio app state delete <key>` run from the worker folder for the computed key (D27) [VERIFIED: the `aio app state` command list above].

**D9. Refresh orchestration (provider-agnostic), with a State lock.** Per call to `search`/`getAsset`: read and decrypt the record; if the `reauth` marker or no record -> `409 provider_reauth_required` / `409 provider_not_connected` before any provider call.
1. **Proactive:** if fewer than 60 s remain on the access token, refresh first.
2. **In-container single flight:** concurrent refreshes of the same record inside one warm container share one provider call (a container may run up to 200 activations concurrently [VERIFIED: #2 Decision 10 citing the throughput-tuning page]); no user-specific data is kept in module memory beyond the in-flight promise map keyed by connection.
3. **Cross-container lock:** the refreshing request first takes a lock `lock.v1.<connKey>` with `putIfAbsent` (value = a random owner id, TTL about 20 s, under the 25 s action timeout [ASSUMPTION: State accepts a TTL this short; minimum TTL is undocumented, OPEN, spike S-OA]). If acquired: **re-read the record** (another container may have refreshed while we waited), refresh only if it is still stale, write the result, release the lock (delete if the value is still ours). If not acquired: poll the record every ~250 ms for up to ~5 s (bounded by the invocation deadline) and use it as soon as it is fresh; when the wait ends, a provider with `rotatesRefreshToken: false` (Dropbox) proceeds with an unlocked refresh (idempotent for it), any other provider answers `502 upstream_unavailable` with `Retry-After` and **never** refreshes without the lock (a second use of a single-use refresh token could burn the connection). Together with the re-read this closes most of the rotation race that a plain per-container single flight leaves open across Runtime containers; it is not a transaction (State has no compare-and-swap on a version) and the residual cases are step 7.
4. **Reactive:** if the provider reports *reauth required* from a browse call, force exactly one refresh (through steps 2-3) and retry the browse call once; a second *reauth required* is definitive.
5. **Store the result:** `accessToken` and expiry always; the refresh token is replaced only when the result carries one (D5). The write is `putIfPresent` with the retention TTL: if the user disconnected while the refresh was in flight, the conditional write is a no-op and the record is **not resurrected**.
6. **Failure classes:** *reauth* from `refresh` -> **before destroying anything, re-read the record**; if storage now holds a newer record (another container won), use it; otherwise destroy the tokens, write the reauth marker and answer `409 provider_reauth_required`; *transient* -> the template's retry schedule applies only where the call is declared safe to retry (the refresh grant is for Dropbox, D22), then `502 upstream_unavailable`, **record kept**; *misconfigured* -> `500 misconfigured`, record kept, no reconnect prompt, a log line naming the provider and class only.
7. **Write failure after a successful rotating refresh** (the provider already invalidated the old refresh token): retry the write once, keep the new record in container memory for the container's lifetime (keyed by connection, dropped on disconnect) and log the event; if every attempt fails the next container finds the old, now-invalid token and the author reconnects (documented residual risk R5, also reachable if the lock TTL expires before the write; absent for Dropbox, whose refresh token never changes).

The orchestration is identical for every provider; Dropbox exercises the non-rotating path and the stub exercises rotation (D17, tests RF1-RF13).

**D10. Credential injection and redaction.** The shell hands the provider the author's credentials through the per-call context; the provider sets the `Authorization: Bearer <author's access token>` header on its outbound calls through the pinned proxy helper (the explicit per-call auth form, not a named secret: the token is not an action input). The IMS token is never forwarded, never stored, never in the context. Because the user's access and refresh tokens, the sealed values and the binding nonce are not action inputs, the #2 redaction pass (which replaces configured secret values) cannot know them: the plumbing registers each request's live token values for **per-request redaction** of every response body, header and log line [gap OG3, D15], so a provider that echoes a token in an error body cannot leak it.

**D11. Disconnect revokes upstream, then deletes.** `POST /dam/{provider}/disconnect` (`api`, IMS-authenticated, idempotent, `204`): if the record holds tokens and the provider implements `revoke`, the shell calls it **best-effort** with a fresh access token (refreshing first if stale), then **deletes the record regardless of the result** (a stale grant at Dropbox is visible to the author in their connected apps; a stuck record in our store is not recoverable by them); it also purges the author's entries in the in-container result cache (D14) and any in-memory kept record (D9 step 7). A reauth marker is simply deleted. Dropbox revoke (D17) invalidates the refresh token and every access token derived from it. Shared links already created are **not** removed (README says so). Connecting again replaces the previous record without revoking the old grant: revoking the old tokens could, for a provider that shares token families, kill the new connection [ASSUMPTION; harmless orphan grants remain visible to the author].

**D12. Worker API surface (#23 reserved routes, now routed; two actions).** `api` base `https://<namespace>.adobeioruntime.net/api/v1/web/multi-dam-picker/api`; `oauth` base as D7. All `api` paths below `/dam/` require the IMS token (auth-first, #2 Decision 7): no token `401` (including unknown paths), token and unknown `404 not_found`.

| Action | Method + path | Auth | Purpose | Result |
|---|---|---|---|---|
| `api` | `GET /dam/providers` (existing) | IMS | gains, for `user-oauth` providers, `connection: { state: connected \| not_connected \| reauth_required, account?: { displayName } }` | `200` |
| `api` | `POST /dam/{provider}/connect` | IMS | issue the begin URL | `200 { beginUrl }`; `404 not_found` unknown/unconfigured; `400 bad_request` if `state` would exceed the provider's limit |
| `api` | `GET /dam/{provider}/session` | IMS | connection state for one provider | `200 { connection }` |
| `api` | `POST /dam/{provider}/disconnect` | IMS | revoke (best-effort) and delete | `204` |
| `api` | `GET /dam/{provider}/assets...` (existing) | IMS | browse and detail now run with the author's credentials | adds `409 provider_not_connected`, `409 provider_reauth_required` |
| `oauth` | `GET /{provider}/begin?ticket` | **public, sealed ticket** | set the binding cookie, `302` to the provider | `302`; `400` generic page for any ticket problem |
| `oauth` | `GET /{provider}/callback?...` | **public, sealed state + cookie** | finish the flow | `200` static page on success, `400` identical static page on every failure; `405` for other methods |

The two `oauth` routes are top-level navigations, not CORS endpoints (no `Access-Control-Allow-Origin`), and answer **only** `GET`; they are the **only** unauthenticated routes in the worker besides `OPTIONS` preflight on `api`. Any other path on `oauth` (including any path without a valid sealed value) gives the same generic failure page. The callback page is static and script-free ("You are connected. You can close this window." or one generic failure sentence), with `Content-Type: text/html`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and a restrictive CSP (`default-src 'none'; frame-ancestors 'none'`), reflecting no request input; that the platform passes these headers through is [ASSUMPTION: confirmed in spike S-OA]. **Error contract additions:** the #2 shape `{ error: { code, message, requestId } }` with two extension codes, `provider_not_connected` and `provider_reauth_required` (both `409`, fixed messages) [gap OG4]; everything else reuses #2 codes (an unknown or unconfigured provider is `404 not_found`, as #23).

**D13. Browser connect panel: the single extension point #23 left.** #23 UI15 shows a provider whose `connection.state` is not `connected` as unavailable with a fixed notice; this ticket replaces that branch with the panel, with **no vendor knowledge** (label and state only):
- `not_connected` -> "Connect to <label>" button. The click handler calls `window.open` **synchronously before any `await`**, then requests `beginUrl` and sets the pop-up's location (after checking the URL's origin against the worker origin, D19 of #23); if `window.open` returns `null` (blocked) a visible instruction and a real link fallback are shown. Completion is detected by **polling `session`** (about every 1.5 s, backing off to 3 s, giving up after about 5 minutes [ASSUMPTION: values]) and by noting the pop-up closing without a connection (message with retry); there is **no `postMessage`** channel, because the pop-up can lose its opener under cross-origin opener policies. On `connected` the panel best-effort closes the pop-up (`close()` works on windows script-opened by the page, [VERIFIED*: MDN `Window.close()`; a no-op otherwise, the page then says it can be closed]) and loads the grid without a reload. Each poll is one Runtime activation plus one State read (about 200 per connect); this is a small fraction of the shared 6,000 activations per minute and the Stage State bandwidth, but it is not free and the poll stops as soon as it can (R19).
- `connected` -> a header "Connected as <displayName>" with **Disconnect**; Disconnect calls `POST disconnect` then shows the Connect state.
- `reauth_required` -> "Reconnect" (and the old account label); an in-band `409 provider_reauth_required` or `409 provider_not_connected` from any browse call flips the panel to the matching state **without a reload**.
- `misconfigured` (`500`) never shows Reconnect: "ask your administrator" only (#23 UI7).
- A rejected `fetch` (the opaque platform-generated failure, #2 R11) or a bounded-wait timeout during connect, session or disconnect shows the same "service unavailable, try again" message as every other worker call (#23 D19, UI17); a cold start adds latency to the first call, so the connect step shows its "working" state.
- Because State's cross-container read-your-writes is not documented (D8), a poll served by another container might in principle see `not_connected` shortly after a successful callback; the poll tolerates that by continuing to its deadline (UO6). Same user, same browser normally reaches the same container pool [ASSUMPTION; observed in MD7].

**D14. Result cache scope for `user-oauth` (the rule #23 D17 left to this ticket).** The shell's short result cache is enabled for `user-oauth` providers **per author only**: the key includes the connection key (D6), the provider's configuration fingerprint (client id, root path) and the full validated request. Two authors never share an entry; entries for an author are dropped on Disconnect and on any *reauth required*; detail responses and errors are never cached (unchanged). Entries live in **container memory only** (never in State, they would hold file names of private files and the State container is shared by all workers); the hit rate is best effort (a different warm container misses) and a hard rule is tested: the key always includes the connection key, so a container serving many authors can never return one author's entry to another (CN7). Dropbox default `DROPBOX_CACHE_SECONDS=30` (`0` disables).

**D15. Template contract gaps this ticket depends on (OG1-OG4), plus #23's TG2/TG3.** Gathered so the owner can approve them as #2 additions or accept this ticket carrying a thin wrapper that reuses the template's exported helpers. **OG1 (public action with a custom authenticator):** a template factory variant for an action whose routes answer without `Authorization` but run their own authenticator (sealed ticket, sealed state plus cookie), with CORS never enabled; #2 Decision 7 currently says there are no unauthenticated routes except preflight, so this is a deliberate, tested amendment (the template's UA matrix is extended so that the `api` action stays fully authenticated and the `oauth` action exposes exactly two route patterns). The repo convention check (#2 Decision 19, UR6) must allow a second action that is raw, custom-options and without `require-adobe-auth`. Fallback: the same as a route option on `api` (D7). **OG2 (store: conditional writes, explicit TTL):** `putIfAbsent` and `putIfPresent` on the store interface and the memory twin, resolving to a boolean, mapped to State's `ifNotExists`/`ifExists`; the store's TTL validation already caps at 365 days. **OG3 (per-request dynamic redaction):** the handler or pipeline can register values (live access/refresh tokens, nonce, sealed strings) for redaction of that request's responses and logs. **OG4 (HTML responses and extension codes):** a route can return HTML with a custom security-header set, a `302` with `Set-Cookie` (string or array) and `Location`, and the error helper accepts extension-defined codes (`provider_not_connected`, `provider_reauth_required`). #23's **TG1 (Basic credential redaction)** is not needed here; **TG2 (optional secrets)** and **TG3 (prefix or parameterised routes)** are prerequisites (the shell secrets are optional, D4; `/dam/{provider}/...` on `api` and `/{provider}/...` on `oauth` are parameterised). None is a redesign of the template; the auth-before-routing order, CORS and error contract are used unchanged on `api` [OPEN: Question 2].

**D16. Configuration split (app-config inputs, #2 Decision 9).** *Shell (provider-agnostic, new in this ticket):* **inputs** `OAUTH_PUBLIC_BASE_URL` (non-secret, one `$NAME` per workspace because the namespace is known only after deploy), `CONNECTION_TTL_DAYS` (optional literal, default 180); **secrets** (committed as `$NAME` references, values only in the untracked `.env`) `TOKEN_ENC_KEY` (and optional `TOKEN_ENC_KEY_PREVIOUS`), `OAUTH_STATE_KEY` (each a base64 32-byte value, validated at registry build with the setting named and never its value; the two must differ). No storage binding exists: State uses the action's implicit credentials and the template's `STATE_REGION`. *Dropbox:* **secret** `DROPBOX_CLIENT_SECRET`; **inputs** `DROPBOX_CLIENT_ID` (the app key, public by nature: it is in the authorize URL), `DROPBOX_SCOPES` (default D18), `DROPBOX_ROOT_PATH` (optional browse and search root), `DROPBOX_ALT_TEMPLATE_ID` and `DROPBOX_ALT_FIELD` (optional, both or neither), `DROPBOX_CACHE_SECONDS` (optional, default 30). **No test-only origin input exists:** tests redirect the Dropbox origins through the test kit's injected `fetch` and Playwright routing (EO), so no production code path honours a test origin and no guard has to forbid one. The Stage and Production workspaces have separate `.env` files and therefore separate keys and (recommended) separate Dropbox apps (D23). The extension reads **no site config** beyond its `library` row. A provider is *configured* when `DROPBOX_CLIENT_ID` and `DROPBOX_CLIENT_SECRET` are both non-empty.

**D17. Dropbox OAuth: authorization-code grant with `token_access_type=offline`, executed by the worker.** Authorize at `https://www.dropbox.com/oauth2/authorize` with `client_id`, `response_type=code`, `redirect_uri` (exact, registered), the sealed `state`, `token_access_type=offline` and an explicit `scope`; token endpoint `https://api.dropboxapi.com/oauth2/token`, authenticated with the app key and secret as `application/x-www-form-urlencoded` POST parameters or HTTP Basic [VERIFIED: https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization.md, re-read 2026-11-18]. Facts that shape the design, all from that page and the OAuth guide: the documented access-token lifetime is `expires_in: 14400` (four hours); `refresh_token` is returned only when `token_access_type=offline` was sent and "is long-lived and won't expire automatically. It can be stored and re-used multiple times"; a refresh "won't return a new refresh token since refresh tokens don't expire automatically and can be reused repeatedly" (so Dropbox never rotates: the refresh race that matters for rotating vendors cannot invalidate a Dropbox connection); a refresh response carries `access_token`, `expires_in`, `token_type` and (only if requested) `scope`; `state` is "up to 2000 bytes"; "All redirect URIs must be HTTPS except for localhost URIs", registered exactly, so the `https://<namespace>.adobeioruntime.net/...` callback is registrable [VERIFIED, same page; that Dropbox's console accepts this particular host is [ASSUMPTION], MD1]. The authorize page "should not be displayed in a web-view", so the pop-up is the supported shape [VERIFIED, same page]. The client secret is the confidential-client credential, so **PKCE is not used and the console's "Allow public clients" toggle is switched off**, which Dropbox advises when neither PKCE nor implicit is used ("If your app uses neither, it is safer to turn the toggle off", OAuth guide [VERIFIED*]); the plumbing has no PKCE support in this ticket and gains it additively if Bynder requires it [OPEN: Question 12]. Client credentials (app auth) are not used (they cannot call user endpoints). **Error classification** (the provider's mapping into D5 classes): token endpoint `400` whose `error` string starts with `invalid_grant` -> *reauth*; `400` starting with `invalid_client` (O2) -> *misconfigured*; any other `400` -> *misconfigured* (never delete on a vocabulary surprise); `5xx`/network -> *transient*; browse calls: `401` with `invalid_access_token`, `expired_access_token`, `missing_scope` or `user_suspended` -> *reauth required* (D5 token-rejected signal; `invalid_access_token` and `expired_access_token` both mean "refresh then retry", https://docs.dropboxapi.com/dropbox-api/docs/error-handling.md [VERIFIED*], O3). [ASSUMPTION: `invalid_grant` is the form for a revoked refresh token; O2 shows only the `invalid_client` form because no valid client exists to probe with; confirmed in MD4.] **Account name:** `POST /2/users/get_current_account` (scope `account_info.read`), `name.display_name` [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account.md; whether a no-argument RPC takes no body is [ASSUMPTION], MD3]. **Revoke:** `POST /2/auth/token/revoke` "disables the access token used to authenticate the call. If there is a corresponding refresh token for the access token, this disables that refresh token, as well as any other access tokens for that refresh token" [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/auth/token-revoke.md]; a `401` on revoke means the token is already invalid and counts as success.

**D18. Scopes and content access: the minimum that serves the criteria.** `account_info.read` (display name), `files.metadata.read` (search, list, metadata, file properties), `files.content.read` (thumbnails), `sharing.read` (find an existing link), `sharing.write` (create one); each is the documented required scope of the endpoint it serves (per-endpoint pages under https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/ [VERIFIED*]). Content access type **Full Dropbox**: App Folder reaches only `/Apps/<name>`, which cannot hold existing brand assets; Dropbox's guidance is to request the least access ("Always ask for the least amount permissions", OAuth guide [VERIFIED*]) and reviewers check `sharing.write` is justified (developer guide [VERIFIED*]). The scope list is configuration (`DROPBOX_SCOPES`); because the authorize request names its scopes, the shell's required-scope check (D5) refuses a connection that lacks one, and a later `missing_scope` answer is *reauth required*.

**D19. Browse and search inside the shell's window contract.** Dropbox declares: `assetTypes` image, video, document, audio; `sorts` **`modified`** (default, newest first) and **`relevance`** (flagged *requires a query*); `window` **300**; `assetIdPattern` for `id:` plus URL-safe characters with a length cap [ASSUMPTION on the charset, DBX-SE7, MD3]; `outboundHosts` `api.dropboxapi.com` and `content.dropboxapi.com`; `authorizeHosts` `www.dropbox.com`; `deliveryHosts` `www.dropbox.com` (the inserted shared-link host; the `raw=1` redirect to the content host happens in the visitor's browser); `cacheSeconds` default 30; `rotatesRefreshToken` false. **Non-empty query:** `files/search_v2` with `options.file_status=active`, `options.file_categories` mapped from the shell type (image -> image; video -> video; audio -> audio; document -> document, pdf, spreadsheet, presentation; all -> those plus `others`; never `folder` or `paper`), `options.path` set to `DROPBOX_ROOT_PATH` when set, `options.order_by` from the shell sort (`relevance`, or `last_modified_time`), `max_results` per call; `search/continue_v2` for more. Dropbox search is cursor-only and documents "Duplicate results may be returned across pages. Some results may not be returned" and a "maximum of 10,000 matches" [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/search-v-2.md]; `max_results` is "default: 100" with no stated maximum and `query` is a required string with no stated empty behaviour [VERIFIED* page; ceilings [OPEN], MD3]. The shell's contract is page + pageSize with `hasMore`; the provider therefore **re-walks from the start**: for page *p* of size *n* it collects at least *p x n* matches (continuing the cursor while `has_more`, capped at three Dropbox calls and the 300-result window [ASSUMPTION: numbers, tuned in MD3]), de-duplicates by file id, drops non-files and non-downloadable files, slices the page, and reports `hasMore` when more were collected than shown or Dropbox said `has_more`; `total` is omitted. **Time budget:** the walk runs inside the invocation's proxy deadline (#2 Decision 11: 15 s overall, under the 25 s action timeout); when the remaining budget is too small for another call it stops and returns what it has with `hasMore` true, never a timeout. A page beyond the window is the shell's `400 bad_request` before any call. **Empty query** (the "recent" view): `files/list_folder` of `DROPBOX_ROOT_PATH` (or the namespace root), **non-recursive**, `include_non_downloadable_files=false`, continued while needed up to a scan cap, files only, filtered by type through the extension table (D20), sorted by `server_modified` descending, then sliced as above. Non-recursive because Dropbox warns that recursive listing "may lead to performance issues or errors" on large trees [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/list-folder.md]; the sort is exact only within the scanned window, which the README states. The `relevance` sort without a query is the shell's `400`. [OPEN: whether `search_v2` accepts an empty query with `order_by=last_modified_time`, which would give true recency without a scan cap; MD3 decides and D19 is then revised before build.] The root is a UX and policy guard, not a security boundary (the token reads everything the author can). **Folders are never listed** (the shell has no folder concept; folder navigation is out of scope). Dropbox search is eventually consistent ("short delay in indexing" [ASSUMPTION per the earlier draft]); the README notes a just-uploaded file may not appear.

**D20. Type, format and thumbnails.** Dropbox metadata has no mime type and results carry no category, so a **provider-owned extension table** maps extensions to the shell's types (image, video, document, audio, other) and to *insertable as an image* (browser-renderable: jpg, jpeg, png, gif, webp, avif, svg [ASSUMPTION: Dropbox serves SVG through `raw=1` with an image content type, MD5]); HEIC, TIFF, BMP and camera RAW are `image` for filtering but **not insertable as `<img>`** with a fixed reason. **Thumbnails:** Dropbox exposes no thumbnail URL (`get_temporary_link` URLs last four hours and "should not be used to display content directly in the browser", https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-temporary-link.md [VERIFIED*]); the thumbnail endpoint returns base64 bytes, "up to 25 thumbnails in a single batch", for jpg, jpeg, png, tiff, tif, gif, webp, ppm and bmp, files over 20 MB are not converted, and the size is chosen from `w32h32`, `w64h64`, `w128h128`, `w256h256` and larger [VERIFIED: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-thumbnail-batch.md, re-read 2026-11-18]; an `<img>` cannot send a bearer header, so a worker thumbnail route would need sealed URLs and new shell routes. #23 D5 already allows the one needed flex: `thumbnailUrl` (only that field) may be an inline `data:image/jpeg|png|webp;base64,...` of at most 64 KB, everything else stays `https:` only. The provider therefore returns inline thumbnails for convertible files up to 20 MB, in batches of at most 25 (two calls for a 50-item page), **at size `w128h128`** (the platform's 1 MB result limit applies to the whole `api` response, #2 Decision 11; at a few KB per thumbnail a 24-item page stays far below it, and a **per-response thumbnail budget of about 500 KB** [ASSUMPTION: value] drops further thumbnails rather than overflowing). **A thumbnail failure or an exhausted budget never fails the search** (the item is returned without `thumbnailUrl`; the shell shows a file-type placeholder). **Fallback if the owner drops the inline allowance (#23 Question 8): zero further shell change, the provider omits `thumbnailUrl`** and the thumbnail step and tests DBX-TH1-TH4 are replaced by DBX-TH-F.

**D21. Detail: link resolution, rendition and alt text (the `getAsset` effect).** Dropbox has no CDN-style rendition URLs; the only stable URL that works for visitors is a shared link. For the selected file `getAsset` (a) reads metadata with media info (dimensions; `media_info` may be `pending`, then dimensions are omitted: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata.md [VERIFIED*]); (b) lists the file's existing links with `sharing/list_shared_links` (`direct_only`) and takes the first that is public (`effective_audience` public, not password-protected, no `expires`, downloads allowed); (c) only if none, creates one with `sharing/create_shared_link_with_settings` requesting `audience: public`, `access: viewer`, `allow_download: true`, and **checks what Dropbox resolved**, because "the resolved visibility, though, may depend on other aspects such as team and shared folder settings" (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/create-shared-link-with-settings.md [VERIFIED*]). A resolved non-public audience, a `settings_error` (`not_authorized`, `invalid_settings`), `access_denied`, `email_not_verified`, or an existing link that is not public makes the asset `insertable: { ok: false, reason }` with a fixed reason, **never an HTTP error**. A repeated call is a no-op by construction (step b finds the link), so the `GET`-triggered effect is idempotent; this is the "documented, README-stated exception" #23 D3 allows for `getAsset`, and **Dropbox is its first user**. Existing links are **never modified or revoked** (modifying an existing link's access level is not supported and widening someone's sharing silently would be worse). Cost, stated plainly in the README and in the rendition label: **opening a file's detail pane creates a public link to it** (the URL carries an unguessable `rlkey`, but anyone holding it can read the file). Creating on insert instead needs a new "prepare for insert" step in the shell [OPEN: Question 5]. **Rendition policy:** one rendition, `original` ("Original (size)"), `defaultRenditionId` pointing at it; no resized variants exist as stable URLs. The inserted image URL is the API-returned link with the display parameter set as Dropbox documents ("use raw=1 as a query parameter ... Changing 'dl=1' or 'dl=0' to 'raw=1' in a URL will cause an HTTP redirect", and developers should "properly parse the URL and add or modify parameters as needed", https://help.dropbox.com/en-us/share/force-download [VERIFIED*]). This stays within #23 D5's URL rule (a provider may build URLs from the vendor's documented URL grammar and the structured fields its API returned): the provider parses the returned link with a URL parser (never string concatenation), deletes `dl`, sets `raw=1`, keeps every other parameter (`rlkey`, `st`) untouched, and requires `https` and host `www.dropbox.com` (the output URL policy of #23 D13 then enforces `deliveryHosts`); it never builds a link from a file id or path; the non-image `linkUrl` is the link exactly as returned. **Alt text:** Dropbox has no description or alt field; the only genuine metadata channel is **file properties**: when `DROPBOX_ALT_TEMPLATE_ID` and `DROPBOX_ALT_FIELD` are set, `get_metadata` asks for that template only (`include_property_groups` with `filter_some`) and the field value, stripped to plain text, is the candidate with `source: property`; else the file name without extension, separators to spaces, `source: name`; else empty with `source: none`; `source: description` is never produced; markup, entities and control characters are stripped as in #23 D15; the author always sees and can edit it or mark the image decorative [OPEN: Question 9].

**D22. Error mapping and retry flags (Dropbox).** Dropbox answers: `401` (`invalid_access_token`, `expired_access_token`, `missing_scope`, `user_suspended`) -> *reauth required* (D5, D9); `403` (`no_permission`, team access) -> the shell's forbidden mapping; `409` endpoint errors: `path/not_found` -> not found, search `invalid_argument` -> bad request, link-creation errors -> a `200` detail with `insertable.ok=false` (D21); `429` (always with `Retry-After`; `reason` `too_many_requests` or `too_many_write_operations`, https://docs.dropboxapi.com/dropbox-api/docs/performance.md [VERIFIED*]) -> *rate limited* with the delay; `5xx` and network -> *upstream unavailable*; fixed messages, never upstream text. **Retry flags** (the #2 explicit opt-in for POST, #2 Decision 11): the read-only RPC calls Dropbox exposes as POST (search, list, metadata, thumbnails, shared-link listing, account) are safe to retry on `5xx`; the **refresh grant is safe to retry**; the **authorization-code exchange and revoke are not**; link creation is safe to retry because repeating it returns `shared_link_already_exists`, never a duplicate (D21).

**D23. Dropbox app registration and Dropbox's rules the README must carry.** Recommended: **one Dropbox app per workspace** (a development-status app for Stage, and the app that goes through production review for Production), created by the maintainer in the App Console: scoped access, **Full Dropbox**, the five scopes, **one redirect URI: the deployed workspace's `oauth` callback** (`{OAUTH_PUBLIC_BASE_URL}/dropbox/callback`, known after the first deploy; the `ref=local` page also calls the Stage worker, so no localhost URI is needed), "Allow public clients" off [OPEN: Question 7: one app serving both workspaces is possible, Dropbox allows several redirect URIs, but mixes development and production status]. The app name "may not include the word 'Dropbox' or begin with 'drop'" (https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/branding-guide.md [VERIFIED*]); proposed name **EW Multi-DAM Picker**; the button text "Connect to Dropbox" identifies the integration and is allowed. A new app has **development status**: it links your own account plus enabled development users up to "500 total Dropbox users", but "once your app links 50 Dropbox users, you will have two weeks to apply for and receive production status approval before your app's ability to link additional Dropbox users will be frozen", and production review "will not be reviewed until your app has linked with at least 50 Dropbox users"; it expects a privacy policy and branding compliance, and the name cannot be changed after approval [VERIFIED*: https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md, "Production approval"]. The same guide lists "Don't build file sharing apps" ("Dropbox doesn't support building publicly searchable file sharing networks on top of Dropbox", [VERIFIED*]); embedding images from the team's own Dropbox is not a public file-sharing network, but Dropbox's terms (https://www.dropbox.com/developers/reference/tos) were not read [OPEN: Question 7].

**D24. Team spaces are out of scope for v1.** All calls run against the author's home root. Business teams with a Team Space keep shared team folders in a separate root that needs the `Dropbox-API-Path-Root` header and the `root_namespace_id` from `get_current_account` (https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/path-root-header-modes.md, https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account.md [VERIFIED*]). Brand folders are often team folders, so this is the likeliest first follow-up and a real limitation on Business accounts [OPEN: Question 8]; the mechanism is documented so the follow-up is a provider-only change.

**D25. Rate, size and time budget (Runtime).** Dropbox publishes no numeric limits: they are "per-authorization", `Retry-After` is always present, and rate-limited requests count (https://docs.dropboxapi.com/dropbox-api/docs/performance.md [VERIFIED*]). Per `api` request the worker issues: a browse (up to 3 search calls plus up to 2 thumbnail-batch calls at the 50-item cap), a detail (3 calls: metadata, list links, create link), at most 1 refresh, plus a few State operations (one read, at most one write, the lock pair only when refreshing). All of it runs inside the action's 25 s timeout and the proxy's 15 s overall deadline (D19), under the platform's 1 MB result limit (D20) and 1 MB parameter limit, and counts against the namespace-wide 6,000 activations per minute and 100 concurrent activations shared with every other worker [VERIFIED: #2 Decision 9, system-settings page]. The default page size stays 24 (#23 D12). Shared links are subject to Dropbox bandwidth limits that affect **published pages**: "Dropbox Basic 20 GB and 100,000 downloads per day, paid plans 1 TB to 4 TB", and a link "shared or downloaded too many times over a 24 hour period" is temporarily disabled (https://help.dropbox.com/share/banned-links [VERIFIED*]). The README states Dropbox links are for staging and low-traffic use, not a production CDN (Out of Scope names the alternative).

**D28. Environments, deploy and secrets lifecycle (#2 Decision 18).** Deploy is manual and Stage-first: `env -u CI aio app deploy` from `apps/multi-dam-picker/worker/` with the owner's Developer Console login, Stage for `ref=local` and branch testing, Production for `main`. Each workspace has its own untracked `.env` (with its own `TOKEN_ENC_KEY`, `OAUTH_STATE_KEY`, Dropbox app credentials and `OAUTH_PUBLIC_BASE_URL`) and its own State container, so Stage connections never exist in Production. Rotating a secret is "edit `.env`, redeploy the action" (`aio app deploy --action <name>`, #2 Decision 9); rotating `OAUTH_STATE_KEY` only invalidates in-flight tickets and states (a connect in progress fails and is retried); rotating `TOKEN_ENC_KEY` needs the previous-key input for one deploy cycle. No Developer Console credential is in CI. This spec's research ran only read-only `aio` commands.

## Testing Decisions

**What makes a good test here.** Assert external behaviour only: given a web-action invocation (raw `params`: headers, path, query; inputs from the kit's `makeInputs`; fake IMS, fake Dropbox, in-memory store) assert the returned `{ statusCode, headers, body }`, redirects and cookies, the stored (encrypted) bytes and the requests the fake Dropbox received (method, host class, path, headers, form or JSON body); given an SDK result and a worker stub, assert the DOM and the SDK actions. Never assert on internal helper names or internal call counts. Properties asserted as negatives across every path: **no Dropbox app secret, access token, refresh token, sealed ticket or state, binding nonce or encryption key ever reaches a response, header, redirect, log line or the browser**; **nothing runs before authentication succeeds on `api`, and the `oauth` action does nothing without a valid sealed value**; **only the browser that began a flow can finish it**; **one author's connection is unusable by any other author**; and, for Dropbox, **the page never contacts a Dropbox API host, no link is created by anything but the detail call, and an existing non-public link is never modified**.

**Proposed seams** (recorded here instead of asked, per #63). The seams are #2's and #23's; **this ticket adds no seam**. The one new seam #23 introduced (P1, the provider interface) is what proves "Bynder and Frontify only add provider config".

## Further Notes

- **Dropbox's API answers browser CORS preflights for `https://da.live` (O1).** That makes it technically easy to put an access token into the page and call Dropbox from the browser; the requirement that the browser never receives a credential forbids it, and the e2e host-allowlist check (EO5) and the unit tests for the connect panel make the forbidden shortcut fail loudly.
- **Dropbox refresh tokens do not rotate and do not expire** (D17), so the Dropbox connection is the robust case, but a leaked stored refresh token is a standing credential until revoked. That is why encryption at rest, key separation, the retention TTL, the purge procedure and the real upstream revoke on Disconnect matter, and why they sit in the plumbing, not in the provider.
- **Why Dropbox first proves only half of the plumbing.** Dropbox's non-rotating refresh and form-encoded exchange do not stress the rotation logic (D9 steps 3 and 7). The stub OAuth provider does, in CI. What neither can prove is a real rotating vendor's behaviour (and State's actual cross-container behaviour under the lock); that is verified in #24 (Frontify) and #22 (Bynder) and, for State, by spike S-OA, which is why a "rotating-provider gate" sits before #24 enables a rotating provider (Open Question 3).
- **Why not create the link at browse time or insert time.** Browse-time creation would publish every file the author scrolled past; insert-time creation is the right moment but needs a shell step that does not exist. Detail-time creation (D21) is the least intrusive point within the current contract (Open Question 5).
- **EDS and external images.** Whether Edge Delivery Services keeps an external `<img src>` in a DA document, and whether it follows the `raw=1` redirect to `dl.dropboxusercontent.com`, is unverified (carries #23 R13) [ASSUMPTION: kept and rendered as an ordinary external image]; manual step MD6 observes it.
- **The Dropbox docs moved** to https://docs.dropboxapi.com (the old `www.dropbox.com/developers/documentation/http/documentation` page is client-rendered); every API claim cites the stable `.md` page of the new site.
- **The callback host is shared.** Every worker of the workspace answers on the same `<namespace>.adobeioruntime.net` host; the OpenWhisk documentation recommends the namespace-as-subdomain form precisely so cookies and local storage are not visible to web actions in *other* namespaces [VERIFIED: https://github.com/apache/openwhisk/blob/master/docs/webactions.md, "alternate URL"], which also means they are visible to other actions in the *same* namespace. The design keeps nothing sensitive in that cookie (D7).
- **Current repo state (observed 2026-11-18).** `apps/multi-dam-picker/` and `shared/worker-template/` hold only spec files (the #23 and #2 specs were just rewritten for App Builder and are modified in the working tree); `apps/hello-world/` has the implemented #1 scaffold without a worker; root `package.json` has the scripts `lint`, `check`, `test`, `test:unit`, `test:scripts`, `test:e2e`; CI has the jobs `lint`, `unit`, `e2e`; `.hlxignore` already hides `**/worker/`, `**/test/`, `shared/worker-template/` and `**/SPEC.md` from the code bus (which also covers `providers/dropbox/worker/`). The #1 convention check treats a folder holding only `SPEC.md` files as planned and ignores it until code is added. Everything here that says "the shell provides" or "the template provides" presumes #23 and #2 landed as specified and that the gaps of D15 are approved or wrapped.

**Auth flow (author to worker):** SDK token -> `Authorization: Bearer` -> #2 verification inside `api` -> `identity.userId` -> record key `conn.v1.` + hash(userId, "dropbox").

**Auth flow (Dropbox connection)** is D7's six steps with Dropbox values: (1) `POST connect` returns `{ beginUrl }`; (2) the click handler opens the pop-up synchronously and navigates it to `beginUrl`; (3) `begin` verifies the ticket, sets the binding cookie, `302` to the Dropbox authorize URL of D17 with the sealed `state` (kept under 2,000 bytes); (4) the author signs in to Dropbox and approves the listed access; (5) Dropbox `302`s to the `oauth` callback with `code` and `state`; the action verifies state and cookie, exchanges the code with the app secret, requires a refresh token and the full required scope, calls `get_current_account` for the display name, stores the encrypted record and returns the static page; (6) the extension's `session` poll flips to connected. The stored access expiry is `now + expires_in` (about 14,400 s).

**Auth flow (per call):** read and decrypt the record -> refresh if under 60 s remain (in-container single flight, then the State lock; no rotation to guard for Dropbox, so a lock timeout proceeds unlocked) -> call Dropbox with `Authorization: Bearer <author's Dropbox access token>`, never the IMS token -> on `401` force one refresh and retry once -> normalise -> output URL policy -> respond. A second rejection destroys the tokens, writes the reauth marker and answers `409 provider_reauth_required`.

**Disconnect flow:** `POST disconnect` -> refresh if stale -> `token/revoke` (best-effort) -> delete the record -> purge the author's cache entries -> `204`.

## 4. Data contracts

Behaviour contracts, not code.

**Worker API:** D12 (table). **Provider-list item for a `user-oauth` provider:** `{ id, label, credentialKind: "user-oauth", connection: { state, account? }, capabilities }`; `state` is `connected` (a record with tokens exists), `not_connected` (no record, expired record or undecryptable record) or `reauth_required` (reauth marker); `account` carries `displayName` only.

**Connect response:** `{ beginUrl }` (origin = the `OAUTH_PUBLIC_BASE_URL` origin; query = the sealed ticket). **Session response:** `{ connection: { state, account? } }`.

**Dropbox capabilities:** `assetTypes: [image, video, document, audio]`; `sorts: modified (default), relevance (requires a query)`; `window: 300`; `assetIdPattern: ^id:[A-Za-z0-9_-]{1,128}$` [ASSUMPTION: charset, MD3]; `outboundHosts: [api.dropboxapi.com, content.dropboxapi.com]`; `authorizeHosts: [www.dropbox.com]`; `deliveryHosts: [www.dropbox.com]`; `cacheSeconds: 30`; `scopes`: D18; `maxStateBytes: 2000`; `requiresRefreshToken: true`; `rotatesRefreshToken: false`.

**Summary (search items):** `id` = the Dropbox file id (`id:...`); `provider: dropbox`; `name`; `type` by the extension table; `thumbnailUrl` = `data:image/<jpeg|png|webp>;base64,...` of at most 64 KB (or absent: fallback, unsupported format, over 20 MB, conversion failure, budget exhausted); `extension`; `fileSize` (`size`); `dateModified` (`server_modified`); `width`/`height` **omitted** (Dropbox returns no `media_info` in search or list results); `warnings: []`.

**Detail:** the summary plus `width`/`height` (when `media_info` is ready), `tags: []`, no `description`/`copyright`, `alt { value, source: property | name | none }`, `renditions: [ { id: "original", label: "Original (<size>)", url, kind: original, width?, height? } ]` (empty when there is no usable public link), `defaultRenditionId: "original"`, `insertable { ok, reason? }`, `linkUrl?` (non-image files: the link as Dropbox returned it).

**`insertable.reason` (fixed strings, never upstream text):** "Dropbox does not allow a public link for this file"; "The existing link for this file is not public"; "The existing link for this file needs a password or has an expiry date"; "This file cannot be shown as an image in a browser"; "This file cannot be downloaded"; "Sign-in with a verified Dropbox email is required to share this file".

**Dropbox-to-shell error map** (D17, D22):

| Dropbox | Shell outcome |
|---|---|
| browse `401` `invalid_access_token` / `expired_access_token` | *reauth required*: shell refreshes once and retries; a second rejection -> tokens destroyed, marker written, `409 provider_reauth_required` |
| browse `401` `missing_scope` / `user_suspended` | same path (reconnect re-requests scopes; suspension is temporary) |
| `403` `no_permission` and team access errors | forbidden mapping |
| `409` `path/not_found` | `404 not_found` |
| `409` link-creation errors | `200` detail with `insertable.ok=false` and a fixed reason |
| `429` (`too_many_requests`, `too_many_write_operations`) | `429 rate_limited` + `Retry-After` |
| `5xx`, network | `502 upstream_unavailable` |
| token endpoint `400 invalid_grant...` | *reauth*: tokens destroyed (after the re-read, D9), marker written, `409 provider_reauth_required` |
| token endpoint `400 invalid_client...` or any other `400` | *misconfigured*: `500 misconfigured`, record kept |
| token endpoint `5xx`, network | *transient*: retried (refresh only), `502`, record kept |

**Stored connection record** (D8; encrypted envelope, stored as a JSON string): `{ v, accessToken, accessExpiresAt, refreshToken, scope, account: { displayName, id? }, connectedAt }`, or `{ v, reauth: true, account, at }`. State key `conn.v1.` + base64url hash(userId, provider) (prefixed per worker by the store); AES-256-GCM, random IV per write, key id in the envelope, authenticated data = the full key; explicit TTL `CONNECTION_TTL_DAYS`. The Dropbox refresh token is stored once and **not rewritten on refresh** (only `accessToken` and `accessExpiresAt` change). **Lock record:** `lock.v1.` + the same hash, value = a random owner id, TTL about 20 s, written with `putIfAbsent`.

**Sealed values:** *ticket* `{ purpose, connKey, provider, exp }` (about 60 s); *state* `{ purpose, provider, connKey, nonceHash, exp }` (about 10 min); both AES-256-GCM under HKDF subkeys of `OAUTH_STATE_KEY`, label-separated, base64url. **Binding cookie:** a random nonce, `HttpOnly; SameSite=Lax; Max-Age<=600; Path=<oauth base path>`, host-only, `Secure` except for a loopback test base.

### 1.2 Token store and isolation (AC2, AC3, AC7)

| ID | Behaviour asserted |
|---|---|
| TS1 | The raw store dump (keys and values) contains none of: access token, refresh token, IMS user id, account name; values are string envelopes (version, key id, IV, ciphertext); keys are `conn.v1.` + a hash and are valid State keys (alphanumeric plus `-_.`, at most 1024 bytes) |
