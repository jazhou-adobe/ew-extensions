## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party), and, once #22 lands, from Bynder. Many teams, especially small marketing teams, agencies and regional offices, keep their working brand assets in **Dropbox**, not in an enterprise DAM. Only AEM Assets is documented in EW, so today an author who wants a Dropbox image leaves EW, finds the file in Dropbox, makes a shared link, edits the link by hand so that it renders instead of showing Dropbox's preview page (`dl=0` -> `raw=1`), pastes it into the document and retypes alt text from the file name. Most of these steps are error-prone, and nothing checks that the link is public: a team-only or password-protected link looks fine to the author but is a broken image for every visitor.

For the maintainer the problem is the same as #22's. Dropbox needs OAuth on behalf of the individual author (so Dropbox's own permissions decide what each person may see), a server-side holder for the Dropbox app secret and the long-lived refresh tokens (extension code is public), and the browser must never hold a Dropbox token. #22 built that plumbing once; #25 must now prove the provider contract with a second kind of vendor **by adding one module and a registry entry, not by forking or patching the shell** (AC3).

Dropbox is also the least DAM-like vendor of the four. It has no public "rendition" URLs, no asset metadata for descriptions or alt text, no tags, no type facet, thumbnails that are binary API responses rather than URLs, folder-first navigation instead of a flat asset bank, and cursor-only paging. Those differences, not the OAuth mechanics, are the real work of this ticket and are decided below.

## Solution

The existing **Multi-DAM Picker** library plugin gains a second provider, **Dropbox**. The author opens the library, and (if more than one provider is configured) chooses *Dropbox* in the provider switch. First use shows **Connect to Dropbox**: a pop-up to dropbox.com where the author signs in with their own Dropbox account (personal or work) and approves the app's read access and link creation. From then on the panel shows files from the author's Dropbox: a thumbnail grid with the file name, filterable by type (images, videos, documents, audio), searchable by file name or content. Selecting a file opens a detail pane with name, dimensions (for photos), type and size, an alt text prefilled from a configured file property if the team uses one, else from the file name (editable, or "decorative"), and a single rendition: the file itself through a public Dropbox link. **Insert** places an `<img>` with that URL and the alt text at the cursor and closes the library. Non-image files are inserted as a link with the file name as text. Files that cannot be used (link policy forbids a public link, password-protected or expiring existing link, format browsers cannot render, not downloadable) are shown as not insertable with a one-line reason.

Behind it, exactly the #22 split. The existing worker, extended with one provider module, starts and completes the Dropbox authorization-code flow with the `offline` access type, stores each user's refresh token encrypted at rest keyed by their IMS identity, refreshes the (4-hour) access token silently, and makes every Dropbox call. The browser only ever holds the author's own IMS token and normalised asset data. Disconnect actually revokes the grant at Dropbox (Dropbox offers a revoke endpoint, unlike Bynder) before deleting the stored copy.

The provider adds no browser code. Its worker module is one folder under the extension's `providers/` folder, plus one registry line, a handful of wrangler vars and one README section. One small additive contract allowance in #22 (thumbnails as `data:` URIs, Decision 4) is requested **before #22 is built**; without it Dropbox ships without thumbnails (a documented one-line fallback).

## Implementation Decisions

(No file paths or code, except endpoint names, which are API contracts. Layout is in the Build Analysis.)

1. **Surface and scope: a provider module only.** No new library row, no new browser code, no new worker routes. Everything the author sees comes from the existing shell driven by the provider's capabilities and its normalised output; everything server-side is one provider module registered with the extension's worker. The extension's only registration remains the `library` row from #22; the **site config read is none**, and the README says so (AC4).
2. **Build against the Dropbox HTTP API, not Dropbox's Chooser drop-in.** The Chooser (https://docs.dropboxapi.com/dropbox-api/docs/pre-built-components/chooser.md) is cheaper (no worker, no OAuth, no production approval: "Using the Chooser doesn't require production approval") and is what Contentful's Dropbox app uses (O5). It is rejected for the same reasons #22 rejected Bynder's UCV: (a) AC2 requires per-user OAuth through the worker with tokens stored and refreshed server-side, and the Chooser is authorised in the browser on dropbox.com's own session; (b) the Chooser brings its own picker UI, which cannot be driven by the shell's capability flags, so the provider would need browser code and break AC3; (c) the Chooser needs the hosting domains registered in the Dropbox app, and EW iframes pages from three host families plus `localhost` (#2 Decision 5). Dropbox's own guidance leans the other way ("If your app only needs the user to select a single file ... use the Chooser. Requesting Full Dropbox access to pick a file when you could use the Chooser isn't a good use of the permission", https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md); the cost of this choice is that the production-approval review applies (Decision 15). Owner confirmation: Open Question 4.
3. **Interface assumptions about #22** (recorded because #22's text is silent; each is something the shell spec implies but does not state; if #22's build resolves one differently, this provider adapts at the module boundary). **A1** a provider declares a *list* of outbound hosts (Dropbox needs `api.dropboxapi.com` and `content.dropboxapi.com`; `www.dropbox.com` is only a browser navigation target). **A2** a provider supplies its asset-id validation (BR6 needs a vendor-specific pattern). **A3** `search` receives the page size the shell validated. **A4** `thumbnailUrl` may be absent on a summary (the Bynder fixtures include a "no-thumbnail" asset). **A5** a provider may declare an empty or short `sorts` list and a subset of `assetTypes`; sort ids are provider-declared opaque strings. **A6** `exchangeCode` and `refresh` return access token, lifetime and an optional refresh token, and signal failure as one of three classes: *reauth* (definitive, delete the connection), *transient* (keep), *misconfigured* (keep, generic 500), as RF6/RF7 require. **A7** a provider may declare a maximum `state` length (Dropbox: 2,000 bytes, https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization.md, `state` parameter). **A8** the account display name comes from a provider call made right after the code exchange. **A9** `getAsset` may perform an idempotent provider-side effect (Decision 12). **A10** a provider's own secrets and vars are optional at deploy time: a provider "whose required config or secrets are absent is omitted" (#22 Decision 10) cannot be reconciled with listing its secret under the wrangler `secrets.required` guard (which fails the whole deploy), so provider secrets are not in `secrets.required`; the shell-owned secrets stay required (Open Question 3).
4. **The one contract change requested of #22: thumbnails may be inline `data:` images.** Dropbox exposes no URL for a thumbnail. `get_temporary_link` URLs expire in four hours and the docs say "This URL should not be used to display content directly in the browser" (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-temporary-link.md) and would serve the original, not a thumbnail; the thumbnail endpoints return base64 bytes ("A string containing the base64-encoded thumbnail data", `get_thumbnail_batch`, up to 25 per call, extensions jpg, jpeg, png, tiff, tif, gif, webp, ppm, bmp, images over 20 MB are not converted: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-thumbnail-batch.md); an `<img>` cannot send a bearer header, so a worker thumbnail route would need new shell routes and sealed URLs. The smallest change is for `thumbnailUrl` (and only that field) to accept `data:image/jpeg|png|webp;base64,...` in addition to `https:`; renditions, `linkUrl` and everything inserted stay `https:`-only. This changes #22's schema and UI13 text, not its architecture, and costs nothing if made before #22 is built. **If the owner declines, the fallback is zero shell change: the provider omits `thumbnailUrl` (A4) and the grid shows file-type placeholders** (the thumbnail step is deleted; DBX-TH tests are replaced by DBX-TH-F). Decision gate in the build plan, step 0. Open Question 1.
5. **Per-user OAuth 2.0 authorization-code grant, `token_access_type=offline`, executed by the worker (AC2).** Authorize at `https://www.dropbox.com/oauth2/authorize` with `client_id`, `response_type=code`, `redirect_uri`, the sealed `state`, `token_access_type=offline` and an explicit `scope`; token endpoint `https://api.dropboxapi.com/oauth2/token` (form-encoded, app key and secret in the body). [VERIFIED: https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization.md.] Facts that shape the design, all from that page and https://docs.dropboxapi.com/dropbox-api/docs/oauth.md: access tokens are short-lived (the documented example is `expires_in: 14400`, four hours); `refresh_token` is returned only when `token_access_type=offline` was sent and "is long-lived and won't expire automatically"; a refresh call "won't return a new refresh token since refresh tokens don't expire automatically and can be reused repeatedly" (so the stored refresh token never rotates and the refresh race that R5 worries about for Bynder cannot invalidate a Dropbox connection); redirect URIs must be registered exactly, "All redirect URIs must be HTTPS except for localhost URIs" (so `http://localhost:8787/oauth/dropbox/callback` is registrable: this answers #22 Question 8 for Dropbox); on error or denial the redirect carries `error`, `error_description` and `state`. The client secret is the confidential-client credential, so **PKCE is not used and the console's "Allow public clients" (implicit grant and PKCE) toggle is switched off**, as Dropbox advises when neither is used. Client-credentials / app-auth is not used (it cannot call user endpoints).
6. **Scopes: the minimum that serves the ACs.** `account_info.read` (display name and account type), `files.metadata.read` (search, list, metadata, file properties), `files.content.read` (thumbnails), `sharing.read` (find an existing link), `sharing.write` (create one). Each is the documented required scope of the endpoint it serves (per-endpoint pages under https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/). Content access type: **Full Dropbox** (the App Folder type only reaches `/Apps/<name>`, which cannot hold existing brand assets). The scope list is configuration with this default; because the scope set is requested at authorize time, a record whose granted scope lacks a required one is rejected at connect (DBX-AU4) and a later `missing_scope` answer from Dropbox is treated as reauth (Decision 11). Dropbox's review wants the least privilege and explanation for `sharing.write` (https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/developer-guide.md, "Minimal Access" in the OAuth guide).
7. **Identity, state, cookie, storage, refresh orchestration: all shell-owned and unchanged.** The provider supplies only HTTP mappings (authorize URL, code exchange, refresh, account name, revoke). Refresh policy per #22 Decision 9 holds with Dropbox numbers: proactive refresh under 60 s remaining of the (about 4 h) access token, reactive once on `401`, `invalid_access_token`/`expired_access_token` both mean "refresh then retry" (they are `401` auth errors, https://docs.dropboxapi.com/dropbox-api/docs/error-handling.md, O3), a second `401` deletes the connection and surfaces reauth. The stored refresh token is kept as-is when a refresh response has none (it never has one). A `400 invalid_client` from the token endpoint (O2 shows the body form) is **misconfiguration**, not user revocation: the connection is kept and the author gets the generic failure, never a "reconnect" loop. A `400` whose error string starts with `invalid_grant` is the definitive revoked/expired grant. [ASSUMPTION: `invalid_grant` for a revoked refresh token; O2 shows only the `invalid_client` form because no valid client exists to probe with; confirmed in manual step M-DBX4.]
8. **Disconnect revokes upstream.** The provider implements the interface's optional revoke with `POST /2/auth/token/revoke`, which "disables the access token used to authenticate the call. If there is a corresponding refresh token for the access token, this disables that refresh token, as well as any other access tokens for that refresh token" (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/auth/token-revoke.md). The shell calls revoke best-effort, then deletes the stored record regardless of the result (a stale grant at Dropbox is visible to the user in their connected apps, a stuck record in our store is not recoverable by them). This improves on #22 Question 9 (where no per-token revoke existed). Shared links already created are **not** removed on disconnect (README states it).
9. **Browse and search: type filter via Dropbox file categories; paging by a bounded window; no folders.** Non-empty query: `files/search_v2` with `options.file_status=active`, `options.file_categories` mapped from the shell's type (image -> image; video -> video; audio -> audio; document -> document, pdf, spreadsheet, presentation; all -> those plus `others`; never `folder` or `paper`), `options.path` set to the configured browse root when one is set, `options.order_by` from the shell sort (`relevance` default, or `last_modified_time`), `max_results` per call; `search/continue_v2` for more. Dropbox's search is cursor-only and documents that "Duplicate results may be returned across pages. Some results may not be returned" and a 10,000-match ceiling (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/search-v-2.md). #22's contract is `search(query, type, sort, page)` with `{ items, page, pageSize, hasMore }`, so the provider **re-walks from the start**: for page *p* of size *n* it collects at least *p x n* matches (continuing the cursor while `has_more`, capped at three Dropbox calls and a window of 300 results [ASSUMPTION: numbers; tune against a real account]), de-duplicates by file id, drops non-files, slices the page, and reports `hasMore` when more were collected than shown or Dropbox says `has_more`. `total` is omitted. A page beyond the window is a clean `400 bad_request` (the BR4 pattern), not an upstream call. The cursor-paging upgrade (the capability flag `paging: cursor` exists in #22 but no cursor field does) is a documented follow-up, not a shell change here. Empty query (the shell's "recent" view): `files/list_folder` of the configured browse root, **non-recursive**, `include_non_downloadable_files=false`, up to a scan cap (continuing with `list_folder/continue`), files only, filtered by type through the extension table (Decision 10), sorted by `server_modified` descending, then sliced as above. Non-recursive because Dropbox warns recursive listing "may lead to performance issues or errors" on large trees (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/list-folder.md); the sort is exact only within the scanned window, which the README states. [OPEN: whether `search_v2` accepts an empty query with `order_by=last_modified_time`, which would give true recency without a scan cap; its documentation does not say, manual step M-DBX3 decides and, if yes, this decision is revised before build.] Search covers the whole namespace unless the browse root is configured; the root is a UX and policy guard, not a security boundary (the token can read everything the user can). **Folders are never listed** (the shell has no folder concept; navigating by folder is out of scope).
10. **Type and format classification is by file extension, in the provider.** Dropbox metadata has no mime type and no category field on results. A provider-owned table maps extensions to the shell's types (image, video, document, audio, other) and to *insertable as an image* (browser-renderable: jpg, jpeg, png, gif, webp, avif, svg [ASSUMPTION: Dropbox serves SVG through `raw=1` with an image content type; checked in M-DBX5]); HEIC, TIFF, BMP and camera RAW are `image` for filtering but not insertable as `<img>` (reason shown). Thumbnails are requested only for extensions Dropbox can convert (list in Decision 4) and files up to 20 MB (`size` is in the metadata).
11. **Error mapping.** Dropbox answers `401` (`invalid_access_token`, `expired_access_token`, `missing_scope`, `user_suspended`) -> refresh-then-retry once, then reauth required; `403` (`no_permission`, team access) -> the shell's forbidden mapping; `409` endpoint errors: `path/not_found` -> `404 not_found`, search `invalid_argument` -> `400`; `429` (the docs state rate-limited responses always include `Retry-After`, `reason` `too_many_requests` or `too_many_write_operations`, https://docs.dropboxapi.com/dropbox-api/docs/performance.md) -> `429 rate_limited` with the header, honoured by the UI; `5xx` and network -> `502 upstream_unavailable`; fixed message strings, never upstream text. Retry flags (the template's explicit opt-in, #2 Decision 8): the read-only RPC calls that Dropbox exposes as POST (search, list, metadata, thumbnails, shared-link listing, account) are marked safe to retry on `5xx`; the refresh grant is safe to retry; the authorization-code exchange and revoke are not; link creation is safe to retry because repeating it returns `shared_link_already_exists` (Decision 12), never a duplicate.
12. **Insertable URL = a public shared link, resolved in `getAsset`.** Dropbox has no CDN-style rendition URLs. The only stable URL that works for visitors is a shared link. For the selected file the provider (a) reads metadata with media info (dimensions; `media_info` may be `pending`, in which case dimensions are omitted: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata.md); (b) lists existing links for that file with `sharing/list_shared_links` (`path` = the file id, `direct_only`) and takes the first one that is public (`effective_audience` public, not password-protected, no `expires`, downloads allowed); (c) only if none, creates one with `sharing/create_shared_link_with_settings` requesting `audience: public`, `access: viewer`, `allow_download: true` and **checks what Dropbox resolved**, because the docs state "the resolved visibility, though, may depend on other aspects such as team and shared folder settings" (https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/create-shared-link-with-settings.md). A resolved audience other than public, a `settings_error` (`not_authorized`, `invalid_settings`), `access_denied` or `email_not_verified`, or an existing link that is not public, makes the asset `insertable: { ok: false, reason }` with a fixed reason (never an HTTP error). A repeated call is a no-op by construction (step b finds the link), so a `GET`-triggered effect is idempotent; this is the shell's interface assumption A9. The cost, stated plainly in the README and in the picker's rendition label: **selecting a file in the detail pane creates a public link to it** (the link URL carries an unguessable `rlkey`, but the file becomes readable by anyone holding it). Modifying an existing link's audience is never done (the API says modifying the access level of an existing link is not supported, and widening someone's sharing silently would be worse). A creation-on-insert design would avoid links for files merely browsed, but needs a new "prepare for insert" step in the shell; deferred to Open Question 2.
13. **Rendition policy: one rendition, the original.** `renditions` has a single entry (`kind: original`, label "Original (size)", the file's dimensions when known), `defaultRenditionId` pointing at it. No resized variants exist as stable URLs (thumbnails are not URL-addressable, Decision 4). The inserted image URL is the shared link with the display parameter set the way Dropbox documents for rendering: its help article says "use raw=1 as a query parameter ... Changing 'dl=1' or 'dl=0' to 'raw=1' in a URL will cause an HTTP redirect" and tells app developers to "properly parse the URL and add or modify parameters as needed" (https://help.dropbox.com/en-us/share/force-download, read 2026-11-16). **This is the one exception to #22 Decision 11 ("never construct or parse DAM URLs")**: the provider parses the API-returned link with a URL parser (never string concatenation), deletes `dl`, sets `raw=1`, keeps every other parameter (`rlkey`, `st`) untouched, and rejects anything not on `https://www.dropbox.com` (or the documented legacy `/s/` form on that host). It never builds a link from a file id or path. The non-image `linkUrl` is the link exactly as the API returned it (the human-friendly preview page), unmodified.
14. **Alt text policy: property, else file name, else flagged empty.** Dropbox has no description or alt field (file metadata documents name, dates, size, hashes, `media_info`, `property_groups`: https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata.md). The only genuine metadata channel is **file properties**: a team can define a property template and attach a field to files. The provider therefore reads, when configured, one template id and one field name; `get_metadata` is asked for that template only (`include_property_groups` with `filter_some`), and the field's value, stripped to plain text, is the alt candidate with `source: property`. Otherwise the file name without extension, separators turned into spaces, `source: name`; otherwise empty with `source: none`. `source: description` is never produced by this provider. All candidates are stripped of markup and control characters, as in #22 Decision 13. The author always sees and may edit the value or mark the image decorative. If the owner wants a different convention (for example a sidecar naming rule or an embedded-metadata read) it is a follow-up, not v1 (Open Question 7).
15. **App registration and Dropbox's rules the README must carry.** One Dropbox app per worker deployment, created by the maintainer in the App Console: scoped access, **Full Dropbox**, the five scopes, redirect URIs for the deployed callback and the local one, "Allow public clients" off. The app name "may not include the word 'Dropbox'" or begin with "drop" (https://docs.dropboxapi.com/dropbox-api/docs/developer-resources/branding-guide.md), proposed name: **EW Multi-DAM Picker**; referring to Dropbox inside the picker ("Connect to Dropbox") is allowed because it identifies a Dropbox integration. A new app is in **development status**: it can be linked to your own account plus enabled development users, "up to 500 total Dropbox users", but "once your app links 50 Dropbox users, you will have two weeks to apply for and receive production status approval before your app's ability to link additional Dropbox users will be frozen"; production review expects a privacy policy and branding compliance and "will not be reviewed until your app has linked with at least 50 Dropbox users" (developer guide URL above). Whether this extension is ever opened to more than 50 authors is the owner's call (Open Question 6). Dropbox also lists "Don't build file sharing apps" among apps it does not allow (same guide); embedding images from one's own Dropbox is not a public file-sharing network, but its terms (https://www.dropbox.com/developers/reference/tos) were not read [OPEN: Question 6].
16. **Team spaces and namespaces are out of scope for v1.** All calls run against the user's default (home) root. Business teams with a Team Space keep shared team folders in a separate root that needs the `Dropbox-API-Path-Root` header and the `root_namespace_id` from `get_current_account` (https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/path-root-header-modes.md; `root_info`, https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/users/get-current-account.md). Brand folders are often team folders, so this is the likeliest first follow-up and a real limitation on Business accounts (Open Question 5); the mechanism is documented here so the follow-up is a provider-only change.
17. **Configuration split.** Secrets (secret store only): `DROPBOX_CLIENT_SECRET`. Non-secret vars: `DROPBOX_CLIENT_ID` (the app key, public by nature: it is in the authorize URL), `DROPBOX_SCOPES` (default the five scopes), `DROPBOX_ROOT_PATH` (optional browse/search root, default the namespace root), `DROPBOX_ALT_TEMPLATE_ID` and `DROPBOX_ALT_FIELD` (optional, both or neither), and a test-only `DROPBOX_TEST_ORIGIN` that redirects all three Dropbox origins to a local fake and is honoured only when the worker's local-environment flag is set (an RC check proves the production config never sets it). The shell's own vars and secrets (`PUBLIC_WORKER_ORIGIN`, `TOKEN_ENC_KEY`, `OAUTH_STATE_KEY`, the KV binding) are reused unchanged. A provider is "configured" when the client id and secret are both present (#22 Decision 10); otherwise it is omitted from the provider list.
18. **Rate and size budget.** Dropbox publishes no numbers: limits are "per-authorization", with `Retry-After` always present; it "does not publish exact rate limits" (performance guide above). Per request the worker issues: search up to 3 calls plus ceil(items/25) thumbnail-batch calls (at most 2 at the shell's 50-item cap), detail 3 calls (metadata, list links, create link), refresh at most 1 more: well inside the Free plan's 50 subrequests per invocation (#2 Further Notes). The thumbnail data URIs make a 24-item response roughly half a megabyte [ASSUMPTION: about 15 KB per 256-px JPEG]; the shell's page-size default stays 24. Shared links are subject to Dropbox bandwidth limits that affect **published pages**: Dropbox Basic 20 GB and 100,000 downloads per day, paid plans 1 TB to 4 TB, and a link "shared or downloaded too many times over a 24 hour period" is temporarily disabled (https://help.dropbox.com/share/banned-links). The README states that Dropbox links are for low-traffic or staging use, not a production CDN (Out of Scope names the alternative).
19. **Tooling and conventions** follow #1/#2/#22 unchanged (ESLint 8 + helix config, Stylelint 16, Node `node:test` for worker tests, `@web/test-runner`, Playwright Chromium, Node >= 22.12). Tests live in the provider folder; no new runner, no new seam.
20. **Docs ship with the code (AC4).** The extension README gains a Dropbox section: what the provider does and its limits (no folders, original-only rendition, public-link side effect, bandwidth), Dropbox-side setup (steps of Decision 15, scopes, redirect URIs, naming, development vs production), worker vars and secrets with the exact names, the optional alt-text property setup, `DROPBOX_ROOT_PATH`, local development (local redirect URI, `DROPBOX_TEST_ORIGIN`), privacy and retention (shared with #22's section), "site config keys read: none; no new config-sheet row". The #22 "add a provider" checklist is followed and ticked off in the PR.

## Further Notes

- **Dropbox's API answers browser CORS preflights for `https://da.live` (O1)**, as Wistia's does in the video picker. That makes it technically easy to put an access token into the page and call Dropbox from the browser; AC2 and AC6 forbid it, and the e2e host-allowlist check (DBX-E2E5) and the page-never-calls-Dropbox test make the forbidden shortcut fail loudly.
- **Dropbox refresh tokens do not rotate and do not expire**, so the Dropbox connection is more robust than a rotating-token vendor's, but a leaked stored refresh token is a standing credential until revoked. That is why encryption at rest, key separation and the real upstream revoke on Disconnect matter more here, and why the purge command and retention note from #22 are part of this provider's README.
- **Why not make every file's link at browse time or at insert time.** Browse-time creation would publish every file the author scrolled past; insert-time creation is the right moment but needs a shell step that does not exist. Detail-time creation (this spec) is the least-intrusive point within the contract (Decision 12, Open Question 2).
- **EDS and external images.** Whether Edge Delivery Services keeps an external `<img src>` in a DA document, and whether it follows the `raw=1` redirect to `dl.dropboxusercontent.com`, is unverified (carries #22 R12) [ASSUMPTION: kept and rendered as an ordinary external image]; manual step M-DBX6 observes it.
- **The Dropbox docs moved** to https://docs.dropboxapi.com (the old `www.dropbox.com/developers/documentation/http/documentation` page is client-rendered); every API claim below cites the stable `.md` page of the new site.
- **Template and shell are not built yet** (#2 and #22 have specs only). Everything here that says "the shell provides" presumes #22 has landed with its contract, plus its own gaps G1-G4 (#22 Decision 18).

**Auth flow (author to worker):** unchanged from #22: SDK token -> `Authorization: Bearer` -> #2 verification -> `identity.userId` -> record key `hash(userId, "dropbox")`.

**Auth flow (Dropbox connection)** is #22's six steps with Dropbox values: (1) `POST connect` returns `{ beginUrl }`; (2) the click handler opens the pop-up synchronously and navigates it to `beginUrl`; (3) `begin` verifies the ticket, sets the binding cookie, 302 to the Dropbox authorize URL of Decision 5 with the sealed `state` (kept under 2,000 bytes); (4) the user signs in to Dropbox and approves the listed access; (5) Dropbox 302s to the worker callback with `code` and `state`; the worker verifies state and cookie, exchanges the code with the app secret, requires a refresh token and the full required scope, calls `get_current_account` for the display name, stores the encrypted record, returns the static page; (6) the extension's `session` poll flips to connected. The record's access expiry is `now + expires_in` (about 14,400 s).

**Auth flow (per call):** read and decrypt the record, refresh if under 60 s remain (single-flight, no refresh-token rotation to guard), call Dropbox with `Authorization: Bearer <user's Dropbox access token>`, never the IMS token, normalise, respond.

## 4. Data contracts

**The worker API is #22's, unchanged** (`/dam/dropbox/connect|session|disconnect|assets|assets/{id}` and the two OAuth routes). Dropbox adds no routes. What the provider produces, in #22's normalised shapes:

**Capabilities:** `assetTypes: [image, video, document, audio]`, `sorts: [relevance, modified]`, `paging: page`.

**Summary (search items):** `id` = the Dropbox file id (`id:...`); `provider: dropbox`; `name`; `type` by the extension table; `thumbnailUrl` = `data:image/jpeg;base64,...` (or absent: Decision 4 fallback, unsupported format, over 20 MB, or conversion failure); `extension`; `fileSize` (`size`); `dateModified` (`server_modified`); `width`/`height` **omitted** (Dropbox does not return `media_info` in search or list results); `warnings: []` (no Dropbox equivalent of limited-use, archived or watermarked).

**Detail:** the summary plus `width`/`height` (when `media_info` is ready), `tags: []`, `description` and `copyright` absent, `alt { value, source: property|name|none }`, `renditions: [ { id: "original", label: "Original (<size>)", url, kind: original, width?, height? } ]` (empty when no usable public link), `defaultRenditionId: "original"`, `insertable { ok, reason? }`, `linkUrl?` (non-image files, the link as Dropbox returned it).

**`insertable.reason` (fixed strings, never upstream text):** "Dropbox does not allow a public link for this file", "The existing link for this file is not public", "The existing link for this file needs a password or has an expiry date", "This file cannot be shown as an image in a browser", "This file cannot be downloaded", "Sign-in with a verified Dropbox email is required to share this file".

**Dropbox-to-shell error map** (Decision 11):

| Dropbox | Shell outcome |
|---|---|
| `401` `invalid_access_token` / `expired_access_token` | refresh once and retry; second `401` -> delete record, `409 provider_reauth_required` |
| `401` `missing_scope` / `user_suspended` | as above (reconnect re-requests scopes; suspension is temporary, reconnect works after it ends) |

## 9. Open questions for the owner

1. **Thumbnails as `data:` URIs (R2, Decision 4).** Dropbox has no thumbnail URLs. Do you accept a one-line additive allowance in #22's contract (thumbnail field only may be `data:image/jpeg|png|webp;base64`) **before #22 is built**? If not, Dropbox ships without thumbnails (file-type placeholders) and AC1's "browse" is weaker; a worker thumbnail route would need new shell routes and is not recommended.
2. **When a public link is created (R3, Decision 12).** This spec creates (or reuses) the public link when the author opens a file's detail, because #22's contract has no "prepare for insert" step. Authors who only look at a file still publish a link to it. Do you accept that, or want #22 amended with an insert-time hook (a new provider method and one extra worker call at Insert)? Also: is creating public Dropbox links from an Adobe-authored tool acceptable under your policy, and should link creation be switchable off per deployment (read existing public links only)?
3. **Interface assumptions A1-A10 and provider secrets (Decision 3).** Please confirm in #22: provider-declared host list, asset-id pattern, page size passed to `search`, optional `thumbnailUrl`, opaque sort ids and a subset of types, three-class refresh errors, a `maxStateBytes` limit, a `getAsset` allowed to have an idempotent effect, and **provider secrets not listed in the wrangler `secrets.required` guard** (otherwise a Bynder-only deployment must set a dummy Dropbox secret to deploy). Do you also accept the single documented exception to "never construct or parse DAM URLs" (the `raw=1` edit, Decision 13)?
4. **API vs Chooser (Decision 2).** Confirm building the full OAuth provider required by AC2 rather than the much cheaper Dropbox Chooser (no worker, no production approval, what Contentful ships). Dropbox's own guide steers pickers to the Chooser; choosing the API commits you to the production-approval path above 50 users.
5. **Business teams and Team Space (Decision 16, R8).** Brand folders are often team folders, invisible without the path-root header. Is v1 (home namespace only) acceptable, or should the `root_namespace_id` support ship in this ticket? Also confirm the browse model: a configured root folder, non-recursive empty-search view (newest first within a scan window), no folder navigation. Is a flat "recent files in one folder" view good enough for authors?
6. **Dropbox app ownership, naming and policy (Decision 15, R9).** Who owns the Dropbox app (a personal or a company Dropbox developer account)? Proposed name "EW Multi-DAM Picker" (the name may not contain "Dropbox"; fixed once in production). Is the audience likely to exceed 50 Dropbox users (then production review, privacy policy and branding assets are needed), and have you read the Dropbox developer terms (https://www.dropbox.com/developers/reference/tos; not read here) regarding using shared links to serve published pages?
7. **Alt text and metadata (Decision 14, R7).** Dropbox has no description or alt field. Accept "file property (if your team defines a template) else cleaned file name, always editable"? Which template and field name would you use, or do you want a different convention (sidecar naming, embedded EXIF/IPTC) as a follow-up?
8. **Sandbox (R1).** Is there a Dropbox developer app and at least two test accounts (one Business with a restrictive link policy, ideally with Team Space)? Who creates and owns them? Without them, M-DBX1-M-DBX9 and real fixtures are blocked and the docs-derived fixtures are unverified.
9. **Hotlinking limits and the ingest alternative (R4).** Dropbox links are bandwidth-capped (20 GB / 100,000 downloads per day on Basic) and depend on the link staying alive. Accept "staging and low-traffic use, documented", or do you want a follow-up ticket that copies the picked file into DA/EDS media at insert time (robust, needs DA write APIs, changes what "insert" means)?
10. **Empty-query behaviour and paging caps (R6).** Dropbox's docs do not say whether `search_v2` accepts an empty query; this spec uses `list_folder` for the empty search and a bounded windowed re-walk for paging (3 calls, 300 results, scan cap) as defaults. Fine, or do you have knowledge of Dropbox's real behaviour? M-DBX3 will settle it.
11. **Names.** Config var names (`DROPBOX_*`), the proposed Dropbox app name, and the README section title "Dropbox" are proposals; the `ORG`/`SITE` assumption (`jazhou-adobe`/`ew-extensions`, #1 R10) is carried from #22.
