## Problem Statement

Content authors in Experience Workspace (EW) can insert images from AEM Assets (first-party), and after #23 from Cloudinary, and after #25 from Dropbox. Many customers keep their brand assets in **Frontify**. Today a Frontify user who wants a Frontify image on an EW page leaves EW, finds the asset in Frontify, opens its share or download dialog to find a link, copies it, comes back, pastes it into the document and retypes alt text that Frontify already stores on the asset. The pasted link is often the wrong size (a full-resolution preview where a 1,200 px image would do), nobody checks whether the asset is still inside its availability window or carries a licence, and the alt text is usually skipped.

The tool should do for Frontify what it does for the other DAMs: browse and search in the editor library, choose a rendition, use the asset's own alt text, insert. It must do so **per user**, because Frontify's own permissions decide what each author may see ("All access tokens in Frontify are issued in the name of a user and give you access to at most the permissions assigned to that specific user" [VERIFIED: authentication page]); it must keep the Frontify OAuth client secret and each author's tokens **in the worker only**; and it must plug into the existing shell as **one new provider module**, with **no new token-storage code**, reusing the connect/disconnect, sealed state, encrypted token store and refresh machinery #25 built.

Frontify is the picker's first **rotating-token** provider, which is the real engineering risk. Frontify's refresh returns a new access token and a new refresh token, invalidates the old access token, and a refresh token "can be used only once" [VERIFIED: authentication page, "3 - Refresh Token"]. A refresh race between two Runtime containers, a lost write after a refresh, or an ambiguous network failure that replays a consumed refresh token can therefore end a connection, which the non-rotating Dropbox grant never could. Alongside that, Frontify brings a per-customer domain (so the OAuth and API hosts are configuration, not constants), a callback that Frontify's own page documents as carrying `authorization_code` rather than `code`, GraphQL instead of REST, search scoped to one library, and renditions that are URL parameters on a CDN rather than a list of files.

## Solution

An author with a Frontify account opens the **Multi-DAM Picker** in the editor library. Frontify appears as a source (the shell's switcher shows once more than one provider is configured). The first time, the panel shows **Connect to Frontify** (#25's connect panel; this ticket adds no browser code). The author signs in to Frontify in a pop-up (the instance's own login, including SSO) and approves read access. From then on the author sees "Connected as <name>" with **Disconnect**, and the site's configured Frontify **library**: a thumbnail grid with asset titles, newest first, searchable by keyword (title, description, tags, metadata, and the other fields Frontify indexes), filterable by type (images, videos, documents, audio), sortable (newest, oldest, name A-Z, name Z-A, and relevance when searching), with "Load more". Selecting an asset shows a larger preview with title, dimensions, type and size, and the author chooses a **rendition width** (480, 800, 1200, 1600 or 2400 px, or the full-size processed preview; default 1200 px; widths larger than the asset are not offered). Alt text is prefilled from **Frontify's own alternative-text field** (or empty and marked decorative when Frontify flags the asset decorative), falling back to the description and then the title, with the source shown; it is always editable. Frontify's availability window, expiry and licences appear as visible warnings. Assets that are still processing, that the author may not download, or that are not embeddable file types are shown not insertable with a one-line reason. One click inserts an `<img>` with the chosen rendition at the cursor and closes the library; videos, audio and documents insert as a link with the asset title.

Behind it, the existing worker, extended only by a provider module, does everything sensitive. #25's plumbing runs the OAuth flow (sealed ticket and state, binding cookie, the encrypted per-author record in State, silent refresh under a State lock, upstream revoke on Disconnect); the Frontify module supplies the **HTTP mappings**: the authorize URL on the customer's domain, a JSON code exchange and a JSON refresh that handle the rotating refresh token, a revoke call, the account name (`currentUser`), and the GraphQL search and detail mappings. The Frontify OAuth client secret is a worker secret (an encrypted action input from `.env`); the author's Frontify access token is injected by the shell into each call and never reaches the browser; every GraphQL document is a fixed constant with all user input in variables; and every URL Frontify returns passes the shell's output URL policy before it can be inserted.

The Frontify provider is **one module**: a provider folder with its fixtures and tests, one registry line, the app-config inputs, `.env.example` entries and a README section. This ticket's diff touches nothing in the shell, the token store, the OAuth routes or the browser code.

## Implementation Decisions

(No file paths or code, except endpoint names, parameter names and wire contracts, which are API contracts. Layout is in the Build Analysis. Template contracts are referenced as "#2 Decision N", shell decisions as "#23 DN", plumbing decisions as "#25 DN".)

**D1. A provider module only; the footprint is machine-checked.** Frontify is implemented as one `user-oauth` provider (identity, capabilities, the OAuth mappings, the browse mappings, the metadata mapping) in its own provider folder, registered by one registry entry, per #23 D3/D5 and #25 D1/D4. There is **no browser code** for Frontify: the shell's UI is capability-driven and #25's connect panel carries no vendor knowledge (#25 UO12). **No token, cookie, sealing, encryption, lock or storage code** is written: the provider never receives a refresh token it must store, never reads or writes State, never sets a cookie and never refreshes itself (#25 D5, D9, D10). **No new action and no new route**: Frontify is served by the existing `api` and `oauth` actions. The pull request's registration footprint is exactly: the provider folder, the registry line, the worker app config's Frontify inputs, `.env.example`, the extension README section and the conformance-suite registration (the same allow-list as #25's RO2). A repo check proves it (FFY-RO2, FFY-RO6).

**D2. Surface and registration unchanged.** Library plugin only; the one `library` row from #23 is unchanged; **no new config-sheet row and no new entry page**; **site config read: none** (the README says so). Frontify appears in the existing panel when its worker configuration is present and the plumbing is enabled (#23 D5, #25 D4).

**D4. Credential kind and rejected alternatives.** Frontify is `user-oauth`: per-author OAuth 2.0 authorization-code grant with a **confidential client**, executed by the worker through #25's plumbing. Rejected:
- *Frontify Service App (client credentials, one shared identity).* Frontify recommends it "for all production integrations that do not require user-delegated access", but its access "is controlled via scopes and the user access of the user that owns the Service App", so every EW author would see that identity's assets, defeating per-user permissions and the criterion "per-user OAuth" [VERIFIED: authentication and OAuth-client pages]. It also returns no refresh token (`"refresh_token": null` in its sample response, [VERIFIED: authentication page]), so it would be a `service` provider; it is a possible follow-up for sites that accept a shared identity [OPEN: Question 11].
- *Frontify Finder (the vendor's ready-made picker).* "Frontify handles authorization and provides a ready-to-use ... user interface" [VERIFIED*: https://developer.frontify.com/document/8#/-/about-frontify-finder] and is "tightly coupled" to the browser-side Frontify Authenticator [VERIFIED*: https://github.com/Frontify/frontify-finder]. That puts a Frontify token in the browser (the criterion forbids it) and its UI cannot be driven by the capability-based shell. It is what Contentful ships [VERIFIED*: https://github.com/contentful/marketplace-partner-apps/tree/main/apps/frontify].
- *Developer tokens.* "testing only" and "perform[] all API requests in the name of a single user" [VERIFIED: authentication page].
- *PKCE with a public client.* Frontify requires PKCE only for public clients ("Public clients MUST additionally use the Proof Key Code Exchange (PKCE)"; "Frontify uses OAuth 2 (code flow with PKCE for non-confidential clients)") [VERIFIED: authentication and OAuth-client pages]. The worker can hold a secret, so the client is confidential and the plumbing's no-PKCE design suffices. Whether a confidential client may or must also send PKCE is not documented [OPEN: MF-P4; contingency A6].

**D5. OAuth client, authorize URL and code exchange (provider mappings).**
- *Client:* a Frontify **account admin** creates the OAuth client in the instance's applications settings with **Support Authenticator off, Confidential on**, at least one redirect URL, and the `basic:read` scope [VERIFIED: OAuth-client page: "You need to have a Frontify Account Admin permission to create a OAuth 2 Client"; steps 1-3, "[OFF] Support Authenticator", "[ON/OFF] Confidential", "Redirect Url. In any case, you must add one"]. The client "is only valid for the Account where you have created it" [VERIFIED: same page], which is why a worker serves exactly one Frontify domain (D9). **One client per workspace is recommended:** Stage and Production have different `oauth` callback URLs (different namespaces) and different `.env` files, so each gets its own client id and secret and the Stage client can be limited to a test library; whether one client may hold several redirect URLs is not documented, so per-workspace clients are the design that works either way [OPEN: MF-P6; Question 14].
- *Authorize:* a top-level navigation to `https://{domain}/api/oauth/authorize` with `response_type=code`, `client_id`, `redirect_uri`, `scope=basic:read` and the sealed `state` [VERIFIED: authentication page, "Example authorization (Private app)": `response_type=code&client_id={ID}&redirect_uri={URI}&scope={scope}`; `state` appears on the redirect and "The developer MUST verify the state parameter in response to prohibit CSRF attacks"; that the authorize endpoint accepts `state` as an input and echoes it is [ASSUMPTION], MF-P1]. `redirect_uri` is `{OAUTH_PUBLIC_BASE_URL}/frontify/callback` (the `oauth` action, #25 D7); it must be registered on the client, and the exchange sends the identical value. Whether Frontify accepts an `adobeioruntime.net` redirect host is not documented [OPEN: MF-P6, R19].
- *Callback:* Frontify's page shows the redirect as carrying `authorization_code` and `state` ("The URL contains 2 GET parameters: authorization_code and state", sample `https://{redirect_uri}?authorization_code=asfeYffSampleAuthCode&state=testStateA@s432!`), while its own token example names the field `code` (`-F code=Avv45866yyssf`) [VERIFIED: authentication page, "2 - Retrieve the Access Token"]. Which name a live instance sends is not established. The provider declares `authorization_code` (D3); probe MF-P1 settles it, and amendment A2 lets the plumbing accept either name so the answer cannot break the build.
- *Exchange:* `POST https://{domain}/api/oauth/accesstoken` with `grant_type=authorization_code`, `code`, `client_id`, `redirect_uri`, `scope` and, for a confidential client, `client_secret`. The endpoint takes "the following parameters in either JSON or multipart form request" (its sample cURL uses multipart `-F`; urlencoded is not mentioned) [VERIFIED: authentication page]; the provider sends **JSON** through the proxy helper (a single provider constant; **multipart is the documented fallback**, chosen by MF-P3 if JSON is refused). Whether `client_secret` is accepted or required in the body is not shown (the sample cURL omits it; the page lists "Your personal client_secret if you have a confidential client" among the values needed) [ASSUMPTION it is sent for a confidential client; [SECONDARY] https://damwiki.com/solutions/frontify/api; MF-P3]. The response carries `token_type`, `expires_in` (the sample shows 2,591,998 s, about 30 days), `access_token` and `refresh_token` [VERIFIED: authentication page]. There is no documented `scope` field, so the plumbing's required-scope check is skipped when `scope` is absent (#25 D5) and the scope the author consented to is whatever the OAuth client allows. The exchange runs in the `oauth` action and is **never retried** (#2 Decision 11 explicit POST opt-in not set).
- *Token result:* the provider returns the normalised result of #25 D5: `accessToken`, `expiresInSeconds` (required and positive; a response without a numeric `expires_in`, or without a refresh token, is refused so the connection attempt **fails closed**), `refreshToken`. `accountId` is not provided.
- *Account name:* a `currentUser { id name }` query with the new access token [VERIFIED: https://frontify.github.io/graphql-api-reference/query/currentUser.md.txt, "Get the current `User`", example selects `id` and `name`]. Whether `basic:read` suffices is not documented (the scopes page says `account:read` is for "account data, including users", with an admin required for other users' data [VERIFIED*: scopes page]; own-user data should not need it [ASSUMPTION; MF-P2]). If the query is refused for permission reasons the provider returns the **Frontify domain** as the label ("Connected to acme.frontify.com") instead of widening the scope; any other failure follows #25's rule (refuse the connection and revoke the fresh grant, #25 OA12).

**D6. Token lifetime and rotation (what Frontify demands of #25's plumbing, and how State changes the picture).** Access tokens are "short-lived (between one week and three months, depending on configuration)", the customer configures the lifetime, and the sample shows about 30 days [VERIFIED: authentication page]. The refresh is `POST https://{domain}/api/oauth/refresh`; "New access token is returned and the original access token gets invalidated. Refresh token can be used only once." [VERIFIED: same page, "3 - Refresh Token"]. The refresh response carries a new `refresh_token` (same shape as the exchange response), which #25 D5 specifies the shell stores in place of the old one. The refresh parameter list is not in the rendered text; it follows the token endpoint (`grant_type=refresh_token`, `refresh_token`, `client_id`, `client_secret`, `scope`) [SECONDARY: damwiki; MF-P3]. How #25 D9's steps meet Frontify, each **proved for Frontify** by tests here:
1. *Single flight in one container* (D9 step 2): two concurrent requests with an expired token cause one refresh.
2. *Cross-container lock* (D9 step 3): the refreshing request takes `lock.v1.<connKey>` with `putIfAbsent` (TTL about 20 s), **re-reads the record** after acquiring it, refreshes only if it is still stale, writes, releases. Frontify declares `rotatesRefreshToken: true`, so when the lock cannot be acquired within the wait bound the shell answers `502 upstream_unavailable` with `Retry-After` and **never refreshes unlocked** (a second use of a single-use token could end the connection). The Frontify refresh is a single attempt of at most the template's per-attempt timeout (8 s, #2 Decision 11), well inside the lock TTL, and its write follows immediately; the residual case "lock expires mid-refresh" needs a refresh slower than 20 s, which the attempt timeout rules out [INFERENCE].
3. *The refresh is never blindly retried.* A rotating grant retried after an ambiguous failure (the server consumed the token but the response was lost) replays a dead refresh token. The provider declares its refresh call **not safe to retry** (it does not set #2's explicit POST safe-to-retry flag, #2 Decision 11, UP7); Dropbox's refresh is declared safe because it never rotates (#25 D22). A transient refresh failure returns `502`, keeps the record, and the next request tries once more. **Residual:** if the failure was a timeout after Frontify had already consumed the token, the next attempt presents a dead token, answers *reauth*, finds nothing newer in State and ends in Reconnect; this is inherent to any rotating grant, rare (about one refresh per author per month) and is documented (R21).
4. *Stale access token after another container's refresh.* Because the refresh invalidates the old access token, a request that read the record just before a refresh completed gets `401` from Frontify. With State's point reads (D8 of #25) this is a narrow race rather than a stale-replica problem. The shell should **re-read the record and retry with a newer one before it forces a refresh** (a forced refresh with an already-consumed refresh token can end the connection, or, if Frontify burns the token family on reuse, destroy the new pair too) [Needs A3b; fallback: #25's re-read-before-destroy (RF8) still saves the connection, at the cost of one failed refresh].
5. *State semantics are only partly documented* (read-your-writes across containers, behaviour of conditional puts under concurrency, smallest TTL): #25's spike S-OA probes them, and the tests keep #25's stale-read double so the design does not depend on them (RF9). The outcome of a lost race is a reauth marker and **Reconnect** (no loop), never a corrupt state. **Frontify must not be enabled in Production before S-OA (P-OA4) has passed and a real rotation has been observed (MF-P5, MF4)** [OPEN: Question 12].
6. *Write failure after a successful rotation* is #25's RF10 (retry the `putIfPresent` once, keep the record in container memory, log by outcome only). The write is `putIfPresent`, so a Disconnect during the refresh is never resurrected (RF13).
7. *Reuse behaviour is undocumented*: whether reuse of a consumed refresh token burns the whole family, and what error body is returned, is [OPEN: MF-P5]. The classification (D8) is conservative so a vocabulary surprise never deletes a working connection.
8. *Retention.* Every record write passes the explicit `CONNECTION_TTL_DAYS` TTL (#25 D8; State otherwise applies one day). Frontify tokens live up to three months and the refresh token's own lifetime is undocumented [OPEN]; an author who does not use the picker for longer than the retention loses the record and reconnects, which is the intended behaviour.

**D7. Revocation.** Frontify has a revoke endpoint: `POST https://{domain}/api/oauth/revoke` with `token` (required) and `token_type_hint` (`access_token` or `refresh_token`; "In case of NULL value, the API internally looks into the type of token and revokes it if found"); "The response with a Status Code 200 indicates access token is revoked successfully" [VERIFIED: authentication page, "4 - Revoke Token", attribute table and sample cURL]. The sample cURL carries **no** `Authorization` header and no client credentials [VERIFIED: same sample]. The provider implements the optional `revoke`: on Disconnect the shell calls it best-effort and deletes the record regardless of the result (#25 D11). Whether revoking the access token also kills the refresh token (or the reverse), and whether client credentials are required, are [OPEN: MF-P5]. Defaults: revoke the **refresh token** (hint `refresh_token`) if the plumbing passes it, and the access token (hint `access_token`) as well, one call each, ignoring failures; with only the access token available, hint `access_token`. Because the call needs no bearer, Frontify does not need #25 D11's "refresh first if stale" step, which would **consume a rotating refresh token for nothing** at Disconnect [Needs A4; fallback: harmless, one extra rotation at Disconnect]. A revoke failure never blocks deleting the record and is never surfaced as an error.

**D8. Failure classification (provider mapping to #25 D5 classes).**

| Call | Frontify outcome | Class and shell outcome |
|---|---|---|
| `exchangeCode`, `refresh` | `400`/`401` whose JSON `error` is `invalid_grant` (or the body names a consumed, expired or revoked token) | *reauth*: the refresh case re-reads storage first, else destroys tokens, marker, `409 provider_reauth_required` (#25 D9 step 6) [ASSUMPTION: the form is standard RFC 6749; MF-P5] |
| same | `invalid_client`, redirect-URI mismatch, any other `4xx`, an unparseable body, a `3xx` (never followed) | *misconfigured*: `500 misconfigured`, record kept, no Reconnect prompt (an unclassifiable failure is never *reauth*) |
| same | `5xx`, network error, timeout | *transient*: `502 upstream_unavailable`, record kept; **never retried** for the code exchange or, for Frontify, the refresh (D6.3) |
| `accountName` | permission or scope error | label falls back to the domain (D5) |
| `accountName` | anything else | the plumbing refuses the connection and revokes the fresh grant (#25 OA12) |
| `revoke` | any | best-effort, ignored |
| `search`, `getAsset` | `401`, or a GraphQL error whose category says the token is invalid or expired | *reauth required* (the shell's token-rejected signal: re-read, then refresh once and retry once, #25 D9 step 4, A3b) |
| same | permission-category error or a null library node | forbidden (`403`), fixed message "no access to the configured library" |
| same | validation-category error on a search | bad request (`400`) |
| same | `429` | rate limited, `Retry-After` from the header or a fixed default (D18) |
| same | `5xx`, network error, GraphQL internal-category error, unparseable body | upstream unavailable (`502`) |

No upstream message text is ever returned or logged.

**D9. Per-portal domain handling.** `FRONTIFY_DOMAIN` is non-secret configuration and the provider's **only** outbound and authorize host. It must be a bare lower-case DNS name (no scheme, port, path, query, fragment, userinfo, whitespace, IP literal or trailing dot; an upper-case host is normalised to lower case); it may be a custom domain, not only `*.frontify.com` [VERIFIED: the authentication page and llms.txt both say "your domain"]. `outboundHosts` and `authorizeHosts` are therefore **computed from validated configuration at registration**, as Cloudinary's `outboundHosts` already is (#23 D6/D21, `CLOUDINARY_API_HOST`); #25's table lists `authorizeHosts` as static values for Dropbox, so this is amendment A1 (confirm both are config-derived; fallback: the provider factory builds the declaration from the action inputs at registry build). Redirects from Frontify are not followed (the proxy helper's `redirect: manual`, #2 Decision 11), so a vendor `3xx` cannot bounce a token or the client secret to another host (#25 SC7). A present-but-malformed value fails the registry build naming the setting (never the value), consistent with #23 D5 and #25 D4: the `api` action then answers every `/dam/*` request after authentication with `500 misconfigured` and the pre-deploy guard refuses the deploy; an **absent** required value omits the provider and the worker still serves the other providers. **Config drift:** a stored connection records tokens issued by one instance for one client; if an administrator later changes the domain or client id, the old tokens would be presented to a different host. The README says to disconnect/purge all connections after such a change (#25 D27's purge script), and amendment A5 proposes that the shell bind each record to a provider-supplied configuration fingerprint so a mismatch reads as not connected (fallback: the README procedure).

**D10. One instance, one library per deployment; Frontify permissions are the boundary.** A worker serves one EW site and one Frontify domain (D9). Browse is scoped to **one configured library** (`FRONTIFY_LIBRARY_ID`), because Frontify search is per library or per workspace project, with brand-level search in beta [VERIFIED: search guide, "On Workspace/Library Level / On Brand Level (through everything accessible by the user - in beta)"]; merging libraries would break pagination and ordering. All searches "are based on the user's permission. Some assets might be hidden depending on the user access level and setup of the account ... ranking/ordering might also be different across users" [VERIFIED: same page], which is exactly the per-user behaviour the criterion wants. Detail lookups are **not** pinned to the configured library: Frontify's permissions decide what a token may read, and the library is a browsing scope, not a security boundary [OPEN: Question 2]. Any library kind that exposes `assets` works (media, document, icon, logo [VERIFIED*: llms.txt, "Libraries" domain]); the README recommends a media library. Several libraries, a library picker, workspace projects, folder browsing and beta brand search are out of scope.

**D11. Browse and search: one fixed GraphQL document against the configured library, offset-paged.** The provider reads the library through `node(id)` with an inline fragment on `Library` and its `assets(page, limit, query)` field, with `query` carrying `search`, `types` and `sortBy`. **Changed from the earlier draft** (which used `library(id)`): the search guide's own sample is `library: node(id: "eY[BrandAssetsLibrary]") { ... on Library { id name assets(page: 1, limit: 25, query: $query) { total items { id title } } } }` [VERIFIED 2026-11-18: search guide, "Advanced Filters by Tag and Custom Metadata" sample]; the reference also lists the equivalent `library(id: ID!): Library` query [VERIFIED: https://frontify.github.io/graphql-api-reference/query/library.md.txt, "Retrieve `Library` details by Id."], and both are valid, so the documented sample is preferred and `library(id)` stays the alternative if MF-Q1 shows a difference [OPEN: Question 15]. Field facts [VERIFIED 2026-11-18: https://frontify.github.io/graphql-api-reference/interface/Library.md.txt ("`assets` (`limit`: `Int`, `page`: `Int`, `query`: `AssetQueryInput`): `AssetItems!` — Search or list `Assets` in this `Library`"), https://frontify.github.io/graphql-api-reference/input/AssetQueryInput.md.txt (`search`, `types`, `sortBy`; `type` is marked deprecated), https://frontify.github.io/graphql-api-reference/type/AssetItems.md.txt (`total`, `page`, `limit`, `hasNextPage`, `items`)]. The shell's `page` and `pageSize` map **1:1** to Frontify's `page` and `limit` (1-based [VERIFIED*: pagination page example `"page": 1`]; `limit` maximum 100 [VERIFIED*: https://developer.frontify.com/document/31#/guides/basics-pagination, "(max 100)"], so the shell's cap of 50 never binds), so no window emulation is needed. **Window:** "Search results are limited to a maximum of 10,000 assets"; without a search term "paginate through the results" to reach all [VERIFIED: search guide]. **D12. Asset identity and detail.** The shell id is Frontify's global asset id: an opaque Base64 string that starts with `ey` [VERIFIED*: Frontify naming conventions, "All Frontify IDs start with ey..."]. The provider's `assetIdPattern` (D3) is checked by the shell before any provider call. Detail is one `node(id)` query with an inline fragment per concrete asset type (`Image`, `Video`, `Audio`, `Document`, `File`, `EmbeddedContent`) [VERIFIED: preview-and-download guide, `node(id: "ey[Your Asset ID]")` with `... on Image`; type pages listed above]. Ids travel only as GraphQL variables, never in a URL path of an outbound call, so there is no path-injection surface. A `node` that is null or not an asset is `404 not_found`. `getAsset` has **no provider-side effect** (unlike Dropbox's link creation): it is a pure read.

**D13. Normalised contract mapping (to #23 D13).**
- *Summary:* `id` = the asset id; `provider` = `frontify`; `name` = `title` (capped 200); `type` by `__typename`: `Image` to image, `Video` to video, `Document` to document, `Audio` to audio, `File` and `EmbeddedContent` to other; `thumbnailUrl` per D14; `width`, `height` where the concrete type has them (Image, Video, Document; `Image.width` and `height` are `Int!` [VERIFIED: Image.md.txt]); `extension` = `extension`; `fileSize` = `size` (a `BigInt` [VERIFIED*: scalar page] coerced to a safe integer or dropped); `dateModified` = `modifiedAt` else `createdAt`; `warnings[]` per D17 (the summary query includes availability, expiry and licence ids so the grid can warn).
- *Detail* adds `description` (plain text, capped 1,000), `tags[]` (`tags { value }`, de-duplicated, at most 20 of 60 characters; AI-generated and manual tags are both listed, neither feeds alt text), `copyright` (= `copyright.notice`, plain text; `copyright.status` alone is not a warning), `alt { value, source }` (D16), `renditions[]` and `defaultRenditionId` (D14), `insertable { ok, reason? }` (D17), `linkUrl?` (D15).
- Only allow-listed fields are mapped; strings are stripped to plain text and capped; every URL passes the shell's output URL policy (https only, host in `deliveryHosts`, #23 D13).

**D14. Renditions and thumbnails: API-returned preview URLs at preset widths; never the original; never a download URL.** Frontify has no rendition list; a preview is a field on the asset. For images `previewUrl` takes optional `width` and `height` arguments and returns a CDN URL ("Preview `Url` which has optional `width` and `height` URL parameters. If parameters are not specified, `Url` without any URL parameters will be returned") [VERIFIED 2026-11-18: https://frontify.github.io/graphql-api-reference/type/Image.md.txt; its type is `Url!`]; the CDN does just-in-time processing, automatic next-generation formats by content negotiation, caps output at 4096 px, and "the original image cannot be retrieved via the URL" [VERIFIED: https://developer.frontify.com/document/20#/introduction/media-processing]. The provider asks the API for **one preview URL per preset width using aliases** (a few GraphQL fields per detail call; no URL building): `w480`, `w800`, `w1200` (default), `w1600`, `w2400`, plus `full` (no arguments, the "full-size preview (processed)"). Widths greater than or equal to the asset's own pixel width are dropped (no upscaling) except `full`; reported dimensions are the preset width with proportional height (for `full`, the asset size capped at 4096). All renditions are `kind: derivative`; **there is no `original` rendition**, because the original is not retrievable from the CDN and `downloadUrl` is a "Signed `Url` to download the original `Image` type file. Is null if the asset is download-protected" that "by default ... expires within 7 days"; the permanent variant "always points to the latest version of the asset" and is a download, not an embeddable image [VERIFIED: Image.md.txt; preview-and-download guide, "Download URL"]. `downloadUrl` is never requested by any query document. `FRONTIFY_DEFAULT_WIDTH` (one of the presets, default 1200) sets `defaultRenditionId`. *Thumbnails:* images use an aliased 320 px sized preview; other types use `thumbnailUrl`, which is nullable ("Provides a `Url` for the custom user defined thumbnail or a system generated one when possible"; "If no custom thumbnail has been set, the asset previewUrl will be returned as a fallback" [VERIFIED: Image.md.txt; preview-and-download guide, "Thumbnail URL"]); a null thumbnail leaves the field absent and the browser shows a placeholder (#23 D5). The two thumbnail sources use **different response aliases** because `previewUrl` is non-null and `thumbnailUrl` nullable, and GraphQL rejects two fields under one response name with different nullability [ASSUMPTION about the validation rule from the GraphQL specification; the schema-validation test in D22 proves it]. *Delivery host:* Frontify's documented CDN host is `media.ffycdn.net` [VERIFIED*: https://developer.frontify.com/document/20#/introduction/getting-started-1, URL format]; it is the default `deliveryHosts` entry, extra hosts come from `FRONTIFY_DELIVERY_HOSTS`, and a returned URL on any other host makes that rendition not insertable with the shell's fixed reason (so a wrong assumption fails visibly and is fixed by configuration) [ASSUMPTION that API-returned URLs use that host; MF-R4]. Open facts that decide AC1's "appropriate rendition URL": whether `previewUrl(width: N)` really resizes (the schema says "URL parameters" without naming them), whether the CDN URL loads **anonymously** for assets in non-public libraries, which formats (TIFF, PSD, HEIC, AI, EPS, SVG) come back browser-displayable [MF-R1, MF-R2, MF-R5; Question 8]. **Documented fallback (not the default; needs owner approval because #23 D5 forbids provider URL construction beyond the vendor's documented grammar):** if sized `previewUrl` does not resize, append the documented Media Processing parameter (`?mod=v1/resize=<width>`) to the unsized preview URL inside one provider function [VERIFIED*: getting-started page: "https://media.ffycdn.net/myImage.png?mod=v1/resize=450 will resize myImage.png to a width of 450 pixels while preserving its aspect ratio"], built by URL parsing and never from user input. *Static, not dynamic, links:* a static preview URL "always point[s] to a specific revision" and its "URL never changes, even if the asset is updated"; a dynamic URL (always the latest revision) exists but is **beta**, needs `X-Frontify-Beta: enabled` and `X-Frontify-Development-Flags: PUBLIC_API_DYNAMIC_CDN` and is outside the stable schema [VERIFIED: media-processing page, "CDN links"; preview-and-download page, "Dynamic Preview URL"]. v1 inserts **static** links, so an inserted image does not follow later edits in Frontify; the README says so [OPEN: Question 5].

**D15. Non-image assets.** `Video` `previewUrl` is the converted mp4, `Audio` `previewUrl` the converted mp3, `Document` `previewUrl` a preview with optional `width`, `height` and `page` arguments ("requesting a PDF from an HTML `<img>` tag will return an image preview of the first page, while linking directly to the PDF will display the full document inline") [VERIFIED: type pages above; media-processing page, "Smart PDF rendering"]. Such an asset is insertable as a **link**: `linkUrl` = its preview URL, text = the asset title, `renditions` empty. `File` (its `previewUrl` is only "`File` type icon in `svg` format"; the guide's table says "Limited. SVG icon available as previewUrl") and `EmbeddedContent` ("If the preview is not available, an svg icon will be returned") are **not insertable** in v1 with the reason "This Frontify asset type cannot be embedded". Classification uses the concrete `__typename`, never file extensions.

**D16. Alt text policy (AC1 "alt text from DAM metadata").** Frontify stores a native `alternativeText` ("Used by screen readers when the asset is not decorative") and an `isDecorative` flag on every asset type; "If true, alternative text is ignored" [VERIFIED 2026-11-18: Image, Video, Audio, Document, File and EmbeddedContent pages; `isDecorative` carries no beta marker there, whereas `previewBackgroundColor`, `provenance` and `targets` on Image do]. Ranked fallback, returned with its source and mapped to the shell enum: (1) `isDecorative = true` -> empty value, `source = property` (the shell has no decorative flag, so the browser shows an empty field labelled from Frontify's property; an optional `alt.decorative` flag is amendment B1); (2) a non-empty `alternativeText` -> `property`; (3) a non-empty `description` -> `description`; (4) the asset title with `_` and `-` turned to spaces and any extension removed (`Hero_Banner-2024.jpg` -> `Hero Banner 2024`) -> `name`; (5) empty -> `none`. Every candidate is stripped to plain text (no markup, entities or control characters), whitespace-collapsed and capped at 500 characters. The author can always edit it or mark the image decorative. AI-generated tags and custom metadata are not consulted in v1 (no configurable metadata property, unlike Cloudinary's alt-field settings).

**D17. Warnings, insertability and the download stance.** [ASSUMPTION: #23 D13 lists `warnings[]` without enumerating values; this spec assumes the shell renders a small fixed vocabulary of codes and uses `not-yet-available`, `expired` and `licensed`; if #23's final vocabulary differs, only this mapping changes (B2, Question 13).]
- `not-yet-available`: `availability.from` is in the future. `expired`: `availability.to` is in the past, or `expiresAt` is in the past [VERIFIED fields: `availability` (`DateTimeRange!`, "When `null` it represents an unspecified start and/or open-ended date"), `expiresAt` ("`Asset` available until date"): Image.md.txt; DateTimeRange.md.txt carried [VERIFIED*]]. `licensed`: the asset has at least one attached licence (`licenses`; a licence has `requireConsensus`, "`License` requires `User` to accept terms before download" [VERIFIED: License.md.txt]) [the semantic fit of "licence attached" as a warning is an assumption; Question 6]. Copyright status (`UNKNOWN`, `COPYRIGHTED`, `PUBLIC` [VERIFIED*: CopyrightStatus.md.txt]) is **not** a warning (it would flag most brand assets); the notice is returned as `copyright`. "Now" is the injected clock.
- **Not insertable, with a fixed reason (never upstream text):** conversion status `PROCESSING` ("Frontify is still processing this asset") or `PROCESSING_FAILED` ("Frontify could not process this asset") [VERIFIED enum: AssetStatusType.md.txt: `FINISHED`, `PROCESSING`, `PROCESSING_FAILED`]; `currentUserPermissions.canDownload = false` ("Downloading this asset is not permitted for you in Frontify"): embedding publishes the preview to anyone, which a download restriction is meant to prevent [ASSUMPTION about intent; VERIFIED field: AssetUserPermissions.md.txt, `canDownload: Boolean!`, "Check if current user has `Asset` download permissions for a specific `Asset`"; the conservative default blocks it, Question 6]; no usable https preview URL on an allowed host; `File` and `EmbeddedContent` (D15).
- Warn-only (insertable): availability and licence. The author decides; the README says the picker does not enforce Frontify's usage rules.

**D18. Errors and limits (mapped to the #2 error contract; fixed messages).** Frontify returns GraphQL errors as an `errors` array, "GraphQL errors will result in HTTP status code HTTP 422 Unprocessable Entity" (and "it is advised to limit retries of the same call") and "429 Too Many Requests" when over the limit [VERIFIED: rate-limiting page]; other sources suggest `200` with `errors[]` and categories `graphql`, `validation`, `permission`, `internal` [SECONDARY: error-handling page not read; MF-P7]. The provider therefore inspects the body for `errors` **regardless of status** and maps per D8; a response whose body is not the expected JSON is upstream unavailable, never parsed further. The limit is **2,500 requests per 5-minute rolling window**; over it Frontify blocks, "Not doing so might get you blocked for longer", "We are working on improving our rate limiting approach towards a leaky bucket. Error codes might change", and "Continuously making requests that result in GraphQL errors may flag as suspicious activity" [VERIFIED: rate-limiting page]. Whether the window is per token, per user or per account is not stated [OPEN]. Cost per author action is one GraphQL call per search page and one per detail view (plus the refresh when due); previews and thumbnails load from the CDN, not the API. The provider adds no extra throttling; the shell's debounce, page-size cap and per-author cache apply. A `429` without a `Retry-After` header (the 429 body and headers are not documented) uses a fixed default delay of 60 s [ASSUMPTION: value]. The provider never retries a `4xx` or a GraphQL-error result (the template retries only `429` and `5xx`). **Runtime budget (#2 Decision 9, #25 D25):** per `api` request the worker makes one State read, at most one State write and the lock pair only when refreshing, plus one GraphQL call (browse or detail) and at most one refresh call; all inside the action's 25 s timeout and the proxy's 15 s deadline, far under the 1 MB result limit (a 24-item page of Frontify summaries is a few tens of KB [ASSUMPTION; measured in MF1]), and counted against the namespace-wide 6,000 activations per minute and 100 concurrent activations shared with every other worker [VERIFIED: #2 Decision 9, system-settings page]. The `oauth` callback makes one exchange, one `currentUser` call and one State write (plus the reauth/retry cases of #25).

**D19. Retry flags (the #2 explicit POST opt-in).** Frontify's GraphQL **queries** are read-only POSTs and are declared **safe to retry on `5xx`**; `currentUser` likewise. The authorization-code exchange, the **refresh** (D6.3) and revoke are **not** retried. Frontify's `429` is handled by the template's `Retry-After`-aware retry for requests allowed to retry on `429` and by the shell's rate-limited mapping otherwise (#2 UP7: a POST is retried on `429` by default).

**D20. Per-author cache.** The shell's result cache applies to `user-oauth` per author only, keyed by the connection key (the hashed IMS user and provider), the configuration fingerprint (domain, client id, library id) and the full validated request, in **container memory only, never State** (#25 D14). Frontify default `FRONTIFY_CACHE_SECONDS=30`. Entries are purged on Disconnect and on *reauth required*. Detail and error responses are never cached.

**D21. Configuration split (app-config inputs, #2 Decision 9; the committed config holds `$NAME` references only, values live in the untracked `.env`).**
- **Provider inputs, non-secret, environment-specific (`$NAME` from `.env`, optional-by-declaration markers per #25 D4/TG2 so a Cloudinary-only or Dropbox-only deployment keeps deploying):** `FRONTIFY_DOMAIN` (required for the provider, D9), `FRONTIFY_CLIENT_ID` (required; public by nature, it is in the authorize URL), `FRONTIFY_LIBRARY_ID` (required, the Frontify global id). They identify the customer's instance, so they follow #23 D21's rule for `CLOUDINARY_CLOUD_NAME` and stay out of committed literals.
- **Provider inputs, non-secret defaults (literals in the committed config, reviewable):** `FRONTIFY_DEFAULT_WIDTH` (optional, one of 480, 800, 1200, 1600, 2400; default 1200), `FRONTIFY_DELIVERY_HOSTS` (optional, extra preview hosts), `FRONTIFY_CACHE_SECONDS` (optional, default 30).
- **Provider secret:** `FRONTIFY_CLIENT_SECRET` (a `$NAME` reference, optional marker, value only in `.env`; its name matches #2's secret-name rule, so UR3 keeps it from ever being a literal).
- **Both actions declare the Frontify inputs:** `oauth` needs the client id and secret for the code exchange and the domain for `authorizeHosts`; `api` needs the same for refresh, revoke and browse. Redeploying the worker after any change applies to both (a secret rotation is "edit `.env`, redeploy", #2 Decision 9; the rotation touches both actions, so redeploy the whole worker or both actions).
- **Shell inputs reused unchanged (#25 D16, #2):** `OAUTH_PUBLIC_BASE_URL`, `TOKEN_ENC_KEY` (+ `TOKEN_ENC_KEY_PREVIOUS`), `OAUTH_STATE_KEY`, `CONNECTION_TTL_DAYS`, `STATE_REGION`, `ORG`, `SITE`, `IMS_ORIGIN`, `ALLOWED_LOCAL_ORIGINS`, `AUTH_MODE`, `ALLOWED_IMS_CLIENT_IDS`. **No test-only origin input exists** (#25 D16): tests reach a fake Frontify through the test kit's injected `fetch` and Playwright routing, so no production code path honours a test origin and no guard has to forbid one.
- The provider is *configured* when `FRONTIFY_DOMAIN`, `FRONTIFY_CLIENT_ID`, `FRONTIFY_CLIENT_SECRET` and `FRONTIFY_LIBRARY_ID` are all non-empty; an invalid present value fails the registry build naming the setting (D9); if it is configured but any plumbing item is missing, the registry build fails naming the item (#25 D4) and the pre-deploy guard refuses the deploy. The redirect URI to register on the workspace's Frontify client is `{OAUTH_PUBLIC_BASE_URL}/frontify/callback`; **the README documents the two-step first deploy** (#25 D28: deploy with a placeholder base URL, read `aio app get-url`, set the base URL and register the redirect URI, redeploy). Whether Frontify allows more than one redirect URL on a client is not documented [OPEN: MF-P6], hence per-workspace clients (D5).

**D22. Input and output hygiene; schema validation.** Query documents are constant strings with **operation names** and typed variables; no template string ever contains user input. Search text is stripped of control characters; asset ids are validated by the shell pattern; `page`, `pageSize`, `type` and `sort` are integers or allow-listed values. From Frontify's response only allow-listed fields are mapped; unknown fields never reach the browser. Because Frontify's own guidance is to verify every field against the schema ("never invent GraphQL fields" [VERIFIED*: Frontify buildforfrontify SKILL.md]), every query document is validated in CI against a **vendored snapshot of Frontify's published SDL** (per-member `.sdl` files linked from llms.txt; no combined schema file exists: `schema.graphql` and `schema.sdl` under the reference site answer 404, observed 2026-11-18) with graphql-js, and a second check fails if a document uses a field the SDL marks beta (no beta header is ever sent). The snapshot carries its fetch date and a documented refresh script [OPEN: Question 9; `graphql` is at `17.1.0` on npm on 2026-11-18; fallback: golden-string tests plus MF-Q1].

## Testing Decisions

**What makes a good test here.** Assert external behaviour only: given a web-action invocation of `api` or `oauth` (raw `params`: headers, path, query; inputs from the kit's `makeInputs`; fake IMS, fake Frontify, in-memory store) assert the returned `{ statusCode, headers, body }`, redirects and cookies, the stored (encrypted) bytes and the requests the fake Frontify received (method, path, headers, JSON body, operation name, variables); given normalised data and an SDK result, assert the DOM and the SDK actions. Never assert on internal helper names or internal call counts. Properties asserted as negatives across every path: **no Frontify client secret, access token, refresh token, sealed ticket or state, binding nonce or encryption key ever reaches a response, header, redirect, log line or the browser**; **nothing runs before authentication succeeds on `api`, and the `oauth` action does nothing without a valid sealed value**; **no user input ever appears in a GraphQL document** (variables only); **no outbound request goes to a host other than the configured Frontify domain**; and **no consumed refresh token is ever presented a second time** on any non-race path.

**Proposed seams** (recorded here instead of asked, per #62). **This ticket adds no seam.** The seams are #2's, #23's and #25's; the one seam #23 introduced (P1, the provider interface and its conformance suite) is the primary one, because this ticket is a provider module.

## Further Notes

- **Docs say nothing about third-party pickers or OAuth in EW.** The EW developer doc cited by the ticket (https://www.aem.live/docs/ew/developing/apps-plugins) documents the SDK, `sendText`, `sendHTML`, `closeLibrary` and the config rows only (#1, #2, #23). Everything here derives from #23's and #25's source reading and Frontify's docs. The SDK action semantics (`sendHTML` then `closeLibrary`, fire-and-forget) and the library iframe and pop-up behaviour are #23's and #25's and unchanged.
- **Frontify prerequisites an agent cannot satisfy.** An **account admin** must create the OAuth client(s) and hand over the domain, library id, client id and secret. Frontify's developer sandbox is "granted selectively based on your use case" and is not automatic; Frontify says it is usually safe to build and test in production with "a dedicated library for testing API-based integrations" with limited access [VERIFIED*: sandbox page]. Until an instance exists, real verification (AC1, AC2, AC6 against real Frontify) is blocked and the fake tiers are the only automated proof [OPEN: Question 1].
- **API plan gating.** "Some API features may be restricted based on your current Frontify plan" [SECONDARY]; confirm the customer's plan includes API and OAuth access (Question 1).
- **Embedded-URL longevity.** Static preview URLs are pinned to a revision and "URL never changes, even if the asset is updated" [VERIFIED: media-processing page]. So an inserted image ignores later replacement of the asset, and whether it keeps loading after the asset is deleted is not established (the page says only that dynamic links stop when the asset is deleted [VERIFIED*: preview-and-download page]; MF-R3 observes). The README says "pickers insert references, not copies".
- **Public reachability of preview URLs.** Frontify positions the preview URL for "Embedding on Website / Application / Email-Newsletter" [VERIFIED: preview-and-download page, "Intended use-cases"], which implies anonymous reachability, but a statement that previews load **without any Frontify session for assets in non-public libraries** was not found [ASSUMPTION: the CDN URL is an unguessable capability link]. MF-R2 tests this and is the gate for AC1 (Question 8).
- **EDS and external images.** Whether Edge Delivery Services keeps an external `<img src>` in a DA document on publish is #23's [ASSUMPTION it is kept]; MF6 observes it for Frontify URLs.
- **Why Frontify, not Dropbox, proves the plumbing's second half.** Dropbox's non-rotating refresh and form-encoded exchange do not stress the rotation logic or the stale-read race; `fakeOAuthDam` does, in CI, and Frontify is the first real rotating vendor (#25 Further Notes). The S-OA and real-rotation gate (Question 12) sits before this ticket enables Frontify in Production.
- **Frontify API drift.** The GraphQL API has beta members (`X-Frontify-Beta`) and no versioning statement was found in the primary sources read [ASSUMPTION it is unversioned]; the schema-validation test and "no beta fields" rule are the controls. The rate-limit page itself says "Error codes might change" while the limiter moves to a leaky bucket.
- **Shared namespace host.** Every worker of the workspace is answered on the same `<namespace>.adobeioruntime.net` host, which is also what Frontify will see as the redirect host; the binding-cookie and gateway caveats are #25's (R25, R26).
- **#2, #23 and #25 are not built yet** (specs only; observed 2026-11-18: `shared/worker-template/` and `apps/multi-dam-picker/` hold only spec files, `apps/hello-world/` has the implemented #1 scaffold without a worker). Everything here that says "the shell provides" or "the template provides" presumes they landed as specified, plus the amendments of Open Questions A1-A6 or their fallbacks.

**Auth flow (author to worker):** SDK token -> `Authorization: Bearer` -> #2 verification inside `api` -> `identity.userId` -> record key `conn.v1.` + hash(userId, "frontify") (#25 D6).

**Auth flow (Frontify connection), #25's six steps with Frontify values in bold:** (1) `POST /dam/frontify/connect` returns `{ beginUrl }`; (2) the click handler opens the pop-up synchronously and navigates it to `beginUrl`; (3) `begin` (`oauth` action) verifies the ticket, sets the binding cookie and `302`s to **`https://{FRONTIFY_DOMAIN}/api/oauth/authorize?response_type=code&client_id=...&redirect_uri={OAUTH_PUBLIC_BASE_URL}/frontify/callback&scope=basic:read&state=<sealed>`** (built by the Frontify module and checked by the shell against `authorizeHosts`); (4) the author logs in at Frontify (SSO if configured) and approves read access; (5) Frontify `302`s to the callback with **`authorization_code`** (or `code`, A2/MF-P1) and `state`; the `oauth` action unseals state, checks the cookie, hands the code to the Frontify module, which **POSTs JSON to `/api/oauth/accesstoken` with the client secret from the secret accessor**, then `currentUser { id name }`; the shell requires a refresh token, writes the encrypted record with the retention TTL and returns the static page; (6) the extension's `session` poll flips to connected.

**Auth flow (per call, `api`):** read and decrypt the record -> refresh if under 60 s remain (single flight in the container, then the State lock; **the new refresh token replaces the old one; the old access token is now invalid**; a lock that cannot be taken answers `502` + `Retry-After`, never an unlocked refresh) -> GraphQL call with the author's access token (never the IMS token) -> on `401` re-read the record and retry with a newer one if present (A3b), else force exactly one refresh through the same lock and retry once -> normalise -> output URL policy -> respond. A second rejection destroys the tokens, writes the reauth marker and answers `409 provider_reauth_required`.

**Disconnect flow:** `POST disconnect` -> `revoke` (best-effort; no refresh first for Frontify, A4) -> delete the record -> purge the author's cache entries -> `204`.

### Amendments requested of the Dropbox ticket (#25) so Frontify is provider config only

Each is additive and optional with a default (like #25 D5); each has a fallback that keeps this ticket's AC3 and AC4 true. They are recorded here, not built here. Re-evaluated against #25's 2026-11-18 text; items #25 already provides are listed in D24 and dropped.

- **A1. Per-portal hosts (per-tenant domain).** #25 D5 declares `authorizeHosts` as the hosts `buildAuthorizeUrl` may point at and #23's `outboundHosts` as the hosts the proxy is pinned to; Dropbox's are constants, Frontify's is `FRONTIFY_DOMAIN`, i.e. configuration. Cloudinary's `outboundHosts` is already config-derived (`CLOUDINARY_API_HOST`, #23 D6/D21). **Ask:** confirm that `outboundHosts` and `authorizeHosts` are computed from validated config at registration and that the shell's checks (outbound pin, authorize-URL validation) use the computed values. **Fallback:** the provider factory receives the action inputs and returns the declaration, so nothing changes in the shell. Also confirm the stub `stub-oauth-a` ("per-tenant host") exercises exactly this.
- **A2. Callback parameter name.** Frontify's page shows `authorization_code`; its own token example says `code` (D5). #25's `callbackCodeParam` is one name (default `code`). **Ask:** allow a list (accept the first present, pass the value to `exchangeCode`). **Fallback:** declare `authorization_code`, and if MF-P1 shows `code`, declare `code`; the build waits for the probe either way, so this only removes a one-line change.
- **A3. Rotating refresh tokens.** (a) **Per-call retry flag:** #25 D22 treats Dropbox's refresh grant as "declared safe to retry", which reads as provider-declared; confirm so that Frontify's refresh can be declared not safe (fallback: the Frontify refresh call opts out through the proxy helper's flag, #2 UP7). (b) **Re-read before a forced refresh:** #25 D9 step 4 forces one refresh immediately on the token-rejected signal; for a rotating vendor a forced refresh with an already-consumed token can end the connection and, if reuse burns the family, destroy the new pair too, and State's lock only helps if the record is re-read first. **Ask:** after the lock is taken, compare the rejected access token with the freshly read record and skip the refresh when they differ (define "still stale" for a forced refresh this way). **Fallback:** #25's re-read-before-destroy (RF8) still saves the connection, at the cost of one failed refresh attempt (FFY-TK8 then asserts that behaviour). (c) **Gate:** the gate is #25's spike S-OA (P-OA4) plus a real rotation observed on Frontify (MF-P5, MF4) before Production (Question 12).
- **A4. Revoke ordering and inputs.** #25 D11 calls `revoke` "with a fresh access token (refreshing first if stale)". Frontify's revoke takes the token as a parameter and shows no bearer, and a refresh at Disconnect would consume a rotating refresh token for nothing. **Ask:** pass `revoke` both the access and refresh token, and add an optional member (default: refresh first) that lets a provider say it needs no fresh access token. **Fallback:** one extra rotation at Disconnect; the access token is revoked with whatever is stored.
- **A5. Config drift.** The record does not bind to the instance or client that issued its tokens (#25 D14 binds only the cache key to the configuration fingerprint), so after an administrator changes `FRONTIFY_DOMAIN` or `FRONTIFY_CLIENT_ID` old tokens would be presented to a different host. **Ask:** an optional provider-supplied configuration fingerprint stored in the authenticated data of the record (mismatch reads as not connected). **Fallback:** the README procedure (disconnect or purge all Frontify connections after such a change).
- **A6. PKCE (contingent).** Frontify requires PKCE only for public clients (D4); a confidential client needs none. If MF-P4 shows the instance requires it anyway, #25's no-PKCE plumbing would need an optional member (verifier carried in the sealed state, which also affects `maxStateBytes`). **Fallback:** none; Frontify would be blocked until added. Probability judged low [ASSUMPTION].
